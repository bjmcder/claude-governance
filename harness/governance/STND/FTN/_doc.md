## Purpose and scope

This standard holds the coding practice that is specific to Fortran, in source written to every revision of the Fortran standard, classic and modern. It adds to STND.CODE, STND.DOCS, STND.BUILD, STND.CONC, STND.MPI, STND.OMP, NUMER, and HW only what the language makes necessary. It covers the revision in force, the options of compilers, and deleted and obsolescent forms (STND.FTN.1, STND.FTN.2, and STND.FTN.3); interfaces and the association of arguments (STND.FTN.4 to STND.FTN.8); defined values, implied and explicit SAVE, and storage association (STND.FTN.9 to STND.FTN.12); kinds, literal constants, and floating-point exceptions (STND.FTN.13 to STND.FTN.17); parallel execution in DO CONCURRENT and OpenMP (STND.FTN.19 and STND.FTN.20); the Fortran forms of the hazards of MPI (STND.FTN.21 to STND.FTN.24); input and output (STND.FTN.25 and STND.FTN.26); interoperability with C (STND.FTN.27 and STND.FTN.28); failures (STND.FTN.29 to STND.FTN.32); legacy source and its modernization without a change of results (STND.FTN.33 and STND.FTN.34); the checks of Fortran code at run time (STND.FTN.35 and STND.FTN.36); and the conventions of names (STND.FTN.37).

STND.FTN.29, STND.FTN.30, and STND.FTN.31 instantiate PRIME.4, so they are binding and apply at every class. The rules of code that hold for every language, the responses to a listed failure and the checks that no execution setting removes among them, are in STND.CODE (STND.CODE.14 to STND.CODE.21), and this standard gives their Fortran forms. Every other provision is a default (GOV.19), which a project replaces by a recorded decision with an alternative that meets the same higher-level outcome (REPRO.7). The standard is agnostic of compiler, vendor, platform, tool, and revision of the Fortran standard: it names the statements, attributes, specifiers, and intrinsic modules of the language, and no compiler, option, or revision, and the repository configuration chooses the revision and the compilers (GOV.18). A provision that names a facility that not every revision provides applies where the revision in force provides it, as its condition states.

## Normative and informative parts

The body of a numbered provision, including a table it contains, is normative. Everything else is informative.

## Terms

This section fixes meaning and imposes no obligation, as the Lexicon does. Repository configuration, Static check, Execution setting, and Untrusted input have the meanings that STND.CODE gives them. For the term Untrusted input, the values that a procedure receives through its dummy arguments are its arguments, and each procedure that a module of the work makes public, by an attribute, by a statement, or by default, and each procedure of the work with the BIND attribute, is in the public interface that the term Untrusted input of STND.CODE takes in. Compilation unit and Checking build have the meanings that STND.BUILD gives them. Concurrent task and Protection have the meanings that STND.CONC gives them; each image, each thread that runs an OpenMP parallel region, and each iteration of a DO CONCURRENT construct is a concurrent task. MPI standard and MPI implementation have the meanings that STND.MPI gives them, and nonblocking operation and MPI datatype the meanings that the MPI standard gives them. Data-sharing clause has the meaning that the OpenMP specification of STND.OMP gives it. Program unit, scoping unit, main program, module, submodule, procedure, interface body, explicit interface, dummy argument, dummy data object, actual argument, common block, storage association, default initialization, assumed-shape array, assumed-size array, explicit-shape array, array section, subscript triplet, kind type parameter, literal constant, intrinsic module, image, locality specifier, C descriptor, unit, and preconnected have the meanings that the Fortran standard gives them.

## Notes

Direction and sources. The custodian's order of standards of 2026-10-24 lists a standard for Fortran, classic and modern, and the standing directions keep each standard agnostic of platform, compiler, vendor, implementation, and tool, and timeless, with strict determinism an option where it is feasible and not a requirement unless the acceptance criterion of the work or its consequence class demands it (STND.VVUQ.82, STND.VVUQ.83). The provisions therefore name the constructs of the language and no compiler, option, or revision. The custodian's directions for C++ and for Julia ask for the newest edition or version, which STND.CXX.2 and STND.JL.1 follow; no direction of the custodian that the corpus records asks the same for Fortran, so STND.FTN.1 has the repository configuration state the revision in force of each file and prefers no revision. This standard defines Revision in force, of a source file and of the Fortran standard, apart from the Edition in force of STND.CXX, which is of a translation unit and of the ISO C++ standard, so that each term keeps the scope of its own standard. A provision that names a facility of a later revision carries the condition that the revision in force provides it, as the first sentence of STND.FTN.19 does; a file at an earlier revision meets such a provision through a modernizing change that raises its revision in force, which is the project's choice. The source is research/fortran-notes/f1-fortran-language.md, which cites the clause numbers of the J3 working document of the 2023 revision (its S1), able to differ from the published text; a statement that the note marks as inference, or that it does not support, is marked unverified. The note research/round-addenda/a1-confirmations.md (a1) confirms the facts on initialization and the SAVE attribute from the J3 working document of the 2023 revision. The Fortran standard calls a compiler, its run-time library, and the computing system together a processor; the provisions say compiler, and STND.DEPS.8 records the revision of each compiler with each result.

The standard adds Fortran content to provisions that already hold the outcome, and does not restate them (GOV.31). STND.DOCS governs the documentation and the comments of Fortran source, from the reader they are written for (STND.DOCS.1) to their agreement with the code (STND.DOCS.11), and this standard sets no form of documentation comment. STND.BUILD holds the build. The compiled interface of a module is a generated file of STND.BUILD, which a build step writes and a later step reads as the interface of a unit that the source names: STND.BUILD.2 derives those inputs from the USE statements and the submodules of the source, STND.BUILD.3 keeps an incremental build equal to a clean one, and STND.BUILD.4 makes the file again only by its generator, so a stale interface does not reach a later compilation. STND.BUILD.11 states each setting that is able to change a result, and STND.FTN.2 names the ones that Fortran adds; STND.BUILD.12 fails the checks of a change on each warning of the toolchain; and STND.BUILD.13 keeps the checking builds of STND.FTN.35 apart. NUMER.5 records the working precision, which in Fortran is the kind of each real entity (STND.FTN.13); STND.VVUQ.1, STND.VVUQ.3, and STND.VVUQ.5 set each comparison within a tolerance, and Fortran has no intrinsic comparison within a tolerance whose defaults would need a provision, as those of STND.PY.20 and STND.JL.21 do; HW.5 and HW.CPU.3 state and restore the floating-point control state; and NUMER.16 and NUMER.17 govern an option that trades accuracy for speed. STND.CONC holds the rules of concurrency for every model, STND.MPI and STND.OMP the rules of those models, STND.CODE.22 to STND.CODE.26 the rules of each foreign interface, and STND.CXX.21 the C++ side of one.

Revisions and compilers. A conforming processor is able to report each obsolescent form and each form that the numbered syntax rules and constraints do not permit, the deleted forms among them (S1 4.2), which is what the check of STND.FTN.1 asks; conformance "does not ensure that a program will execute consistently on all or any" processors (S1 4.2), which is why STND.FTN.1 and STND.DEPS.8 concern the compilers as well as the revision. The deleted forms include the real DO variable, PAUSE, ASSIGN, the H edit descriptor, the arithmetic IF, and the nonblock DO (S1 B.1, B.2); the obsolescent forms include fixed source form, the computed GO TO, statement functions, ENTRY, the labeled DO, COMMON, EQUIVALENCE, the specific names of intrinsic functions, and FORALL (S1 B.3). The list has grown at most revisions, and the 2023 revision added none (S2), so the term Obsolescent form takes the later published revisions as well, while the check of STND.FTN.1 reports only the forms that the revision in force lists. A deleted form that a compiler still accepts is an extension, which STND.FTN.2 records and STND.FTN.3 keeps out of new and altered statements. A conversion of a file from fixed to free source form is a modernizing change of its own. The exception in the second sentence of STND.FTN.3 lets a change gather the declarations of an existing common block into the one source text of STND.FTN.12; the replacement of the block by module variables, a row of STND.FTN.34, removes the form. That compilers offer options that change the default kinds, or give local variables static storage or an initial value, is unverified; such an option changes the meaning of conforming source without a change to it (STND.FTN.2).

Interfaces. With an implicit interface the compiler does not compare actual and dummy arguments, and a mismatch of type, kind, rank, or number is a program error that the Fortran standard does not require a processor to diagnose; an explicit interface is required in 20 situations, assumed-shape, pointer, allocatable, optional, and VALUE arguments among them (S1 15.4.2.2). An interface body written for an external procedure repeats the error that it is meant to prevent unless it is compared with the definition, which the second sentence of STND.FTN.4 asks; a reference that reaches no explicit interface is the report that the same check makes, and STND.BUILD.12 fails the change on it. Implicit typing makes a misspelled name a new variable (S1 8.7); an internal or module procedure takes the implicit typing of its host and an interface body does not, by the rules of host association (unverified) (STND.FTN.5). A dummy argument of intent OUT is undefined on entry, an allocatable one is deallocated on entry, and one of a derived type with default initialization is reset (STND.FTN.5, STND.FTN.9). Under sequence association, "the rank and shape of the actual argument need not agree with the rank and shape of the dummy argument, but the number of elements in the dummy argument shall not exceed the number of elements in the element sequence of the actual argument" (S1 15.5.2.12); an assumed-size array has no extent in its last dimension against which to check a subscript, and a leading extent that differs between caller and callee reads another element (STND.FTN.6). Interfaces of C and of libraries outside the work fix the form in the exception.

Aliasing. While an entity is associated with a dummy argument, it is changed only through that dummy, except in the stated cases of POINTER and TARGET dummies; for CALL SUB(A(1:5), A(3:9)), "the array section A(3:5) cannot be defined, redefined, or become undefined" through either dummy (S1 15.5.2.14 and its Note 2). The compiler is free to keep values in registers or to reorder, the program is not conforming, and no diagnosis is required, so the failure shows at one level of optimization and not at another (STND.FTN.7). A further restriction of the same clause on references through other names during the call is unverified, and STND.FTN.7 does not state it. A discontiguous actual argument for an explicit-shape, assumed-size, or CONTIGUOUS dummy is able to be passed by a copy in and out (S1 Note 6 of 15.5.2.5), so a pointer or a C address that a callee keeps for such a dummy designates a temporary after the return (STND.FTN.8). The Fortran standard admits pointers that alias a TARGET dummy only in the cases that it states (S1 15.5.2.14); STND.FTN.8 is the simpler rule, and a project that relies on those cases replaces it by a recorded decision.

Defined values and saved state. Local variables, function results, dummies of intent OUT, newly allocated variables, and LOCAL variables of DO CONCURRENT have no defined value until assigned, and the Fortran standard asks no processor to detect the use (S1 4.2, 11.1.7.5); private copies under OpenMP are covered by STND.OMP.6 (STND.FTN.9). Explicit initialization of a variable that is not in a common block "implies the SAVE attribute" (a1, 8.4 paragraph 3), and a variable that a DATA statement initializes has the SAVE attribute (a1, 8.6.7), so REAL :: s = 0.0 in a subroutine sets s once and keeps its value between calls, and the OpenMP specification treats such a local as shared (S3); this has held since Fortran 90, and before that it was processor dependent (S1 4.3.8). STND.FTN.10 makes the attribute visible where the author meant it and puts a value meant for each call in an assignment. Unlike explicit initialization, the default initialization of a component of a derived type does not imply that the object has the SAVE attribute (a1, 7.5.4.6), so the first sentence of STND.FTN.10 excepts a variable that only default initialization initializes; that note read the working document of the 2023 revision alone, and that earlier revisions agree is unverified. A variable with the SAVE attribute, a module variable, and a variable in a common block are shared mutable objects under STND.CONC whenever concurrent tasks access them and one writes, which STND.CONC.3 governs; STND.FTN.11 names them because Fortran shares them without a declaration that shows it. A pure procedure meets STND.FTN.11 by construction, since the Fortran standard forbids it to define such variables and a processor diagnoses the violation (S1 15.7). COMMON and EQUIVALENCE are "error-prone" and "can inhibit performance" (S1 B.3.11): declarations of one block that differ between scoping units overlay storage silently, and one INCLUDE line for each block gives one declaration; a block declared outside a main program or a module is saved in each scoping unit that declares it (S1 8.5.16) (STND.FTN.12).

Kinds and constants. The values of kind parameters are not specified by the language, so a literal kind number is not portable, and SELECTED_REAL_KIND maps a precision and a range to a kind (S1, S4 20.1.9) (STND.FTN.13). A real literal constant without a kind parameter is of default kind whatever the variable it initializes, and "the significand may be written with more digits than a processor will use" (S1 7.4.3.3), so 0.1 stored in a variable of a wider kind carries the rounding error of the default kind. The first sentence of STND.FTN.14 therefore reaches the literals that meet an entity of another kind, written with a kind parameter or with a D exponent for double precision. Where an operation combines real operands of different kinds with the same precision or range, the kind of the result is processor dependent (S1 10.1.9.3 and Annex A); the second sentence of STND.FTN.14 asks an explicit conversion for every mixed operation, which also shows the precision on which the code relies. Fortran has no checked integer arithmetic in the language, unlike Julia (STND.JL.17); the behavior of an integer result outside the range of its kind is not established (inference, unverified), and STND.FTN.15 asks the check in either case.

Floating-point exceptions. Halting "is not precise and may occur any time after the exception has occurred", and the initial halting mode is processor dependent (S1 17.6), which is why STND.FTN.16 has the main program set it and HW.5 records it in the delivered arithmetic; a halt names a location near the cause, not at it. A library has no start of its own: a library that sets the modes changes the state of its caller, which STND.CONC.17 asks a library to leave unchanged and the third sentence of HW.CPU.3 asks restored before control returns to code that the hardware contract does not cover. HW.CPU.3 confirms the state in each thread or pool that computes, and STND.OMP.30 and STND.OFFLD.14 keep code from relying on a floating-point environment outside the host code or region that sets it, so a mode set at the start of the main program says nothing of a target region, and the run of STND.FTN.36 is a run on the host. An intrinsic procedure leaves the flags of overflow, division by zero, and invalid operation as they were on entry (S1 17.5), and the procedures that save and restore the floating-point status are the Fortran means of HW.CPU.3; whether a processor restores the halting and rounding modes at the return from a procedure of the work is unverified. A program that neither halts at these exceptions nor reads their flags continues past an invalid operation without a trace, which is why HW.5 has the hardware contract state the handling of non-finite values. The support of the IEEE modules is a property of the processor and the kind, which the IEEE_SUPPORT inquiry functions report (STND.FTN.16). Halting is among the facilities that a processor is free not to support, so STND.FTN.36 asks its run where the compiler and the host of the work support halting at these exceptions, and a work without that support is not blocked. The relations <, <=, >, and >= signal on a NaN, and == and /= are quiet (S1 C.1, 17.11), so under halting at invalid operation an ordered comparison of a NaN halts the program; a quiet comparison lets a NaN reach a branch without a trace, which is why the second sentence of STND.FTN.17 reaches only the comparisons that code is designed to make on a NaN (STND.FTN.17). A test of x /= x for a NaN is one that an option assuming finite values is able to remove, a hazard that is unverified for Fortran compilers. The first sentence of STND.CODE.21 keeps code that holds such a check from an option that, by the documentation of its compiler, lets the compiler assume finite values, as a default for every language, at the cost of one choice of option for a file that holds a required check; no binding provision rests on the hazard for Fortran, and STND.CXX.18 binds the same sentence for C++.

Parallel execution. The constraints of DO CONCURRENT forbid RETURN, image control statements, branches out of the construct, references to impure procedures, and the procedures that change floating-point modes and flags, and a processor diagnoses them; the locality of a variable is LOCAL, LOCAL_INIT, REDUCE, SHARED, or unspecified; a LOCAL variable is undefined at the start of each iteration; REDUCE combines "in any order"; a variable of unspecified locality that more than one iteration defines is undefined after the construct; and a SHARED variable that one iteration defines and another references breaks the rules without a diagnosis (S1 11.1.7.5). The construct does not promise parallel execution, so STND.CONC.11 keeps its iterations from waiting on one another. DEFAULT(NONE) makes each omission of a locality a constraint that the compiler checks (STND.FTN.19); locality specifiers came with the 2018 revision and REDUCE with the 2023 revision (S1 C.1, S2), and a variable declared in a BLOCK construct inside the body is local to its iteration (unverified). STND.CONC.21 and STND.CONC.22 govern a result that depends on the order in which REDUCE combines values or on the number of threads that a compiler uses, and STND.CONC.24 the tests at several numbers of threads where an option runs the iterations in parallel. Images are concurrent tasks: image control statements, events, and atomic subroutines are the synchronization that STND.CONC.3 asks for coarrays; ERROR STOP ends every image (S1 11.4), which STND.CONC.2 asks of a halt; and a failed image, in the revisions that define it, changes the control flow of the other images (S1), and a status that reports it is answered under STND.FTN.30. Under OpenMP, STND.OMP.5, STND.OMP.6, and STND.OMP.7 govern data-sharing, and the Notes of STND.OMP already state that procedures with saved or initialized locals share them; STND.FTN.11 states the same for every model. Members of a common block named in a clause other than shared "no longer have a Fortran storage association with the common block" (S3) (STND.FTN.20); how a threadprivate directive names a common block is not settled by the sources and is unverified.

MPI. STND.MPI says nothing of Fortran, and the MPI standard states that its Fortran bindings are "a property of an MPI library together with the Fortran compiler suite" (S4 20.1.7). A compiler assumes that a local variable does not change across a call that does not receive it, so it is able to keep a buffer in a register across the wait and to "schedule the load of buf earlier than typed in the source" (S4 20.1.17.1); the ASYNCHRONOUS attribute, in a BLOCK construct or a procedure of limited scope as the example of S1 C.13 shows, or the routine that synchronizes registers after the wait, prevents it, and the MPI implementation reports through a constant whether its binding protects such buffers (STND.FTN.22). Where the implementation reports that it does not support array sections, "the use of Fortran arrays with subscript triplets as actual choice buffer arguments in any nonblocking MPI operation ... may cause undefined behavior" (S4 20.1.12), because the copy that the compiler makes is released at the return of the call, before the operation completes. STND.MPI.16 asks the buffer of a pending operation to stay allocated and unwritten until its completion, which such a copy does not do, and STND.FTN.23 keeps the copy from arising; whether the same holds for one-sided and split collective operations is unverified. The module mpi_f08 is the only binding that, by the MPI standard, the Fortran standard fully supports, and the include file mpif.h gives implicit interfaces with no checking of arguments and is deprecated by a recent revision (S4 20.1.5, 20.1.10); STND.MPI.1 keeps a deprecated facility out, STND.FTN.4 keeps out a binding with implicit interfaces, and STND.FTN.21 asks for the binding that the Fortran standard fully supports. The MPI datatypes for Fortran data are defined by kind, through the precision and range of SELECTED_REAL_KIND, and match only for equal precision and range (S4 20.1.9), which STND.FTN.24 adds to the type signatures of STND.MPI.14.

Input and output. A unit number is a nonnegative integer that the program chooses, and numbers chosen by hand in two components collide; a library that connects a unit by a fixed number shares that number with its caller, the hidden coupling of DSGN.14. The NEWUNIT= specifier of later revisions lets the compiler choose the number, and ISO_FORTRAN_ENV names the preconnected units INPUT_UNIT, OUTPUT_UNIT, and ERROR_UNIT; input from the unit of an asterisk is preconnected on image 1 alone (S1 12.5.5, 12.6.4.3) (STND.FTN.25). The order of the records that different iterations of DO CONCURRENT write to one sequential file is processor dependent (S1 11.1.7.5, Annex A), and the records of different images are not ordered by the language (S1 12.5, 16.10.2) (STND.FTN.26); output gathered from the parallel parts and written by one image in a fixed order is one remedy. STND.FTN.26 is the Fortran form of STND.CONC.30: the constraints of DO CONCURRENT forbid image control statements and references to impure procedures, so no protocol of its iterations orders their records, while image control statements are able to order the writes of images, which the second sentence of STND.FTN.26 admits.

Interoperability with C. BIND(C), the kinds of ISO_C_BINDING, C_PTR, and the C descriptor define the boundary; later revisions let an interoperable procedure take allocatable, pointer, optional, assumed-shape, and assumed-rank dummies (S1 18, C.1). The extents and strides in a C descriptor have the C type ptrdiff_t and not default integer, the layout of the descriptor is fixed only through its functions, and a LOGICAL of default kind is not interoperable (S1 18) (STND.FTN.27). A test with an array section of a stride other than one exercises the descriptor where errors of stride hide (STND.FTN.28). STND.FTN.27 and STND.FTN.28 give the Fortran forms of STND.CODE.22 and STND.CODE.23.

Failures. Fortran has no exceptions, so the responses that PRIME.4 admits are a halt with a diagnosis, the designed safe state, a visible degradation, and the return of the condition, which a subroutine makes in a status argument because it has no result (STND.FTN.29, the Fortran form of STND.CODE.14, whose pass of the condition to the caller in its result, in an argument that the caller passes to receive it, or by a mechanism of the language that propagates it takes in Fortran the result of a function and the status argument). Without a STAT=, IOSTAT=, or CMDSTAT= specifier, an error of an ALLOCATE, an input or output statement, or a command ends the program by error termination, a halt whose diagnosis is the processor's (unverified); with the specifier, the program receives the condition (STND.FTN.30), and the ERRMSG= and IOMSG= specifiers give the text of a diagnosis. A failed allocation is resource exhaustion, and an input record that does not match its format is invalid input; an end of file that the code expects is not a condition that PRIME.4 lists, and STND.CODE.12 governs a status that code discards for another reason. Checks of subscripts against bounds are a facility of the compiler, set by an execution setting, and the Fortran standard requires no processor to diagnose an out-of-range subscript, so the check of STND.CODE.6 for an untrusted subscript is a test in the code (STND.FTN.31). It is made where the untrusted input enters, or, for a bound that is not known there, at the first point at which the bound is known. An assumed-size dummy has no extent in its last dimension, so its test is against the extent that the caller passes; where an interface that a library fixes passes none, a procedure of the work that takes the extent and calls the library is one remedy. STND.CODE defines the term Untrusted input once for every language, and the Terms of this standard place in the public interface that the term takes in each procedure that a module makes public, an entity of a module being public unless the module makes it private, and each procedure with the BIND attribute, as STND.PY and STND.JL place the functions of their public interfaces. The custodian's ruling of 2026-10-23 that this reach raises no floor was made for STND.PY and STND.JL, and the ratification of 2026-10-24 extended the reach to this standard. An external procedure that the documentation or the repository configuration names for use by code outside the work is in the interface for outside use of STND.CODE, and the paragraph on the floor argues that reach; an external procedure that nothing names is not, which keeps out the external procedures that in legacy code are the internal structure of a program. ERROR STOP initiates error termination of every image (S1 11.4), where STOP initiates normal termination, so a halt on a failure by ERROR STOP keeps a workflow from reading it as a normal end (STND.FTN.32); the exit status that a compiler reports for each is unverified. ERROR STOP ends the images of one Fortran program, and each process of an MPI execution is a program of its own, so ERROR STOP alone meets STND.MPI.6 only where the hardware contract of STND.MPI.7 states that the end of one process ends the others (unverified for each MPI implementation). Whether ERROR STOP is permitted in a pure procedure depends on the revision (unverified), and the return of the condition under STND.FTN.29 remains open there.

Legacy source and modernization. A conversion of source form, IMPLICIT NONE with each name declared, a computed GO TO replaced by SELECT CASE, and a labeled DO replaced by END DO change no result by the semantics of the language; the steps that are able to change one are the rows of STND.FTN.34. That an intrinsic reduction, SUM among them, combines in an order of the processor's choice is unverified. Columns of fixed-form source past the last significant position are ignored, so a conversion to free form that keeps them makes them part of the statement (inference from the significance of position 72, unverified). The legacy list follows the list of exempted modules of STND.PY.6: existing source enters it at the change that adopts this standard, a change of a compiler or of the revision in force, or a revision of this standard that adds a provision the list names, and otherwise the list only shrinks. The provisions that it names are those that a check or a reviewer decides from the text of one file; the others concern the behavior of code at a call or a run, which no entry for a file states. One reason serves a class of forms, so an entry for a file in fixed form that uses COMMON throughout states its reason once for each. An entry for external code that the work incorporates is able to cite as its reason the record of STND.DEPS.11, which keeps that code apart. A file that the list holds for STND.FTN.13 or STND.FTN.14 takes its working precision from the default kinds that the options of STND.FTN.2 set, which is where the record of NUMER.5 reads it.

Checks. A processor is able to report the obsolescent forms, the forms that the numbered syntax rules and constraints do not permit, an unsupported kind, inconsistent use of names, and a nonstandard intrinsic procedure or module (S1 4.2), so the numbered constraints are checkable during compilation (STND.FTN.1, STND.FTN.4). The rules that the Fortran standard states without a constraint are not: overlap of arguments, use of an undefined value, a subscript out of range, a shape that sequence association mismatches, an integer out of range, and unsynchronized access. They are checked by the runs of STND.FTN.35 and STND.FTN.36, by STND.CONC.25 for data races, and by review. A check that the Fortran standard does not require is able to be absent from a compiler, which is why STND.FTN.35 has conditions; each such build is a checking build of STND.BUILD.13, and the fixed value of its second sentence keeps the verdict of a test the same on each run, as STND.CODE.9 asks.
