## Purpose and scope

This standard holds the conventions of Python source that the language-neutral practice of STND.CODE and STND.DOCS leaves to the language. They cover style from the Python Enhancement Proposals, enforced by tools at each change (STND.PY.1 and STND.PY.2); annotations under strict type checking (STND.PY.3 to STND.PY.9); docstrings in the numpydoc format, with the examples of the documentation run as doctests (STND.PY.10, STND.PY.11, and STND.PY.12); the declared and checked releases of Python and of the work's dependencies, and the lock files of the environments that produce reported results (STND.PY.13, STND.PY.14, and STND.PY.33); random number generators and values that vary between runs (STND.PY.15 to STND.PY.19); comparisons within a tolerance (STND.PY.20); reporting from library code, and the hooks that report an exception that no handler catches (STND.PY.21, STND.PY.22, and STND.PY.32); idioms of Python source (STND.PY.23 and STND.PY.24); the handling of failures (STND.PY.25 to STND.PY.31); and foreign interfaces (STND.PY.34 to STND.PY.37). STND.PY.22, STND.PY.25, STND.PY.27, STND.PY.30, and STND.PY.32 instantiate PRIME.4, and STND.PY.4 instantiates GOV.48 and binds agents alone, by its own force (GOV.48); STND.INSTR.10 carries it into the agent instructions. These six are binding and apply at every class. STND.PY.22 states the one set of responses to a condition that PRIME.4 lists, in the Python form of STND.CODE.14, and the other provisions refer to it. The provisions of STND.CODE hold for Python as for every language, and the Notes give their Python forms. Every other provision is a default (GOV.19) and a recommendation, which a project replaces by a recorded decision with an alternative that meets the same higher outcome (REPRO.7, PRIN.10). The standard is agnostic of platform, version, and tool: the provisions state what a tool or a reviewer decides, and the project chooses its versions and tools in its repository configuration and its dependency record (GOV.18).

## Normative and informative parts

The body of a numbered provision, including a table it contains, is normative. Everything else is informative.

## Terms

This section fixes meaning and imposes no obligation, as the Lexicon does. Repository configuration, Static check, Execution setting, Untrusted input, High-assurance code, and High-assurance coding standard have the meanings that STND.CODE gives them; Work documentation has the meaning that STND.DOCS gives it.

| Term | Definition |

## Notes

The custodian's directions of 2026-10-22 are four: use the PEP standards for style and idioms, enforced with mechanical tools wherever possible; always use types and type checking; use the numpydoc docstring style; and format code so that it reads by the logical grouping of its instructions. The custodian's rulings of 2026-10-23 add that the standards are platform and compiler agnostic and that the project chooses its versions and tools. Each provision therefore states an outcome that a tool or a reviewer decides from the source and the repository configuration, and names no version, platform, or tool (GOV.18). Where a Note names a library function, it does so to show the hazard that a provision guards against. The note research/round-addenda/a2-language-facts.md (a2 below) confirms facts of these Notes from the documentation of Python, from PEP 751, and from the specification of the pylock.toml file, and the keys S1 to S10 that the Notes cite after a2 are entries of its table of sources.

Departures from the directions. The directions for style, docstrings, and layout are matters of form, so their provisions are defaults (GOV.19), whatever the verb of the direction. The direction "always" for types is met in two parts. Writing an annotation costs an agent only the form of the code it writes, not a tool or added work, so STND.PY.4 binds every agent at every class by its own force (GOV.48), and STND.INSTR.10 carries it into the agent instructions; that it raises no floor (GOV.11) is the custodian's ruling of 2026-10-23 (PRIN.10). Annotations that no checker reads are able to drift from the code (INTPR.3), and a type checker is a tool that the provisioned environment holds only under an authorization of the human owner (PRIME.7), which a standing authorization of STND.PROJ.3 gives (STND.DRAFT.42). A run of a tool is not bound at CSQ4 (GOV.11), so the checking and the remaining annotations are defaults from CSQ3.

Style. PEP 8 and PEP 257 are active, and PEP 8 leaves choices to a project, the length of a line among them, which the repository configuration settles (STND.PY.1). The idioms of this standard come from the Programming Recommendations of PEP 8, from PEP 257, from the typing PEPs through the typing specification, and, for scientific code, from SPEC 7 of the Scientific Python project and the logging guide of the Python documentation. The Zen of Python, PEP 20, informs review and decides nothing mechanically, so the standard does not cite it. STND.PY.2 asks the linter to check the agreement of documented parameters and return values with each function; agreement of the documented exceptions is left to review.

Names from notation. PEP 8 names constants and classes by case, and NUMER.4 asks for names that map to the notation of the equations, so a matrix "A" or an operator "K" keeps its case (STND.PY.1, STND.DOCS.12). A list of those names in the settings of the naming rules of the linter keeps each use free of a suppression comment, and a long line of displayed mathematics in a docstring takes a coded suppression (STND.PY.8).

Grouping. STND.CODE.13 groups the statements of each function body into blocks of one step each, and applies to Python as to every language. PEP 8 asks for blank lines in functions "sparingly, to indicate logical sections", which is the same rule. A formatter that keeps single blank lines inside a function keeps the grouping that the author makes; one that inserts a blank line before a nested definition inserts it under the exception of STND.CODE.13. A table of constants or a matrix kept in aligned columns is excluded from formatting at that statement only, by the suppression comment of the formatter.

Strict type checking. The term lists the findings by outcome, so that the project's choice of checker meets it by its settings. A dependency that carries no annotations makes the values it returns of the dynamic type, so the repository configuration gives the checker stubs, which are development tools in the dependency record (STND.DEPS.9), or a per-module override that relaxes that report for that dependency alone, with its reason (STND.PY.5). Existing source that does not pass is listed once by module in the repository configuration, and the list shrinks as changes touch the modules (STND.PY.6); the change that adopts strict checking writes the first list. Notebooks are outside the checking of STND.PY.5, because type checkers read them only through an added tool; this departure from "always" is the custodian's ruling of 2026-10-23, and a module that a notebook imports is library code and is checked. "Any" is the type that the checker does not check; STND.PY.8 asks for the reason at each use, and for "object" where every value is accepted, as the typing best practices advise. A suppression comment that names its rule code does not hide a finding that it was not written for. The py.typed marker of PEP 561 tells the checkers of dependents to read the annotations of a distributed package (STND.PY.7).

Arrays. An array library's type for inputs that a function converts often admits strings and carries no element type, as NumPy's ArrayLike does, which is why STND.PY.9 admits a narrower type, an array of a concrete scalar type, for a numeric input. A concrete scalar type also avoids a type argument that a generic scalar type would need under strict checking. Annotations of shape are checked at run time only where the project adds a run-time checker.

Docstrings. The numpydoc standard fixes the sections and their order, from the short summary to Examples (STND.PY.10), and its format guide says nothing of annotations. STND.PY.11 departs from the practice of major scientific libraries, which state each parameter's type in the docstring as well, by the custodian's ruling of 2026-10-23: a type restated in a Parameters entry is documentation that merely restates the code (INTPR.2) and drifts from it unchecked (INTPR.3), while the annotation is checked. The Returns and Yields sections keep a type, because the numpydoc standard requires one there and reads a one-line entry as a type; that type is written as the annotation writes it, and review compares the two. A docstring validator that reads parameter types from the docstring alone is set not to require them, and the documentation build takes the types from the annotations. The units, shape, and range of valid values of an item appear in its entry only where the item has them (STND.PY.10, STND.CODE.3, INTPR.4).

Doctests. STND.DOCS.13 compares the shown result of an example within a stated tolerance, and the doctest module of the standard library compares text exactly. A test runner that compares each floating-point number to the precision written in the expected output makes the written digits the tolerance; an example that needs another tolerance shows a value that it rounds itself, or the result of a comparison that states its tolerances (STND.PY.12). An example that shows an exception compares its type and not its message, which changes between Python releases. The test runner also collects the examples of documents outside docstrings.

Versions. The project chooses the releases of Python and of its dependencies that it declares, under STND.DEPS.3 and STND.DEPS.4, and the repository configuration records them (STND.PY.13). A distributed package declares the oldest releases it supports so that its dependents know what they are able to combine with it, and its checks run on the oldest declared combination and on the newest combination that its declared ranges admit (STND.PY.14). A new Python release is able to precede the releases of dependencies that support it, which is why the newest combination is limited to releases consistent with one another. An application or an archived study that no other work imports pins its interpreter and packages as dependencies, and a qualified revision stays fixed under STND.DEPS.3. A change of the Python release on which the work runs is a change of the runtime of each execution path under HW.7 and of a pinned revision under STND.DEPS.5, and each run records the exact Python and library revisions (STND.DEPS.8); the lock file of the package installer is the exact record of those revisions (STND.DEPS.10). STND.PY.33 keeps a lock file that the tools of the work write under version control wherever the work reports results, as STND.JL.4 does for a Julia manifest, so that the revisions of a run are those of its source; it asks for no lock file where the tools write none. STND.RUST.30 differs: it asks that each Rust lock file be under version control without the condition on reported results, and that builds use the revisions that it records and fail on a lock file that does not match the package metadata. The term Lock file has the wording of the term of STND.RUST, with an environment in place of a set of crates built together, because a Python installation resolves the packages of an environment. A distributed package whose own environment produces no reported result leaves its dependents to resolve their own environments, and its checks run on the combinations of STND.PY.14; that such a package commits no lock file is common practice (unverified). PEP 751, a standard of status Final, specifies a common format for lock files, named pylock.toml (a2, S9 and S10); which installers read or write it is unverified, and a format of a project tool's own is a lock file in the sense of the term where it records each exact revision, as a requirements file is that pins the exact revision of each package that the environment installs, its transitive dependencies included. STND.CODE.19 fixes, for high-assurance code, a release of Python that its high-assurance coding standard covers and for which each tool that runs that code holds the validation that the work requires; that release is a qualified revision, which STND.DEPS.3 leaves fixed, and STND.PY.14 yields to it by its own text. Running the checks of STND.PY.14 at release, and not at each change, is a deferral of verification under RSRC.12.

Randomness. STND.CODE.2 already asks that the source of randomness arrive through the interface; STND.PY.15 gives its Python form, a generator object passed through a parameter named rng as SPEC 7 names it, and keeps library code off the global random states of its libraries and of the random module, which are hidden global state (DSGN.14). SPEC 7 also lets the rng parameter accept a seed or None; this standard keeps that conversion at the entry point (STND.PY.16), because an integer passed to two functions gives them identical streams and None draws entropy that nobody records. Streams for parallel parts derive from the root seed and the part index through spawning, jump-ahead, or counter-based keys (STND.PY.17, STND.VVUQ.62); a stream chosen by worker or process identity, or copied into forked processes, differs between runs. STND.PY.17 states for the work in Python the rule of STND.CONC.23, which keys each stream of a computation divided among concurrent tasks to a part defined independently of the number of tasks and of the task that computes it. STND.PY.17 reaches further: it governs each division of work into parts, parts run as separate runs included, which STND.CONC.23 does not reach; both apply from CSQ3. NUMER.24 governs the evidence that the streams are independent.

Stable values. A generator library is able to keep the stream of a bit generator fixed for a seed while the sampling methods built on it change their output between releases, as the methods of NumPy's Generator have done. A test reference of exact drawn values therefore draws through a stable stream or holds stored data (STND.PY.18). A test whose verdict depends on a seeded stream states in advance how it is repeated after an upgrade of its generator library, because NUMER.26 forbids reseeding as the remedy for a failure without such a rule. The built-in hash of a str or bytes object varies between runs with the hash seed of the interpreter, and with it the iteration order of a set of strings (STND.PY.19).

Comparisons. STND.VVUQ.1 sets the tier of each comparison, STND.VVUQ.5 the relative and absolute parts of the rounding and numerical-error tiers, and STND.VVUQ.3 the agreement of NaNs; STND.PY.20 asks that the Python comparison state those parameters where the code makes it, through a library function or an expression. Defaults differ between comparison functions: math.isclose defaults to an absolute tolerance of zero, and NumPy's assert_allclose treats NaNs as equal while its isclose does not, so a comparison that relies on defaults decides for a reason the reader does not see. Each tolerance is a named constant with its basis beside it (STND.CODE.10, NUMER.11), so that a copied value without a basis stands out in review.

Reporting. Library code writes diagnostics through a module logger and leaves the handlers to the program that imports it (STND.PY.21). A null handler on a library logger also stops the last-resort output of Python, so a warning written only to that logger is silent when the program configures nothing. STND.PY.22 therefore gives the responses to a condition that PRIME.4 lists, of which a record from library code is no part; an entry point whose handler shows the record degrades visibly through it. A warning of a category that the default filters hide, DeprecationWarning outside the main module, PendingDeprecationWarning, ImportWarning, and ResourceWarning among them, is silent and does not count. An exception other than SystemExit that is raised and not caught reaches the hook that the sys module holds for it, just before the program exits, and one that the run method of a thread raises reaches the hook that the threading module holds; the default hooks print the traceback and the exception to the standard error stream (a2, S1 and S2). STND.PY.32 is the Python counterpart of the second sentence of STND.RUST.13: it asks a hook that the work installs in their place, to write the exception to a log or to a report among them, to deliver the diagnosis of each listed condition that reaches it, and work that keeps the default hooks meets it unchanged. The hook of the sys module that the interpreter calls when an exception has occurred and Python has no way to handle it is such a hook (a2, S1).

Idioms. Python evaluates a default value once, at definition, so a mutable default is state shared across calls (STND.PY.23); None is the usual default, with the object built in the body. The default text encoding of Python has depended on the platform, so a file opened without its encoding is able to read differently on different machines, and an error handler of "ignore" or "replace" substitutes characters silently (STND.PY.24). File system paths held as path objects of the pathlib module are clearer to read than strings joined by hand, and the linter's rules for them are a choice of configuration.

Assertions. STND.PY.22 is the Python form of STND.CODE.14, which admits the pass of a condition to the caller in its result, in an argument that the caller passes to receive it, or by a mechanism of the language, an exception among them, that propagates the condition to the caller; in Python a raised exception is that mechanism, and a returned result the first form. STND.PY.25, STND.PY.27, and STND.PY.30 are the Python forms of STND.CODE.6 and STND.CODE.7, each limited to the conditions that PRIME.4 lists. STND.CODE.15 asks nothing of Python until a form of declaration under which an ignored result is diagnosed is among the means of the work, and STND.CODE.7 still forbids discarding a listed failure. The interpreter removes assert statements under its optimizing mode, an execution setting, so an assertion that checks untrusted input lets invalid input through in that mode (STND.PY.25). An argument of the public interface is untrusted input unless the threat model of GUARD.16 records otherwise, so a shape check of an argument raises an exception in place of an assertion; that this reaches every function of the public interface at every class, as PRIME.4 does, is the custodian's ruling of 2026-10-23 (PRIN.10). STND.CODE defines the term once, and the term Public interface places the functions and methods of that interface in the public interface that the term takes in, so the reach of the ruling is kept; STND.CODE adds the functions that the documentation or the repository configuration names for use outside the work. The optimizing mode, set by an option of the command line or by an environment variable, removes assert statements and the code that depends on the value of __debug__ (a2, S3 and S5). A run-time check of an invariant or postcondition that the work relies on is written as a raise statement for the same reason (STND.PY.26), and STND.CODE.16 binds the same for each check that CPS.5 or CPS.9 requires where those apply. STND.JL.13 binds a check of each index that derives from untrusted input, because an annotation or an execution setting of Julia removes the bounds checks of its indexing. A built-in sequence raises IndexError for an index outside its range (a2, S6 and S7), a response that STND.PY.22 admits, and the optimizing mode leaves that check in place, since it removes only assert statements and code that depends on __debug__; whether each array library checks its indices in the same way is unverified. This standard therefore has no counterpart of that sentence. A negative index from minus the length to minus one selects from the end of a sequence and raises nothing, and a slice raises nothing whatever its bounds (a2, S6); where the contract of a function excludes it, only a check of the function under DSGN.2 rejects it. Code that a compiler translates from Python source is able to index without bounds checks, by default or by an option (unverified for each compiler); STND.PY.31 asks the reason for each such use, and STND.CODE.6 keeps an execution setting from removing a check of untrusted input there.

Handlers. MemoryError and RecursionError derive from Exception, so a handler of Exception, of BaseException, or of every exception catches the resource exhaustion that PRIME.4 lists, and a suppression context with those classes discards it with no handler at all (STND.PY.27). A handler meets STND.PY.27 by raising the same exception, by raising another one from it, by halting, or by a visible fallback, a computation in smaller pieces with a warning among them. KeyboardInterrupt and SystemExit are the operator's stop and the program's exit, which PRIME.4 does not list, so STND.PY.28 raises them again as a default; a handler that stores an exception to raise it in another thread raises it again there.

Error settings. A process-wide setting of the floating-point error handling of a numerical library, numpy.seterr among them, or of the warnings filters changes the behavior of every other component in the process, which is hidden shared state (STND.PY.29); an entry point is the place for such a setting, and the reason for each suppression is stated at its location (STND.CODE.12). Where the suppressed report signals a condition that PRIME.4 lists, a convergence warning among them, STND.CODE.7 still forbids discarding the condition, so the code detects it by another means, a convergence flag or a check of the result, and responds as STND.PY.22 gives (STND.PY.30); an entry point that ignores invalid-value reports for the whole process and checks each result for finite values meets it.

Relaxed checks. Functions that substitute values, numpy.nan_to_num and numpy.clip among them, are silent defaults under PRIME.4 where the value they replace is invalid input, and STND.CODE.7 governs them there. An argument that disables a finiteness check, check_finite=False of SciPy among them, a compiler option for fast floating-point arithmetic, and a disabled bounds check remove a check or relax the arithmetic, so each carries its reason (STND.PY.31). Where code compiled under such an option holds a check of a floating-point value that STND.CODE.6 governs, STND.CODE.21 recommends against an option that lets the compiler assume finite values, beside the reason that STND.PY.31 asks. On the path of a numerical result, a relaxation of floating-point semantics is a performance approximation, which NUMER.16 and NUMER.17 govern.

Foreign interfaces. STND.PY.34 to STND.PY.37 give the Python forms of what STND.CXX.20 and STND.CXX.22, STND.RUST.24 to STND.RUST.27, and STND.FTN.27 and STND.FTN.28 state for their languages: types and layouts that match the foreign declaration, exceptions kept from crossing into foreign code, and memory with one owner and a stated lifetime (DSGN.4, DSGN.5, DSGN.14). A compiled extension module is built against the declarations of the foreign code, so that its compiler checks the types of each call (unverified for each build tool). A library that loads a shared library while the program runs reads no header, and takes the types of each call from what the Python source declares to it, or from defaults where it is given none (unverified for each library). The ctypes module of the standard library is unable to determine the signature of a foreign function, checks no number of arguments where none are declared, and assumes that a function returns a C int unless its result type is declared; incorrect arguments are able to corrupt memory or crash the interpreter (a2, S8). These hazards are why STND.PY.34 asks for each type, and its two sentences are applied apart where the work declares no structure. A C declaration of a pointer to elements states no order of dimensions and no strides, so STND.PY.37 takes them from the documentation of the foreign function or from a test, as STND.FTN.28 tests a section with a stride other than one; a slice of an array is a view whose elements are not always adjacent in memory (unverified for each array library). What a foreign interface does with an exception that a Python callback raises is unverified for each interface, so STND.PY.35 asks for the catch unless the documentation of the interface states that the exception is passed on. Its three sentences are one remedy and are not applied apart: an exception caught and neither converted nor stored is discarded, which STND.CODE.7 forbids for a listed failure, and KeyboardInterrupt and SystemExit are raised again after the foreign call, as STND.PY.28 asks of a handler. The ctypes module keeps no reference to a callback object, which the garbage collector is then able to free while C code still holds it, crashing the program when the callback is made (a2, S8); whether a buffer passed to foreign code is kept alive is unverified for each interface. STND.PY.36 asks the work to keep the reference, and to give each resource that foreign code creates one owner, as STND.RUST.27 does. STND.CXX.22, STND.RUST.25, STND.PY.35, and STND.JL.39 take the same steps for an exception or a panic in a callback: catch it there, then convert it to the error of the interface or answer it after the foreign call returns.

Floor. STND.PY.22 asks for the responses that PRIME.4 already requires, and STND.PY.25, STND.PY.27, and STND.PY.30 ask only for a response that STND.PY.22 gives, or forbid a construct that leaves a listed condition without one, so none of them asks for work that PRIME.4 does not; that these raise no floor is the custodian's ruling of 2026-10-23 (PRIN.10). They bind at every class, CSQ4 included, as PRIME.4 does. STND.PY.32 reaches only a listed condition whose exception no handler caught, which ends a thread or the program or is dropped, and asks only for the actionable diagnosis that PRIME.4 names, at the cost of the wording of a hook that the work installs. A replaced hook that drops a listed condition without a diagnosis lets the program end or continue past the error in silence, which the last sentence of PRIME.4 forbids; the default hooks print the exception, so the provision binds only where the work replaces one. It asks for no work that PRIME.4 does not, so it raises no floor (GOV.11); no ruling of the custodian covers it, and the argument is the one that the ratification of 2026-10-24 accepted for the second sentence of STND.RUST.13. It binds at every class, CSQ4 included.

Class onset. Under STND.CLASS.10, each default provision instantiates only DSGN, SIMPL, INTPR, REPRO, VV, RSRC, or a provision of NUMER, and applies from CSQ3; work of CSQ4 may omit it. STND.PY.26 instantiates the run-time checking of VV.10 and DSGN.2, which STND.CLASS.10 applies from CSQ1, and applies from CSQ1. STND.PY.34, STND.PY.35, and STND.PY.37 instantiate the schemas of DSGN.4 and the external contracts of DSGN.5, which STND.CLASS.10 applies from CSQ2, and apply from CSQ2; STND.PY.33 and STND.PY.36 rest on no row and apply from CSQ3. STND.PY.5 asks for type checking of all code from CSQ3, and the mechanical checking of each contract of a safety-related component, which STND.CLASS.10 applies from CSQ0 under DSGN.3, stays with that row. No default instantiates a prime directive, GUARD, GOV, or a floor obligation, and no provision raises the floor (GOV.11).

Existing source conforms when a change next touches it, other than the strict checking of STND.PY.5, which existing modules reach through the list of STND.PY.6.
