## Purpose and scope

This standard holds the practice of concurrent execution that is the same in every language and every parallel programming model: threads, tasks, coroutines, asynchronous operations, event loops, pools of workers, and the processes of one run. It adds to DSGN, VV, REPRO, INTPR, RSRC, PRIME.4, HW, and NUMER only what concurrency makes necessary. It covers the failures of concurrent tasks (STND.CONC.1 and STND.CONC.2); shared state (STND.CONC.3, STND.CONC.4, STND.CONC.5, and STND.CONC.6); locks and waits (STND.CONC.7, STND.CONC.8, STND.CONC.9, STND.CONC.10, and STND.CONC.11); the lifecycle of tasks, cancellation, queues, pools, and event loops (STND.CONC.12, STND.CONC.13, STND.CONC.14, STND.CONC.15, and STND.CONC.16); state that applies to a whole process or node (STND.CONC.17, STND.CONC.18, and STND.CONC.19); blocking in constrained targets (STND.CONC.20); results that depend on the number of tasks (STND.CONC.21, STND.CONC.22, and STND.CONC.23); verification (STND.CONC.24, STND.CONC.25, STND.CONC.26, STND.CONC.27, and STND.CONC.28); the record of operations left pending at the end of a run (STND.CONC.29); and the order of the writes of concurrent tasks to one output or one record (STND.CONC.30).

STND.CONC.1 and STND.CONC.2 instantiate PRIME.4, so they are binding and apply at every class. Every other provision is a default (GOV.19), which a project replaces by a recorded decision with an alternative that meets the same higher-level outcome (REPRO.7). The standard is language, platform, implementation, and tool agnostic: it names no language, library, runtime, checker, or platform (GOV.18). The standards for one parallel programming model or one language add the forms that their facilities need: STND.MPI holds the forms for message passing, STND.OMP holds those for directive-based threading, and STND.OFFLD those for accelerator offload. Workflows of many runs, retried tasks, restart state, and access to shared files and storage belong to STND.WFLOW, whose STND.WFLOW.32 holds the guarantees of shared file systems on which work relies; the memory of accelerators belongs to HW.GPU and to STND.OFFLD, whose STND.OFFLD.9 to STND.OFFLD.12 and STND.OFFLD.21 to STND.OFFLD.23 govern it.

## Normative and informative parts

The body of a numbered provision, including a table it contains, is normative. Everything else is informative.

## Terms

This section fixes meaning and imposes no obligation, as the Lexicon does. Execution path and Constrained target have the meanings that HW gives them; Hardware thread has the meaning that HW.CPU gives it; Safety-related component has the meaning that STND.CLASS gives it.

| Term | Definition |
| --- | --- |
| Concurrent task | A thread, task, coroutine, process, signal or interrupt handler, or other sequence of execution of the work that runs, or is able to run, while another of the same run has not completed. |
| Parent | Of a concurrent task: the concurrent task, or the scope of code, that starts it, or to which the handle by which its end is awaited passes. |
| Asynchronous operation | An operation whose start returns to the code that started it before the operation completes, and whose completion and failure that code observes later through a handle, a future, a request, an event, or a callback. Each concurrent task that the work starts is one. |
| Shared mutable object | An object that more than one concurrent task accesses, at least one of them by a write. |
| Protection | The means by which a protocol orders the conflicting accesses to a shared mutable object: a lock, atomic operations, the transfer of the object from one concurrent task to another by a message, confinement to one concurrent task, or immutability after publication. |
| Data race | Two accesses to one memory location by different concurrent tasks, at least one of them a write, that no protection orders and that are not both atomic operations. |
| Lock | A synchronization object that one concurrent task acquires and releases to exclude other concurrent tasks from a region of code or from an object; a mutual-exclusion object, a read-write lock, and a semaphore used for exclusion are locks. |
| Suspension point | A point at which a coroutine or an asynchronous function yields control to the event loop or scheduler that runs it. |
| Event loop | A concurrent task that runs, one at a time, the callbacks and coroutines that are ready, and waits for events between them. |
| Pool | A set of concurrent tasks that runs work submitted to it. |

## Notes

The custodian's direction of 2026-10-24 sets the scope: one model-neutral home for the rules of concurrent execution, so that STND.MPI, the language standards, and the standards of other parallel programming models hold only the forms that their own facilities need. It keeps the standard agnostic of language, platform, implementation, and tool, and keeps the custodian's directions on determinism (STND.VVUQ.82 and STND.VVUQ.83): strict determinism is an option where it is feasible, not a requirement unless the acceptance criterion of the work or its consequence class demands it, and a declared variation within the agreement that the acceptance criterion fixed is no defect. A true race is a correctness defect. The sources are the project's research notes research/concurrency-notes/c1-corpus-gaps.md (the coverage of the corpus and its gaps), c2-model-neutral-practice.md (the published coding standards, memory models, and verification literature), c3-distributed-resilience.md (the composition of runtimes on one node), and c4-model-landscape.md (the hazards that recur across models), with research/parallel-models.md for the gaps G1 to G4; a fact that those notes do not support is marked unverified.

The standard adds the content of concurrency to provisions that already hold the outcome, and does not restate them (GOV.31). DSGN.15 asks that concurrent access to shared state follow a stated protocol whose invariants are verified, and HW.11 asks that the protocol be verified under the memory model of the hardware contract or of the language or library; STND.CONC.3 to STND.CONC.9 say what such a protocol states and what its code does. DSGN.14 gives each piece of mutable state one owner and a stated lifetime, which STND.CONC.5, STND.CONC.12, and STND.CONC.17 apply to tasks, objects reached by reference, and the state of runtimes. HW.12 has each execution path declare whether the scheduling of its concurrent work varies between runs on identical inputs; STND.CONC.21 adds the dependence on the number of tasks, which the Notes of STND.MPI observe that HW.12 and REPRO.3, written for identical recorded inputs, do not reach. HW.CPU.4 records the threads that a run uses and HW.CPU.5 reports oversubscription; STND.CONC.18 has the program set the sizes of its pools so that the excess does not arise. STND.VVUQ.2 gives the rule for reductions under bitwise identity and STND.VVUQ.62 the construction of random streams, which STND.CONC.22 and STND.CONC.23 apply across numbers of tasks. INTPR.7 detects stalled progress, which a bounded wait reports (STND.CONC.10).

STND.CONC.1 and STND.CONC.2 close the gaps G1 and G2 of research/parallel-models.md outside MPI and accelerators. An asynchronous operation reports its failure only when its completion is observed, so an operation whose completion is never observed loses its failure, which is the silent continuation past an error that PRIME.4 forbids. Python's documentation states that the exception of a task that is never awaited surfaces only as a log line when the task is reclaimed (c2, section 5); the same holds of a detached thread whose failure ends only that thread (unverified). HW.GPU.3 holds this outcome for offloaded work, and the second sentence of STND.MPI.5 for nonblocking operations of MPI; STND.CONC.1 states it once for every asynchronous operation, each concurrent task included, and those two provisions remain its forms for their models. STND.OFFLD takes each submission of offloaded work, and STND.WFLOW each job that a workflow submits to a scheduler, as an asynchronous operation under it; the Notes of STND.RUST apply STND.CONC.1 and STND.CONC.2 to a spawned thread that panics or whose join handle is dropped, and those of STND.SV to each concurrent task of a testbench. A run that ends with an operation still pending states it in its record under STND.CONC.29, a default, so that a lost failure is at least visible; PRIME.4 itself still governs an unobserved operation whose result nothing relies on, which STND.CONC.1 does not reach. A concurrent task that halts alone leaves the tasks that wait on it blocked, which is a silent hang: STND.CONC.2 has the failure reach the parent where the parent relies on the task's result, and the other tasks of the same result halt, or learn of the halt and respond as PRIME.4 requires, which is the reading of HW.8 that the Notes of HW give for a run of several processes and that STND.MPI.6 states for MPI. STND.OFFLD.8 is the way by which STND.CONC.2 reaches device code, whose threads have the submitting host code as their parent, and the Notes of STND.FTN read ERROR STOP, which ends every image, as the halt that it asks.

STND.CONC.1 and STND.CONC.2 instantiate PRIME.4 and bind at every class, CSQ4 included. Neither raises the floor (GOV.11), for these reasons. STND.CONC.1 asks that the failure of an asynchronous operation be observed before a result relies on the operation, which PRIME.4 already requires; it asks no run to wait for an operation whose result nothing relies on. STND.CONC.2 asks that a failure that PRIME.4 lists not end silently inside a task on whose result its parent relies, and that the tasks that depend on a halted task not wait on it forever, and leaves the failing task and each dependent task every response that PRIME.4 admits. PRIME.4 does not name a parent; the first sentence stays within it because a parent that relies on the result of a task that failed, without learning of the failure, continues silently past an error, which PRIME.4 forbids. A signal or interrupt handler whose result no parent relies on is outside that sentence. Its cost is one handle by which the parent learns of the failure, and one notice or one call that ends the dependent tasks.

Shared state follows the published coding standards and the memory models of the mainstream languages (c2, sections 1 and 2). A data race has an undefined outcome in some languages and an outcome that is weakly bounded in others; a program free of races behaves as if its tasks ran in an interleaving of their steps, so a protocol that is free of races is reasoned about by interleavings alone. One stated protection for each shared mutable object, beside the object, is the rule of the C, C++, and Java coding standards and of the C++ Core Guidelines (STND.CONC.3). The sequentially consistent ordering of atomic operations is the default of the languages that offer weaker orderings; one safety coding standard for C requires it for every synchronization, and a weaker ordering is the source of defects that tests rarely reveal, so it carries its reason (STND.CONC.4). A qualifier that marks an object as changed outside the program does not order accesses between tasks in the languages that define a memory model (unverified beyond the coding standards in c2, which forbid its use for synchronization), so STND.CONC.3 asks that a protection by synchronization use a facility that the memory model of the language or library, or the ordering model of the hardware contract that HW.11 admits, defines as ordering them; confinement and immutability need none. STND.CXX.23 is its form for objects that C++ code shares with signal and interrupt handlers. STND.STDC.35 is its form for adjacent bit-fields in C, STND.FTN.11 for the variables that Fortran shares without a declaration that shows it, STND.RUST.21 for an unsafe implementation of `Send` or `Sync`, which names the protection, and STND.OFFLD.5 for host storage that an asynchronous transfer reads. The Notes of STND.SV read STND.SV.5 to STND.SV.8 as the protection by scheduling for the processes of a simulation, which STND.SV reads as concurrent tasks, and STND.SV.5 and STND.SV.7 cite STND.CONC.3. An object made reachable before its construction ends is seen in part by another task, and an object that a task uses by reference after its owner has released it is a use after its lifetime, the hazard of the lifetime of captured data that c4 finds across models (STND.CONC.5). STND.OMP.8 is the form of STND.CONC.5 and STND.CONC.12 for the local variables that a routine shares with explicit tasks of OpenMP. Whether concurrent calls to an interface are safe is part of its contract (STND.CONC.6), and in C++ that contract is the declaration comment of STND.CXX.15.

The rules on locks and waits are those that every coding standard in the research note shares (c2, section 3). A deadlock among locks needs a cycle in the order in which tasks hold them; one stated order without a cycle, or a facility that acquires several locks together, removes it (STND.CONC.7). In one study of deadlocks, 22 percent came from a task acquiring a lock that it already held. Code under a lock that calls code whose locking it does not know, waits for another event, or suspends, holds the lock across steps that it does not control, and a callback is such code (STND.CONC.8). STND.RUST.23 makes STND.CONC.8 mechanical for asynchronous Rust, where a static check reports each guard of a lock held across a suspension point. A wait for a condition is able to return when the condition does not hold, so it tests the condition again (STND.CONC.9). A wait on another task without a bound turns a lost notification into a hang, and the bound or the cancellation of STND.CONC.10 turns it into a report; a blocking read of a file or a device is outside it. A construct whose tasks the runtime is free to run one after another, a parallel loop among them, deadlocks when one of its tasks waits for another that has not started, so the second sentence of STND.CONC.11 keeps such waits out (c4, hazard 6). STND.OFFLD.18 is its form for the groups of one submission to an accelerator, and the Notes of STND.FTN apply it to the iterations of a DO CONCURRENT construct. STND.CONC.11 closes the gap G3 beyond MPI: DSGN.15 asks for invariants, which are properties of safety, and a protocol in which tasks wait on one another also needs completion, which STND.MPI.12 asks only of message protocols. Where the statement of a protocol carries no argument of completion, the detection of deadlock of STND.CONC.25 is the evidence that remains. Message passing does not give freedom from deadlock by construction; in one study of 171 defects of a language built around channels, message passing caused more blocking defects than shared memory did (c2, section 3).

The lifecycle rules follow the practice that the research note calls structured concurrency: a task does not outlive the scope that starts it, so its failure has somewhere to go and its resources have an end (STND.CONC.12; c2, section 4). The languages that provide scoped tasks, task groups, or threads that join when their handle ends make this the default; detached work is the exception. Cancellation that does not reach the tasks a task started leaves them running after their result is no longer wanted, and code that swallows a cancellation keeps its caller from ending (STND.CONC.13). STND.RUST.22 adds what the cancellation of a future by its drop makes necessary in Rust, the statement of whether the future is cancellation safe among it. A queue without a bound lets work accumulate without limit behind a slow consumer, which the literature on backpressure warns against (c2, section 4), and tasks that wait on one another inside one bounded pool deadlock when each worker holds a task that waits for a task still queued (STND.CONC.14). Code that blocks an event loop, or computes on it without returning control, delays every task on it, and the objects of most event loops are not safe to call from other threads (STND.CONC.15). A runtime that moves a task between threads at a suspension or scheduling point changes the thread on which the task resumes, so state that the task keeps in storage local to its thread, or selects by the identity of its thread, is lost or shared (STND.CONC.16); STND.JL.27 states the same of Julia, and STND.OMP.7 is its form for the tasks of OpenMP. The Notes of STND.RUST apply STND.CONC.15, STND.CONC.16, and STND.CONC.17 to blocking on an executor, to state local to a thread, and to executors as pools.

The rules on state that applies to a whole process or node close the gap G4 beyond MPI (c1, item 8; c3, section 6). A library that creates its own pool of threads, or resizes a pool of the process, multiplies the threads of a program that already runs its own, and a library that changes the handling of signals or another setting of a runtime that applies to the whole process changes the behavior of its caller (STND.CONC.17). STND.OMP.19 is its form for the internal control variables of OpenMP, and the Notes of STND.FTN apply it to a library that sets the floating-point modes of its caller. Two components that each size their pool to the whole node run twice as many threads as the node holds, which HW.CPU.5 reports and STND.CONC.18 prevents by having one place, the program, set the sizes. A process that creates a child by copying itself while other threads run gives the child a copy of locks that those threads held and that nothing in the child releases; POSIX restricts the child of a process with several threads to calls that are safe in a signal handler until it starts a new program (unverified; the research notes did not retrieve the POSIX text), so a child is started by a facility that starts a new program in it, or by one that the documentation of each runtime in the process states as safe (STND.CONC.19).

STND.CONC.20 states, for a constrained target with tasks that share a processor or a lock, what the bound of HW.20 counts: the time that a task waits for tasks of lower priority and for the locks that they hold. Without that time, a bound on execution time alone misses the inversion of priorities by which a task of lower priority holding a lock delays one of higher priority; the resets of the Mars Pathfinder lander in 1997 came from such an inversion (c2, section 3, from a search extract). A protocol that bounds blocking, the inheritance or the ceiling of priorities among them, is one means of meeting it, and a project chooses its own (GOV.18).

STND.CONC.21 has each result that depends on the number of tasks, on the division of the computation among them, or on the order in which they combine values declared with the size of its dependence, as STND.MPI.18 does for processes; a dependence so declared that stays within the agreement that the acceptance criterion fixed is no defect (STND.VVUQ.82). STND.CONC.22 applies STND.VVUQ.2 across numbers of tasks, as STND.MPI.19 does across numbers of processes: partial results of parts of the computation that do not depend on the number of tasks, combined in a fixed order, or an order-independent combination, give the same bits at every number of tasks. STND.CONC.23 keys each random stream to a part of the computation, not to the task that computes it, so that the streams do not change with the number of tasks; STND.PY.17 and STND.JL.24 state the same for their languages, STND.SV.23 is the form of STND.CONC.23 and STND.VVUQ.62 for the random stimulus of a testbench, and STND.VVUQ.62 gives the construction of the streams. Records that concurrent tasks write to one file or one log appear in the order in which the tasks reach their writes, which the schedule sets unless a protocol of the tasks fixes it; a declared variation of that order is no defect under REPRO.3, and a result that relies on an order that nothing fixes rests on undeclared variation (STND.CONC.30). REPRO.3 already asks that variation be declared, and HW.12 has each execution path declare whether the scheduling of its concurrent work varies; STND.CONC.30 adds the scope, the writes of concurrent tasks to one output, and the alternative of an order that a protocol of those tasks fixes. STND.FTN.26 is the Fortran form of STND.CONC.30, and the stricter one: it asks that code not rely on the order of the records that the iterations of a DO CONCURRENT construct or the images of a Fortran program write to one file, with no exception for an order that a synchronization of the images fixes.

The verification rules combine methods because each has a blind spot (c2, section 6). Tests at three or more numbers of tasks, among them the smallest that a component admits, find the defects that appear only in serial or only in parallel, and a number that divides the work unevenly exercises the handling of remainders (STND.CONC.24, as STND.MPI.24 does for processes). A dynamic detector of data races based on the order of events reports only the races of the executions it observes, and is nearly free of false reports; its cost in one documented detector is five to fifteen times in time (STND.CONC.25). In one study of concurrency defects, nearly all appeared under some order between two tasks, and 92 percent of the 105 defects studied under an order among at most four accesses, so varied schedules, by perturbed timing or by systematic or randomized exploration, find what a fixed schedule hides (STND.CONC.26). The record of a verification states what its method does not cover (STND.CONC.27), and a protocol of a safety-related component is proved or checked on a model of its design by exhaustive exploration, as the verification of such a component under the CSQ0 row of STND.CLASS.10 asks (STND.CONC.28), with the model ordering accesses as the memory or ordering model that HW.11 names, since a model that assumes a stronger ordering than the hardware gives proves nothing about it; one published account of model checking in industry found a defect whose shortest trace had 35 steps, after design reviews, code reviews, and tests had passed it (c2, section 6). STND.CXX.26 and STND.MPI.25 are the forms of STND.CONC.25 for C++ and for MPI; it applies to C and to Fortran by its own scope, as the Notes of STND.STDC and STND.FTN say. STND.OMP.32 runs the tests of target regions under a check of mapping errors, which escape detectors of data races, and STND.OFFLD.30 runs the tests of device code under the checks of device code that the means of the work include. STND.RUST.33 states the limits of a check of unsafe code as STND.CONC.27 does, one record meets STND.STDC.38 and STND.CONC.27 for data races in C, and the second sentence of STND.BUILD.13 makes STND.CONC.27 specific for the parts of the work linked without a check. STND.LEAN.19, with the row Code that runs of STND.LEAN.4, is the statement of correspondence that STND.CONC.28 asks of a Lean model.

High-assurance practice adds restrictions that this standard leaves to the project as choices, because they constrain designs rather than state outcomes: a set of tasks fixed at the start of a run, communication only through protected objects, and a locking protocol with bounded blocking, as the restricted tasking profile of one language defines (c2, section 8). Such a profile is one means of meeting STND.CONC.7, STND.CONC.20, and STND.CONC.28.

Under STND.CLASS.10, each default instantiates only DSGN, VV, REPRO, INTPR, RSRC, or a provision of HW or NUMER, and applies from CSQ3; work of CSQ4 may omit it. The part of a default that rests on a row of the table of STND.CLASS.10 applies from the class of that row: STND.CONC.19, which instantiates only DSGN.5, from CSQ2; the run-time checks of STND.CONC.25 and the varied schedules of STND.CONC.26, which verify the invariants of a protocol (DSGN.15), and the stated limits of STND.CONC.27 (INTPR.10), from CSQ2; the report of a reached bound in the second sentence of STND.CONC.10 (INTPR.7) and the record of operations left pending of STND.CONC.29 (INTPR.8), from CSQ1; and the proof or exhaustive check of STND.CONC.28 (VV.1), from CSQ0, where it applies only to safety-related components. STND.CONC.11, whose argument concerns completion rather than the invariants of DSGN.15, the protections, orderings, and lock rules of STND.CONC.3 to STND.CONC.9, among them the third sentence of STND.CONC.3, which states what a protection uses rather than how its invariants are verified, and the lifecycle rules of STND.CONC.12 to STND.CONC.17 apply from CSQ3, as do STND.CONC.18, STND.CONC.20, and STND.CONC.21, whose onset follows DSGN.14, RSRC.1, and REPRO.3, on which they and the provisions of HW that they instantiate rest. STND.CONC.30 states the order that a protocol fixes, or the variation that a record declares, and not how the invariants of that protocol are verified, so it applies from CSQ3, as STND.CONC.3 does. The sentences of each provision with three modals share one onset, so that the provision applies as one bundle. No default raises the floor (GOV.11).
