## Purpose and scope

This standard holds the coding practice that applies to source in every language, hardware descriptions included, as outcomes that a tool or a reviewer decides from the source, its repository configuration, and its record of checks. It adds to DSGN, SIMPL, INTPR, REPRO, VV, QA, NUMER.11, PRIME.2, and PRIME.4 only what makes their outcomes checkable at each change. The language standards of LVL2 add the conventions of each language, and the form that its constructs give an outcome of this standard. Beside structure, checking, tests, and source, it states the responses to a failure that PRIME.4 lists, the declarations that keep a returned failure from being ignored, the checks that no setting or definition removes, and the settings that let a compiler assume finite values in code that holds such a check (STND.CODE.14, STND.CODE.15, STND.CODE.16, and STND.CODE.21), recommends against the annotations that do the same (STND.CODE.27), and has a hook or a handler that the work installs deliver the diagnosis of a listed condition that reaches it (STND.CODE.33). It states once for every language a convention of names (STND.CODE.28), seeded generators of random numbers and the values that change between runs (STND.CODE.29 and STND.CODE.30), the tolerances of comparisons (STND.CODE.31), the static checks of the provisions of the language standards (STND.CODE.32), claims that code is free of undefined behavior (STND.CODE.34), and the calls of functions of dependencies that report a listed failure in their results (STND.CODE.35). It states what code keeps true at a foreign interface: the types, the layouts, and the arrays that cross it, the failures that it keeps from crossing, one owner for each owned resource that crosses it, and the lifetime of each object that foreign code keeps (STND.CODE.22 to STND.CODE.26). For the code that a release of work of CSQ1 or CSQ0 delivers or runs to produce a reported result, it asks for conformance to the high-assurance coding standard that the work adopts, claims of that conformance limited to what was checked, an edition that the standard covers and the toolchain is validated for, and recorded deviations (STND.CODE.17, STND.CODE.18, STND.CODE.19, and STND.CODE.20). STND.CODE.6, STND.CODE.7, STND.CODE.14, STND.CODE.15, STND.CODE.16, STND.CODE.21, and STND.CODE.33 instantiate PRIME.4, and STND.CODE.18 instantiates PRIME.2, so these eight are binding and apply at every class; every other provision is a default (GOV.19) and a recommendation, which a project replaces by a recorded decision with an alternative that meets the same LVL0 outcome (REPRO.7, PRIN.10). No provision names a language, tool, or method (GOV.18).

## Normative and informative parts

The body of a numbered provision, including a table it contains, is normative. Everything else is informative.

## Terms

This section fixes meaning and imposes no obligation, as the Lexicon does. Safety-related component has the meaning that STND.CLASS gives it.

| Term | Definition |
| --- | --- |
| Repository configuration | The versioned files of the work that set how its tools build, check, format, and test it, apart from its governance. |
| Static check | A check of source or of a build that the means of the work make without running the work. |
| Execution setting | An option, flag, or variable of a compiler, interpreter, build, or run that changes which code executes. |
| Foreign interface | An interface through which code of the work in one language calls, or is called by, code in the same process that does not follow the rules of that language for ownership, lifetime, and the propagation of failures, code written in another language among it. A function that the work declares for such code or loads from it, a function of the work that such code invokes, and a thread that a runtime of such code starts in code of the work are foreign interfaces. The contract of a foreign interface includes the declaration of each of its functions in its own language and the documentation of the interface. For STND.CODE.24 alone, a structured block of a compiler directive for parallel execution is also a foreign interface, which carries no error and whose invocation returns at the end of the block. |
| Owned resource | Memory, a file, a lock, a handle that a foreign interface issues, or another facility that code acquires and has to release. |
| Library code | Code of the work that other code calls through its interface, other than tests and the code that holds the entry point of a program; in a language whose standard defines the term, the code that its definition gives. |
| Untrusted input | Data that reaches the work from outside its own code, the arguments of each function of its interface for outside use included, other than data from a source that the threat model of the project records as trusted. The interface for outside use of the work is each function that its documentation or its repository configuration names for use by code outside the work, together with each function that the standard of the language of that function places in its public interface. A function, in this term, is a function, procedure, subroutine, method, or other unit of code that a call enters. |
| High-assurance code | The code of the work that a release of work of CSQ1 or CSQ0 delivers, or runs to produce a reported result, each file that such code includes or imports included. Tests, development tools, and external code that the work incorporates are not high-assurance code. |
| High-assurance coding standard | A coding standard for a language of the work written for safety-related or mission-critical software, published or of the work's own making, with a procedure for recording deviations from its rules, its own or one that the decision record adopting it sets. |

## Notes

Each default provision asks for the cheapest evidence that keeps an outcome of LVL0 from failing silently. A tool that looks for cycles at each change keeps DSGN.7 true as the code grows (STND.CODE.1). Inputs that change between runs, the source of randomness and the run settings included, arrive through the interface, so that DSGN.14, DSGN.16, and DSGN.17 are visible at the call; a named constant, a hardware parameter fixed at synthesis, and a fixed configuration of a constrained target are not such inputs (STND.CODE.2). A contract stated at the declaration, or a citation of the one place that declares its units and conventions, puts DSGN.1 and INTPR.4 where every reader of the interface passes (STND.CODE.3).

The repository configuration names the static checks that the languages of the work offer, and each change passes them; a finding left in place is suppressed where it occurs, with its reason, so that the reason is the decision record of REPRO.7 (STND.CODE.4). A suppression records an accepted finding; it is not a way to pass a check (PRIME.2, AGENT.47). An agent that weakens a check or a setting in the change that the check judges records the two apart (AGENT.5) and states the weakening in its work report (AGENT.47). A layout that a named tool produces and confirms costs the reviewer nothing (STND.CODE.5); for a language whose tools offer no such layout, STND.CODE.5 asks nothing.

STND.CODE.6 and STND.CODE.7 rest on PRIME.4 and bind at every class, CSQ4 included, a tightening of PRIME.4 at the cost of one look at one location (PRIME.15). A check of untrusted input that an execution setting removes, as an assertion compiled out of an optimized build is, lets invalid input pass silently in the builds that run in production. A failure of a kind that PRIME.4 lists is never discarded (STND.CODE.7). Another failure that code discards carries, at that location, the reason the results stay correct, which a reviewer checks (STND.CODE.12, a default). HW.8 and HDES.14 add the responses that hardware asks for.

Untrusted input. The term is defined here once, and the language standards import it (GOV.31). The arguments of a function of the interface for outside use come from code that the work does not see, so they are untrusted unless the threat model of GUARD.16 records their source as trusted, and the check that STND.CODE.6 governs is at the entry of that function. The clause on the standard of the language keeps the public interfaces that STND.PY, STND.JL, STND.RUST, and STND.FTN define by the constructs of their languages. The clause on the documentation and the repository configuration widens each of them by the functions that those name and the language standard does not place: in Python, a documented function outside library code or with a leading underscore; in Julia, a documented function that the package does not declare public; in Rust, a documented function of a crate that is not a library; in Fortran, a documented external procedure. Through STND.CODE.6, the term also reaches the documented functions of C, C++, Lean, and hardware descriptions. In C and C++, an assertion on an argument of such a function is a check that a setting removes, and so a form that STND.CODE.6 excludes. A Lean function whose precondition a proof establishes carries no run-time check, and STND.CODE.6 constrains only the checks that code makes, so the reach adds nothing there. In a hardware description, the ports of the top-level design carry data from outside the work's own code under the first clause, and a function or task of the description is reached only where the documentation names it for outside use. The reach constrains only the form of a check that the code makes and adds no check: PRIME.4 already excludes the silent continuation of invalid input, and DSGN.2 already asks for its check where it enters, so the cost is the wording of an existing check as a test with its response (GOV.11). The custodian's ruling of 2026-10-23 on the reach was made for STND.PY and STND.JL, and the ratification of 2026-10-24 extended it to STND.RUST and STND.FTN; no ruling yet covers the widening by documentation, or the reach in C, C++, Lean, and hardware descriptions.

Responses. STND.CODE.14 lists the responses that PRIME.4 admits, together with the pass of the condition to a caller, in its result, in an argument that the caller passes to receive it, or by a mechanism of its language that propagates it, which STND.CODE.7 keeps from discarding it and which STND.CODE.14 binds in turn. Its forms in each language are these: in Python and in Julia, a raised or thrown exception, or a returned result; in Rust, a returned result or a panic, which propagates the condition under the unwinding strategy and halts under the aborting one, and so is a response under either; in C++, a thrown exception, a returned value, or an argument that the caller passes; in C, a returned value or an argument that the caller passes, other than a report through errno alone (STND.STDC.2); in Fortran, which has no exceptions, the result of a function or a status argument, which is an argument that the caller passes to receive the condition; in Lean, a result of a type that carries the condition, or an error raised in a monad whose caller receives that error; and in a hardware description, a status at the interface, the form that HDES.14 asks for saturation and overflow. A language standard adds to them only where its language sets a trap: the warning categories that the default filters of Python show (STND.PY.22), the levels at which the default logger of Julia shows a record (STND.JL.15), and the report through errno that STND.STDC.2 excludes. A record that library code writes to a log reaches no person unless the program that uses the library installs a handler or a logger that shows it, so the second sentence of STND.CODE.14 keeps such a record from being the only visible degradation in every language; an entry point whose handler shows the record degrades visibly through it, and in Julia a record that other code writes counts at the levels of STND.JL.15. A condition that a mechanism of the language carries past every caller ends a thread or the program, and PRIME.4 asks that end to carry a diagnosis. The default exception hooks of Python and panic hook of Rust print the condition (the Notes of STND.PY and STND.RUST), and STND.CXX.33 recommends a terminate handler where the one that the C++ implementation provides writes none; STND.CODE.33 has a hook or a handler that the work installs in place of a default deliver the diagnosis of each listed condition that reaches it and that no other response answers, so work that keeps the defaults meets it unchanged. A Rust panic that is caught and answered by a returned error or a visible degradation carries its diagnosis through that response, and a Rust build without the standard library defines the handler of a panic, which STND.CODE.33 reaches. A language in which the work installs no replaceable hook or handler for that end gives STND.CODE.33 no subject: Julia, for which the research notes of the corpus hold no source on such a hook (unverified), and Fortran, Lean, and SystemVerilog; in C, a handler that the work installs for the signal that abort raises is reached where that signal carries a listed condition. STND.CODE.14 asks only the responses that PRIME.4 already requires, in the forms that each language gives, and its second sentence only keeps out a form that leaves the condition unseen, so it raises no floor in any language (GOV.11); the custodian's rulings of 2026-10-23 that the same list raises no floor were made for C++, Python, and Julia, the ratification of 2026-10-24 accepted the second sentence for Rust, and the custodian ruled on 2026-10-28 that a record that library code writes to a log is never the only visible sign of a degraded result, in any language. STND.CODE.33 reaches only a hook or a handler that the work installs and a listed condition that already ends a thread or the program there, or that the runtime drops, and asks only for the actionable diagnosis that PRIME.4 names, at the cost of the wording of that hook or handler; a replaced hook that drops a listed condition without a diagnosis lets the program end or continue past the error in silence, which the last sentence of PRIME.4 forbids. It asks for no work that PRIME.4 does not, so it raises no floor (GOV.11), the argument that the ratification of 2026-10-24 accepted for the panic hook of Rust, and that holds for a hook or a handler of any language, since it concerns what the handler that the work writes delivers and not a construct of the language.

Ignored results. STND.CODE.15 asks one declaration for each function that returns a listed failure, in a language or toolchain that provides a form of declaration for one function, or for the type of its result, under which a call that ignores the result is diagnosed. A rule of a static check that reports every ignored result, whatever the declaration, is not such a form, because it is not a declaration of the function; this reading lowers, for C, the reach that the C reading of STND.STDC 1.0 gave the outcome, which accepted any compiler or static check that diagnoses an ignored value; a language standard that states a wider form for its language keeps it, and in Rust the must_use attribute is the form of the declaration. The nodiscard attribute of C and C++, the equivalent attribute of a compiler, and the must_use attribute of Rust are such forms; on the type of the result, the attribute also covers indirect calls (unverified for each compiler). The corpus records no such form for Python, Julia, Fortran, Lean, or SystemVerilog (unverified for each toolchain), where the provision asks nothing until the means of the work include one, and STND.CODE.7 still forbids discarding a listed failure. The cost is one declaration for each such function, without which a listed failure that a function returns passes silently where a caller ignores it; where no form exists, the cost is nothing, so the provision raises no floor (GOV.11). The custodian's ruling of 2026-10-23 on this outcome was made for C++; STND.STDC and STND.RUST, adopted on 2026-10-24, condition it on a compiler or static check among the means of the work, and this provision conditions it on a form of declaration that the language or those means provide. STND.CODE.35 carries the same form to each call of the work to a function of a dependency that reports a listed failure in its result: through the declaration that the dependency gives, which a compiler or an analyzer that knows the functions of a library also gives, or through a function of the work that wraps the call and is so declared. In C, the test of STND.STDC.28 or an error handler that ends the run receives some such failures, and STND.STDC.29 has the call carry the suppression of STND.CODE.4 there.

Required checks. The first sentence of STND.CODE.16 carries STND.CODE.6 to the checks that CPS.5 and CPS.9 require of work that commands hardware, where those provisions apply to the work at its class: a check that an execution setting removes is absent from each build and each run under that setting, where CPS.5 or CPS.9 still requires it. The words differ from those that the custodian ruled for C++, which had each such check run, with its response, in every build; the outcome is the same, because a check that CPS.5 or CPS.9 already requires, that no execution setting removes, and that no definition in the source turns off under the second sentence runs with its response in every build and run, and the present words also reach a run of an interpreter that has no build. Its second sentence reaches a check that a definition that the source gives to conditional compilation turns off, which is not an execution setting and which STND.CODE.6 therefore does not reach. The assert macro of C expands to an expression that does nothing where NDEBUG is defined at the point at which its header is included, whether an option of the compiler or a line of the source before that inclusion defines it, and is defined again at each inclusion of the header (research note round-addenda/a2-language-facts.md, which cites the working draft of C, 7.2); the same for the header of C++ is unverified. A definition after the last inclusion turns nothing off and is outside the second sentence. A check under a directive of conditional compilation on a macro that the source defines is removed in the same way; the two sentences exclude these forms for a check of untrusted input and for a check that CPS.5 or CPS.9 requires. In Python and Julia, the first sentence extends to the checks of CPS.5 and CPS.9 the forms that STND.PY.25 and STND.JL.13 exclude for untrusted input: an assert statement, which the optimizing mode of the interpreter removes, and in Julia `@assert` and a `@boundscheck` block. The second sentence adds nothing in Python, which has no conditional compilation, and a check under an ordinary condition on a constant of the source is not reached; in Julia it reaches a check under `@static if` on a constant that the source defines. In Rust, a condition of compilation is set by the build configuration, an execution setting that STND.CODE.6 and STND.RUST.15 already reach, so the sentence adds nothing there. In Fortran, standard source has no conditional compilation (unverified), and the sentence reaches only source that a preprocessor reads, where a definition in the file guards a check. In SystemVerilog, it reaches a check under a conditional compilation directive on a macro that the source defines. Lean has no conditional compilation of its own (unverified), so the sentence adds nothing there. The sentence reaches only a build that holds the code the check guards, so code compiled out together with its check leaves no input unchecked and is outside it. Each sentence keeps in every build a check that STND.CODE.6, CPS.5, or CPS.9 already requires, at the cost of the form of that check, so neither raises the floor in any language (GOV.11). The two sentences have one subject, the form of a required check, and apply together. The custodian's ruling of 2026-10-23 on the first sentence was made for C++, and the ratification of 2026-10-24 accepted it for C and for Rust (STND.RUST.15); the argument for the other languages, and for the second sentence in every language, is the one given here.

Finite values. An execution setting or an annotation that, by the documentation of its compiler, lets the compiler assume finite floating-point values licenses the deletion of tests for not-a-number and infinite values. The documentation of two compilers states the assumption and names no test that it deletes (the same research note), so whether a given compiler deletes them is unverified, and the Notes of STND.FTN record the hazard as unverified for Fortran compilers. STND.CODE.21 therefore keeps such a setting from the compilation of code that holds a check that the floor requires, the check of untrusted input of STND.CODE.6 or a check of CPS.5 or CPS.9 under STND.CODE.16, in every language, whether or not its compiler is known to delete the check, and STND.CODE.27 recommends against an annotation in the source that does the same. In Julia, the annotation is the `@fastmath` macro and the setting a mode of the compiler; the Python language has neither, and a compiler of Python code that offers such an option is reached by STND.CODE.21. Where a setting does remove the check, STND.CODE.6 or the first sentence of STND.CODE.16 already excludes it, in every language. STND.CODE.21 costs one choice of compiler option for code that holds a required check, and asks for no check that the floor does not already require, so it raises no floor in any language (GOV.11); the custodian ruled so for C++ on 2026-10-23, the ratification of 2026-10-24 applied it to C, and the custodian ruled on 2026-10-28 that the option binds for the checks that the floor requires, in every language alike. It binds at every class, CSQ4 included.

High assurance. High-assurance coding standards restrict a language to a subset that analyzers are able to check, commonly by limiting dynamic allocation, recursion, unbounded loops, the mechanisms of exceptions, casts, and the preprocessor, and each sets a procedure for recording deviations. Published ones exist for C and C++; for a language without one, the term admits a standard of the work's own making. The provisions name no standard, because standards and their editions change, and accept any that a decision record of the work adopts, the custodian's ruling for C++. Restrictions of this kind make the proof or exhaustive checking of the CSQ0 row of STND.CLASS.10 and the bounds of HW.20 and HW.EMBED.3 attainable in every language. Conformance reduces undefined and unspecified behavior by a mechanical check (DSGN.3); it is not evidence that a result is correct (VV.1). STND.CODE.18 keeps a claim of conformance to what was checked, by an analyzer, by a reviewer, or by both, so that no claim rests on a check that did not run (PRIME.2).

The custodian ruled for C++ that for high assurance the validation status is more important than the language standard. STND.CODE.19 therefore takes an edition that the adopted standard covers and for which the toolchain holds the validation or qualification that the work requires, which is often older than the newest, and admits one later feature at a time by decision record. The edition of a language is a revision of its definition, or, for a language that its implementation defines, a release of that implementation. For a hardware description, the toolchain includes the tools that synthesize and simulate it. STND.CXX.2 names STND.CODE.19 among the editions that it yields to; another language standard that asks for the newest edition yields to it where its own text says so. A check that runs the tests on a newest release without blocking a change, as STND.DEPS.14 asks, builds no delivered code, and so is outside STND.CODE.19. High-assurance code is all the delivered code of CSQ1 and CSQ0 work, so that no code of CSQ0 work gets less than code of CSQ1 work, and STND.CODE.17 asks conformance of the safety-related components of CSQ0 and advises it elsewhere, because the CSQ0 rows of STND.CLASS.10 bear on those components. Code built into CSQ0 work is used at CSQ0 (GOV.14), so a file that a CSQ0 controller and a CSQ3 simulation share is high-assurance code; the human owner may record a less severe class for a component shown to be isolated (GOV.13). External code that high-assurance code incorporates is governed by STND.DEPS and DSGN.5, with the contract and the wrapper that isolates it recorded. An analyzer is installed only under a recorded authorization (PRIME.7) and is listed in the tool record of STND.DEPS.9. An analysis too costly for each change is deferred to the release under RSRC.12, recorded in the unit record as STND.WPROC.9 provides. The deviation marker of STND.CODE.20 lets the release record of STND.WPROC.13 list each deviation by a search. A deviation is a decision record under REPRO.7, not a waiver, and code explains it by its technical reason (STND.DOCS.5).

STND.CODE.17 and STND.CODE.19 are defaults that apply from CSQ1 to high-assurance code, asking their outcome of the safety-related components of work of CSQ0 and advising it for other high-assurance code; they tighten the mechanical checking of each contract of a safety-related component, which STND.CLASS.10 applies at CSQ0 under DSGN.3, and VV.1, whose CSQ0 row the restricted subset serves, and those rows hold in every language alike. STND.CODE.20 asks the record of each deviation of work of CSQ1 or CSQ0, and the marker alone of other work that adopts such a standard (REPRO.7). Where the classification records an expected class of CSQ1 or CSQ0, STND.CLASS.21 has the design not preclude the subset, the edition, the failure channel, and the dependencies that STND.CODE.17, STND.CODE.19, and STND.DEPS.1 ask at that class, with the reason for each such choice in a decision record, and asks no other record of that class before the reclassification than the records of STND.CLASS.23; the marker of STND.CODE.20 is the one thing of this standard kept earlier, so that the reclassification finds each deviation by a search and the record that STND.CODE.20 then owes is written once. A project replaces each of the three by a recorded decision with an alternative that meets the same outcome, so they block no work in a language for which no standard is published. The fields of STND.CODE.17, STND.CODE.19, and STND.CODE.20 depart from the rule of STND.CLASS#reading-the-standard: they tighten the CSQ0 rows of DSGN.3 and VV.1. The custodian ratified the onsets of STND.CODE.17 and STND.CODE.19 for C++ with the provisions on high-assurance code that STND.CXX 1.1 held, and for C through STND.STDC.1; the record of STND.CODE.20 was ratified then as applying wherever such a standard is adopted, and revision 1.5 moves it to CSQ1 under the custodian's ruling of 2026-10-28 on design for the expected class, which minimizes what is owed before a reclassification. For the other languages the argument is this: the onset of CSQ1 follows the term High-assurance code, which starts at CSQ1 in every language because reliance by a party outside the project starts there; each of the three is a default, a tightening above the floor that a recorded decision replaces (PRIME.15, GOV.19), so none raises the floor; and the marker of STND.CODE.20 reaches work of CSQ3 only where that work has chosen to adopt a high-assurance coding standard, at the cost of one marker for each deviation from it. The three sentences of STND.CODE.19 concern one edition of one body of code and apply together. The custodian's rulings on high assurance were made for C++, and STND.STDC applied them to C on 2026-10-24; for the other languages the argument is the one just given. STND.CODE.18 adds to PRIME.2 only the naming of the means that checked a claim of conformance, at the cost of one sentence for each claim, and concerns claims and not the constructs of a language, so the argument holds in each language; it reaches only high-assurance code, which is never below CSQ1. The custodian ruled at the ratification of 2026-10-23 that the same provision raises no floor for C++ (GOV.11, PRIN.10).

A test added for each fixed defect (STND.CODE.8) is a regression guard unless its reference is independent of the code it judges (VV.7); either way it lets VV.8 detect the defect's return. A test whose verdict changes between runs of the same revision, seeds included, gives no evidence, and a test whose reference is local needs no network access, which would otherwise call for an authorization (PRIME.7) (STND.CODE.9). A constant that a measurement, a published reference, or a recorded choice fixes carries its unit, source, and revision once (STND.CODE.10), while a literal of a formula, a loop bound, and an index origin are not such constants; a measured or calibrated constant is also versioned data under REPRO.6, whose calibration states the conditions and the interval over which it holds (MEAS.5). Code disabled by turning it into a comment is neither active nor retired; the source history keeps it (STND.CODE.11, SIMPL.8). The custodian directs that code be laid out by the logical grouping of its instructions, so that a reader follows a computation step by step: a blank line ends a step, and a comment names a step whose purpose its code does not show (STND.CODE.13, INTPR.1).

Rules for every language. A rule that more than one language standard would state in one text, with no construct of its language, is held here once (GOV.31), and the language standards keep the constructs that give it a form. STND.CODE.28 has the names of the source follow the convention that the standard of its language gives, the tables of STND.CXX.14 and STND.JL.6 and the style guide of STND.PY.1 among them, or that the repository configuration names where the language standard gives none; the research notes of the corpus retrieved no convention of names that the definition of C, Fortran, or Lean fixes (unverified), and a convention that the lints of a compiler check, as those of the Rust compiler check the case of names, is named at no added cost. Its third sentence keeps the case of a symbol of the notation of NUMER.4, a matrix `A` or an operator `K`, under each such convention, and a lint that reports such a name is suppressed at its location with its reason under STND.CODE.4. STND.CODE.29 keeps a seed or fresh entropy from entering below the entry point, where an integer passed to two functions gives them identical streams and an unrecorded draw of entropy is repeated by no seed; its third sentence keys the stream of each part of divided work, parts run as separate runs included, to the root seed and the index of the part by a facility of STND.VVUQ.62, and STND.CONC.23 keys each stream of a computation divided among concurrent tasks to a part in the same way. STND.PY.15 and STND.JL.22 give the parameter through which a generator arrives in each language. STND.CODE.30 keeps out of results the values that a hash function leaves free to change, among them the built-in hash of a string in Python, which varies with the hash seed of each run, and the values of `hash` in Julia, which have changed between releases, and the iteration orders of the collections built on them, a set of strings in Python and a `Dict` or a `Set` in Julia (the Notes of STND.PY and STND.JL). STND.CODE.31 has each comparison within a tolerance state its parameters where the code makes it, since the defaults of comparison functions differ and a comparison that relies on them decides for a reason that the reader does not see: the isclose function of the math module of Python takes an absolute tolerance of zero, and `isapprox` of Julia, the function behind `≈`, a relative tolerance from the machine epsilon and an absolute tolerance of zero, so that `x ≈ 0` holds only for an exact zero. Each tolerance is a named constant with its basis beside it (STND.CODE.10, NUMER.11), so that a copied value without a basis stands out in review. STND.CODE.32 has the static checks that the repository configuration names decide each provision of the language standards that a static check among the means of the work is able to decide, the linter of STND.PY.2 and the static checks of STND.RUST.31 among them. STND.CODE.28 to STND.CODE.32 are defaults, each a tightening above the floor that a recorded decision replaces (PRIME.15, GOV.19), so none raises the floor (GOV.11).

Claims of soundness. STND.CODE.34 keeps a claim that code is free of undefined behavior, or of a kind of it, or that no use of an interface of the work is able to cause it, the claim that a Rust module is a sound module among them, to what its means checked: a detector observes only the executions that it runs, an analyzer is documented as sound for a kind of undefined behavior or not, and code of a dependency in the call chain is code that a claim covers or leaves out (the Notes of STND.RUST and STND.STDC). STND.RUST.33 and STND.STDC.38 add what the record of such a check states, and STND.RUST.34 binds STND.CODE.34 for Rust code (PRIME.2). A soundness argument at an unsafe construct is not such a claim. STND.CODE.34 is a default, a tightening above the floor that a recorded decision replaces (PRIME.15, GOV.19), so it raises no floor (GOV.11).

Foreign interfaces. The terms Foreign interface and Owned resource are defined here once, and the language standards that use them import them, and those with constructs of their own name the constructs of their language that are foreign interfaces (GOV.31). Code on the other side of a foreign interface does not check what code of the work assumes of it: the types and the layout of the data that cross, which failures leave a function and how, and who releases what and when. STND.CODE.22 to STND.CODE.26 state those assumptions as parts of the contract that DSGN.5 asks for each external component, and the language standards add only what their constructs make necessary: the representation attribute and the null pointers of STND.RUST.24, the unwinding of STND.RUST.25 and STND.RUST.26, the release of STND.RUST.27, the interoperable kinds and the strided sections of STND.FTN.27 and STND.FTN.28, the preserved memory of STND.JL.38, the interrupts of the operator in STND.PY.35 and STND.JL.39, and the failed releases of STND.CXX.21. The two sentences of STND.CODE.22 are the schema of one type at one boundary (DSGN.4): the second applies to a layout that the work declares again, apart from the declaration that the other side compiles, and is not applied without the first. A C declaration of a pointer to elements states no order of dimensions and no strides, so STND.CODE.23 takes them from the contract or from a test of the call. STND.CODE.24 keeps a failure from crossing code that does not propagate it: ISO C++ defines no behavior for an exception that unwinds through C frames, the specification of a structured block of a parallel directive requires an exception raised in it to be caught there, and an unwinding that enters Rust frames from a non-unwinding declaration is undefined behavior (the Notes of STND.CXX and STND.RUST). Its three sentences are one remedy and are not applied apart: a failure caught and neither converted nor stored is discarded, which STND.CODE.7 forbids for a listed failure. STND.PY.35 and STND.JL.39 store an interrupt of the operator in place of its conversion and raise it again after the foreign call returns, and the form of STND.CODE.14 in each language answers each other failure so stored. A language that propagates no failure by a mechanism of its own, Fortran among them, meets STND.CODE.24 with nothing. STND.CODE.25 gives each owned resource that crosses one owner, as DSGN.14 asks of state, and an owned resource that the interface predefines has the interface as its owner. Its second sentence applies to an owned resource that the interface creates for the work, and names its owner on the side of the work; the first applies to every owned resource that crosses, and the second is not applied without it. STND.CODE.26 keeps an object that foreign code still uses from being released or collected under it: a callback that foreign code calls after the data that it reaches is released is its hazard, and STND.CONC.5 governs the same hazard between concurrent tasks. STND.CODE.22 to STND.CODE.26 apply to the C, Fortran, and Lean source of the work, and to a hardware description, for each foreign interface that it declares, beside what STND.FTN.27 and STND.FTN.28 state. The structured block of a parallel directive is a foreign interface for STND.CODE.24 alone, the one rule that the terms of STND.CXX and STND.STDC applied to it, since the data and the resources of a block have no contract of an interface that fixes their layout or their owner.

Under STND.CLASS.10, each default provision applies from the class that its field `onset` gives, which work of CSQ4 may omit, and STND.CODE.21 binds at every class; the rules of the form of code at a foreign interface, the declaration of STND.CODE.35, and the catch of STND.CODE.24 apply from CSQ3, since each costs nothing when the code is written and a rewrite of each interface when it first applies at a reclassification, while the comparison of layouts in the second sentence of STND.CODE.22 compares two declarations under the schema of DSGN.4 and starts at CSQ2. No default provision raises the floor (GOV.11). Hardware descriptions are code under this standard; HDES.6 governs what their verification shows.
