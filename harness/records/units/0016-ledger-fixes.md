# Unit 0016: ledger fixes of QA.8 part B

The QA.8 review of part B (`review-records/harness/qa8-part-b.md`) read the ledger, core, cli, workflows, derive, and query packages and found 3 High, 6 Medium, and 8 Low findings. The High findings are a ledger that one text character makes unreadable for good (H1), a ledger rewritten without signatures that passes once `SIGNR` is removed although the owner's configuration names an anchor (H2), and a tail of the ledger that can be cut with `verify` still passing (H3). The Medium findings are a key closed for a ledger that stays valid through an `all` row (M1), `record_transaction` writing manifests before the ledger refuses the entry (M2) or appending an unsigned entry that the register requires to be signed (M3), a pin that goes stale when a later scope covers the same directory with other paths (M4), a scope hash that two sets of files can share (M5), and signature rules that no test holds (M6). This unit fixes every High and Medium finding, and L1, L2, and L5.

## Definition of done

1. H1: a ledger line ends at a line feed only, so an entry whose text holds U+2028, U+2029, or U+0085 reads back whole, and `append` refuses a line that does not read back as the entry. A test covers each of the three characters.
2. H2: where the signer configuration names an anchor and the corpus has no `SIGNR`, the ledger check of `verify` fails, and so does every reader that trusts the ledger through it.
3. H3: the signer configuration may pin the head of the corpus ledger (`seq` and `hash`). `verify` and `sign check` fail when the ledger lacks that entry. The README states the residual without a pin. A missing or empty ledger fails where the corpus holds content to pin. No file is written under `/etc`, and no owner configuration is created; the tests build or patch one.
4. M1: a row for a ledger overrides an `all` row for the same key and role label there.
5. M2: `record_transaction` writes nothing before every refusal that `append` can raise has been checked. A test compares the whole tree after each refusal.
6. M3: an unsigned entry that the register requires to be signed is refused, naming `ledger append --sign`, and a register transaction is refused while the register has problems.
7. M4: a pin holds per path, not per scope tuple, and the live corpus still verifies.
8. M5: the scope hash is unambiguous, and every hash recorded in the live ledger stays valid.
9. M6: a test kills each surviving mutation the review lists, and each mutation, rerun on a scratch copy, fails a test.
10. L1, L2, and L5 are fixed where cheap; the other Low findings are listed with the reason they are not done.
11. The tests of what changed pass, with `tests.test_architecture` and `tests.test_conventions`. `verify governance` passes on the live corpus with its ledger unchanged. Ruff adds no finding on the changed files. The README describes each change of behavior. `harness/governance/` is unchanged.

## Record

- H1, done in `ledger/transactions.py` and `ledger/chain.py`.
  - `parse_ledger` splits on `"\n"` only, and names the line of a refusal (`line N: ...`). `canonical_json` writes Unicode unescaped, so the three characters go into the file raw, and `str.splitlines` took each for a line end.
  - `append` parses the line it is about to write and refuses it, with nothing written, unless it reads back equal to the entry. After the split fix no text reaches this, but a NaN does: JSON writes `NaN` and reads back a value unequal to itself (part of L4).
  - Tests, in `tests/ledger/test_chain.py`, class `ReadBack`. `test_line_separators_in_text` appends a rationale holding each character, in a subtest per character, reads it back equal, appends again, and expects the ledger check to pass. `test_entry_that_does_not_read_back` appends a NaN field and expects the refusal with the file unchanged. The reviewer's command-line repro (`ledger append ... --rationale` with all three characters, then a second append and `verify --no-logic`) now passes on a copy.
- H2, done in `checks/ledger.py`. Where `config.anchor` is set and the tree has no `SIGNR/_doc.md`, `ledger_problems` reports "the signer configuration names an anchor key, but the corpus holds no SIGNR". The configuration is the trusted side, since the agent cannot write it. `environment` already refused this case through `register_trace` (unit 0010), and its `verified` reading now also fails through `ledger_problems`. `sign check` already failed without a register. No other reader trusts the signatures. Test: `tests/checks/test_ledger.py`, `TrustedConfiguration.test_anchor_without_register`.
- H3, done in `ledger/gpg.py`, `ledger/transactions.py`, `checks/ledger.py`, and `cli/records.py`.
  - `SignerConfig` has a field `head`, read by `read_config` from the key `head` of the configuration file, `{"seq": N, "hash": H}`. It is read under the same `unalterable` gate as the anchor, and it is kept as given, so that a malformed pin fails rather than being dropped.
  - `transactions.head_problems(entries, head)` fails when the pin is malformed (not a whole number from 1 with a text hash; `true` is not a number here), when the ledger ends before entry N ("entries were cut"), or when entry N has another hash ("the ledger was rewritten"). The chain check then holds every entry up to N.
  - `ledger_problems` and `sign check` (on the corpus ledger) report these lines. `sign check` now reads the corpus ledger with `read_ledger`, so a corpus with a register and no ledger file is a failure line, not a `FileNotFoundError`.
  - `ledger_problems` fails a missing or empty ledger where the tree holds any Markdown file. Every corpus has content a scope can pin, so this is the plain reading of "where the corpus has scopes to pin".
  - Residual, in the README under "What `verify` checks": without a pin, any tail of the ledger can be cut by an account that can write `ledger.jsonl`, and `verify` passes; with one, the entries after N can still be cut, so a revocation is durable only from the pin on. The README gives a command that prints the pin from the last line. Work ledgers have no pin.
  - Nothing was written under `/etc`; the tests build a `SignerConfig` or patch `read_config`.
  - Tests: `TrustedConfiguration.test_head_pin` (pass at the head, pass after a later append, fail when the last two entries are cut, fail when entry N is rewritten with its links rebuilt, which passes without the pin, and five malformed pins); `TrustedConfiguration.test_missing_ledger` (the check, and `verify --no-logic` exits 1 with the file removed and with it empty); `tests/ledger/test_signatures.py`, `SignCheckHead.test_cut_entry_fails` (a signed corpus, `sign check` passes with the head at its last entry and exits 1, "entries were cut", once that entry is removed).
- M1, done in `ledger/register.py` and `ledger/signatures.py`. `governing_rows(register, fpr, role, ledger)` returns the rows for that key and role label that name the ledger, or, when none does, those for `all`. `_valid_for` and `active_signers` use it, so `all | none` with `governance | 5` lets the key sign governance entries up to 5 only, and other ledgers still. The register's docstring says how an `all` key is closed. Test: `SignerRows.test_all_row_closed_per_ledger`, the reviewer's repro.
- M2, done in `workflows/amend.py`. `record_transaction` appends first and rebuilds the manifests after. The manifests are not Markdown, so no `corpus_hash` covers them and the entry is the same either way. Every refusal of `append` (the type, the file, the chain, and the refusals of M3 and M4) now comes before any write. Tests: `tests/workflows/test_amend.py`, `RecordRefusals.test_refusals_of_the_ledger` (an unknown type, a broken chain, and an unreadable last line) and `RecordRefusals.test_unsigned_entry_the_register_requires`. Each raises STND.INSTR first, so that its manifests are stale, and compares `tree_digests` of the whole copy before and after.
- M3, done in `ledger/chain.py`, in `append` rather than only in `record_transaction`, since `ledger append` without `--sign` sealed the same unverifiable entry. `_chained` reads the register whenever the corpus has one, and `_refusals` refuses:
  - an unsigned entry whose actor a requirement row covers at its `seq` (`signatures.required_of`, which `check_signatures` now shares): "`The Custodian` must sign entry N (required from entry M): use ledger append --sign KEY; nothing appended";
  - a transaction whose scope names `SIGNR` while the register has problems, which `_chained` used to ignore.
  - Tests: `Refusals.test_unsigned_entry_the_register_requires` (refused with the tree unchanged, then appended signed and the ledger verifies), `Refusals.test_register_with_problems`, and the amend test above. The case "renumbered to evade a requirement" of `test_ledger_signatures` appended the unsigned entry that is now refused; it writes it with a new helper, `append_unchecked`, as an agent with write access to the file could, and `verify` still sees it.
- M4, done in `ledger/transactions.py`, `checks/ledger.py`, and `ledger/chain.py`.
  - `live_pins(entries)` keeps a transaction while some path of its scope is not covered by a later scope, the same path or a directory above it (`covers`). The latest transaction that covers a file is always live, so every file is still compared with a pin. The ledger check compares only live pins. Live pins are a subset of the latest pins per tuple, so a corpus that passed before passes now; `verify governance` passes.
  - The converse case of the review, a narrower scope after a wider one, cannot be fixed in the check, since one hash covers the older scope. `append` refuses it instead (`_left_stale`): a scope that shares content with a live older pin whose content changed is refused, naming that entry and asking for all its paths.
  - Tests: `Pins.test_wider_scope_after_narrower` (STND/DFLT edited, then pinned with STND/PY, and again under STND), `Pins.test_narrower_scope_after_wider` (refused for STND/DFLT alone and with STND/CXX, ledger unchanged; accepted with both paths), and `Pins.test_live_pins` on hand-built entries.
  - STND.HARN.9 reads "the latest governance-ledger transaction with that scope". Taken literally, it asks for the FAIL in the forward case that this fix removes, so the check is now laxer than the letter of the provision in that one case, though every file is still pinned. See Open.
- M5, done in `core/corpus.py`. Changing the encoding of `scope_hash` would change the hash of every scope, so every recorded `corpus_hash` of the live ledger would go stale; per the brief, it was not changed. A file name rule closes the ambiguity instead. `scope_hash` raises `ValueError` for an included file whose name holds a control character (Unicode category Cc, which takes in the line feed). With no line feed in a name, each line ends at a line feed and its last 64 characters are the digest, so the encoding is unambiguous. `ledger append` refuses such a scope; the ledger check reports a live pin over one as a failure line. The live corpus has no such name, and every recorded pin still matches. Test: `Pins.test_control_character_in_a_name`.
