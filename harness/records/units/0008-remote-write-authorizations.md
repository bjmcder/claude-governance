# Unit 0008: remote writes that an authorization names

The remote-write row of STND.HARN.18 refers each remote write that no authorization in force names by destination and kind of write. Under the transition of ledger entry 53, the derived configuration has referred every remote write, because STND.PROJ fixed no form in which an authorization names a destination and a kind. This unit drafts that form (STND.PROJ 1.2: STND.PROJ.6 and STND.PROJ.7), the rule by which a derived configuration relies on one (STND.HARN 1.2: STND.HARN.29), and the harness change that implements the row. The amendments are drafts for the custodian, in `tools/amendment-scripts/apply_round_2026_10_24_harn.py`; until they are applied, the code cites provisions that the live corpus does not yet hold.

## Definition of done

1. `environment` takes `--authorization ID`, repeatable, naming an authorization file of the corpus. Without it the configuration is unchanged except that the guard's policy gains the field `remote_writes`, empty.
2. A named authorization is in force only where it meets every test of STND.HARN.29: status adopted, grantor the human owner, recorded no later and expiring later than the derivation, an intact ledger whose latest transaction pinning the file is an `authorize` of it by the human owner that pins its current content and that no later `revoke` names, a signature verified by the signer register for assured work, and every field in the form of STND.PROJ.6 and STND.PROJ.7. One that is not in force exits 1 with every reason. A standing authorization of publish or transmit, or naming a destination not recorded as provisioned, is not in force (GUARD.11). A per-action authorization, and the kinds publish, transmit, and other, open nothing and are named in the coverage report.
3. Each destination and kind of commit or post that a standing authorization in force names reaches the policy with its branches and expiry, the ask rule `Bash(git push *)` is dropped while a commit is opened, and the coverage report of remote-write states the conditions, the authorizations still referred, and each destination whose host is no opened domain. No outcome becomes full.
4. The guard lets a `git push` or a `gh issue create`, `gh issue comment`, or `gh pr comment` proceed without referral only where an unexpired entry of the policy names its kind and its destination as the same whole string, and, for a push, every branch; the call holds no other command; no assignment, reserved word, or global option precedes it; it takes no option outside a short list; and, for a push, the git configuration of the repository, the worktree, the account, and the system is readable and sets no rewriting of addresses, push address, inclusion, recursion into submodules, pushing of tags, transport program, or proxy, the remote has one address, the refspecs name branches and no local tag, and no variable of git is set; for a post, `--repo HOST/OWNER/REPO` names the tracker, no variable of gh is set, and a body file is checked as a read. Every other remote write is referred, as before. A malformed or expired entry refers.
5. Each criterion has a test; every earlier test passes; ruff is clean on the new files and adds no finding on the changed ones beyond those the files already had; the convention and architecture tests pass; the guard imports nothing from the package; the rehearsal of the round verifies.
6. The README and decisions 0001 and 0002 record the change.

## Revision after review

The security review (`review-records/round-2026-10-24/harn-auth/review-security.md`) and the cold and pair review (`review-cold-pairs.md`) found three High findings, two Defects of STND.HARN.29, and Medium and Should-fix items. This section supersedes the statements above where they differ: the ask rule for every push is no longer dropped, and a push passes only as one command of plain words.

- H1: `-n` is a dry run only as a word of its own beside options that take no value (`dry_run`), for push and for every other subcommand; `git --namespace x` and `--config-env` take their value. The ask rules for `git push` and the three `gh` posts stay; the guard answers `allow` for a write an authorization names. No source authorized for this unit shows that a hook's allow outranks an ask rule, so the design refers in doubt.
- H2: `work_repository` takes only the work's own `.git`, valid as git tests it (`HEAD`, `objects`, `refs`), with no `.git` between the command's directory and the work, by the paths links lead to. A write into a `.git` directory by a file tool, a redirection, or a copying or creating command reaches history-rewrite (Refuse).
- H3: an authorized write passes only where the whole command line matches `PLAIN_RE`, so no here-document, here-string, redirection, substitution, expansion, pattern, comment, or separator is present.
- M1: git and gh named by a path are referred. M2: `alias`, `credential`, `core.hooksPath`, `core.fsmonitor`, and `core.askPass` are read as redirections, and a hook other than a sample in the repository refers the push. M3: a post takes only `--title`, `--body`, and `--repo`, with literal text holding no `@`; a body file is referred. M4: a signature is required wherever a signer register exists, and the command prints, for each authorization, the transaction that pins it and what it opens. M5: `--expiry-horizon DAYS` bounds the expiry; `environment --check` fails once an authorization is revoked, because the derivation then fails. M6: the coverage text, the README, and decision 0002 state the conditions and what is not seen.

## Revision after re-verification

The re-verifications (`verify-security.md`, `verify-cold-pairs.md`) found no Critical or High finding and the amendments adoptable, with these last items.

- Correction of the item L2 above: reading paths where their links lead holds for the work and the command's directory at the time of the call; it does not cover a program that changes a link, a configuration, or a hook afterwards. For that, M-a: while a commit is authorized, the managed settings add `<work>/.git/config`, `<work>/.git/config.worktree`, and `<work>/.git/hooks` to the sandbox's `denyWrite` (`git_metadata` in `derive/environment/claude_code.py`), so a program started earlier is unable to swap them between the guard's check and the push while the sandbox runs; `git config` and `git remote set-url` then fail in the sandbox, and commits and pushes, which write objects, refs, and logs, still run. A `core.hooksPath` needs no entry: the guard refers every push while one is set, and these files are where a shell command would set it. The common configuration of a linked worktree lies outside the work and is writable by a shell command only where the owner opens its location. Test: `test_git_metadata_denied` in `tests/derive/test_authorizations.py`. Installation test, open: in a session under the installed configuration with a commit authorization, `python3 -c "open('.git/config', 'a')"` run by the shell fails.
- Finding A: the kind commit of STND.PROJ.7 reads "a named branch, whose update neither publishes nor deploys, of a remote repository".
- Findings B and C: the Notes of STND.HARN say that after a revocation a derivation that still names the authorization stops with the reason, and one that no longer names it differs from the installed configuration, which STND.HARN.21 reports; the floor argument names the checks the harness makes as part of the cost.
