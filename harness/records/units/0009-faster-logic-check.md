# Unit 0009: a faster built-in solver for the logic checks

Every amendment transaction runs a full `verify`, and most of its time went to the built-in SAT solver of the proofs (checks f), whose unit propagation rescanned every clause on each pass. The custodian directed on 2026-10-24 that the solver be made substantially faster without changing any result. This unit replaces the propagation with two watched literals per clause and codes the clauses once per solve; the search order, and so every status, model, and core, is kept.

## Definition of done

1. Unit propagation in `checks/logic/satlib.py` no longer rescans the clause set: a clause is visited only when one of its watched literals becomes false. Standard library only; no new dependency; no clause learning.
2. The solver gives the same status as before on every clause set, and the same model and the same core wherever it reports one: it splits on the first unassigned variable of the first clause not yet satisfied, in the order given, false before true, and a clause is unit or in conflict under the same rule as before, counting a repeated literal once per occurrence.
3. Seeded tests compare the solver with brute force on many small random clause sets and with the search it replaced, and cover the empty set, the empty clause, unit clauses, repeated and complementary literals, and a set over no variable. Every earlier test passes.
4. On the live corpus, `verify` prints the same output as before, character for character, and every solve gives the same status, model, and core as the baseline captured before the change.
5. The time of `verify` and of the full suite is measured before and after; the README states the solver and the time.
6. Ruff 0.16.10 at 79 columns adds no finding on the changed files; the convention and architecture tests pass; `governance/` is unchanged.

## Record

- Changed, in `checks/logic/satlib.py`: `_satisfied` and `_propagate` are removed. `_encode` numbers the variables in order of first appearance and codes the literal `(variable, polarity)` as `2 * number + polarity`. `_Search` holds the values, the trail, and the watch lists: each clause of two or more literals keeps a working copy whose first two positions are watched (the scheme of Chaff and MiniSat), and `propagate` visits only the clauses watching a literal just made false, moving the watch to a literal that is not false, or else assigning the other watched literal (unit) or reporting a conflict. One-literal and empty clauses are settled before the search (`roots`). `_dpll` now takes coded clauses and returns the values of the model; it keeps the explicit stack of splits, so it still neither recurses nor touches the recursion limit, and it undoes the trail to the split on backtracking, where the watches need no undoing. `solve_builtin` codes the clause set once and gives each search of the core minimisation the coded axioms and the remaining facts, in the same order as before. `ClauseSet`, `SolveResult`, `solve`, `solve_z3`, and `prove_entailed` are unchanged.
- Why the results are the same: unit propagation from a given assignment ends in the same assignment, or in a conflict, whatever order it visits the clauses in, since each literal it assigns is forced in every extension that satisfies the clauses. The rule for unit and conflict is unchanged (a clause not satisfied with exactly one unassigned occurrence, or none), so each node of the search has the same assignment as before; the split variable depends only on that assignment and the order of the clauses, which is unchanged, and the stack tries false first and backtracks chronologically as before. So the search visits the same nodes and returns the same first model. The core depends only on the status of each search of the deletion loop, in an unchanged order. The model reported is the same dictionary, in the same key order (`ClauseSet.variables`).
- Baseline and comparison (scratch scripts outside the repository): before the change, `verify` was run in process with `solve_builtin` and `_dpll` wrapped, recording for each of the 8 solves the clause set, the status, the model with its key order, and the core, and the status of each of the 3122 searches (221 satisfiable). After it, the same capture gives the same output (186 characters), the same 8 results, and the same 3122 statuses. Replaying the 8 recorded clause sets through the new `solve_builtin` gives the same results. `check governance --no-z3 --out-dir DIR`, run with the old and the new `solve_builtin` in one process, prints the same 5087 characters and writes the same `logic_report.md`, `logic_facts.json`, and `drafting_punch_list.md`. The tests of `tests/checks/` were also run with every in-process call of `solve_builtin` made by both solvers and compared: 3991 calls (2029 satisfiable), none differing in status, model and its key order, core, or backend, and the 34 tests passed.
- Measurements, on the machine of this unit (Python 3.14.8, no z3, so the built-in solver runs), wall time: `verify governance` 11.26, 11.43, and 11.31 s before (median 11.31 s), 2.85, 2.88, and 2.91 s after (median 2.88 s), with the same output, compared with `cmp`; the solver alone, replaying the 8 solves of `verify`, 10.60 s before and 1.40 s after; the full suite (`python3 -B -m unittest discover -s tests`) 302.8 s for 189 tests before, 138.6 s for 197 tests after, all passing. Under cProfile, before, `_satisfied` was called 38.2 million times and `_propagate` 34,572 times, with 22.1 s of 25.8 s in `_dpll`; after, propagation takes 0.5 s, and building the watch lists for each of the 3122 searches is most of what remains (under cProfile, 5.4 s of 9.3 s in `solve`, of which 3.2 s is `_Search.__init__` and 1.0 s `roots`, against 0.6 s for `propagate`). The brief's figures (22.6 s, 2,966 searches) were taken on another machine and an earlier corpus.
- Tests, in `tests/checks/test_satlib.py`: `AgreesWithBruteForce.test_random_formulas` (3000 clause sets of up to 14 clauses of up to 4 literals over up to 6 variables, seeded with `SEED`, drawn with replacement so that literals repeat and clash, about one clause in thirty empty; the status equals brute force, a model satisfies every clause and equals the model of `rescanning_model`, a copy of the replaced search, and a core equals the core of the same deletion order decided by brute force; both statuses occur in more than a fifth of the sets), `test_solve_and_entailment_use_the_same_search` (300 bases with random claims through `solve` and `prove_entailed` without z3), `test_long_chain_propagates` (2000 implications); `EdgeCases` (no clauses, the empty clause alone and among others, unit clauses and contradicting ones, repeated literals, tautologies). Each of eight changes to the solver fails these tests, checked by patching each in turn: trying true first, branching on the last open variable, ignoring a conflict in propagation or among one-literal clauses, ignoring an empty clause, moving a watch to a false literal, merging repeated literals, and not unassigning on backtracking (two of them make the search run on, which the suite shows as a test that does not end).
- Ruff 0.16.10 at 79 columns, with the settings it resolves for the tree (no configuration file): no finding on `satlib.py` or `test_satlib.py`, before or after, with E501 selected too; `ruff format --check` at 79 columns now passes on both, where it would have reformatted one expression of `satlib.py` before.
