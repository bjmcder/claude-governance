# Unit 0011: reuse of the logic check's solves

Every amendment transaction runs a full `verify` (`record_transaction` in `workflows/amend.py`), and `rehearse` runs a round of them. After unit 0009, about half of `verify`'s 3 s went to the built-in solver: 8 solves, about 3,100 searches, nearly all of them the core minimisation of the six refuted claims. The clause set comes only from the authority-tier statements and from LVL0's precedence and waivers, and the lead found it byte-identical across the round of 2026-10-25 (2,562 clauses). The custodian directed on 2026-10-25 that the results of those solves be reused when their clause sets are unchanged, so that a transaction that does not change the authority-tier statements does not solve again.

## Definition of done

1. Correct by construction: a solve's key is a SHA-256 digest of everything its result depends on, namely the clause set in a canonical serialization that keeps every order the solver's result depends on, the claim, the backend (the built-in solver, or z3 and its version), and a version of the solver code. A changed input is a new key and a full solve.
2. A reused result makes the output of `verify`, of `check`, and of every report byte-identical to a fresh solve, statuses, cores, and backend strings included.
3. The cache lies outside the corpus and is no part of the record or of any rendered or derived file. Its location is an XDG cache directory, an environment variable, or a command option. It can be turned off (`--no-cache`, `GOVHARNESS_NO_CACHE`). Deleting it costs only time. A corrupt, truncated, or unreadable entry is ignored and recomputed. Writes are atomic: a temporary file, then a rename.
4. Rehearsals hit across their temporary copies, since the key depends only on content. Two processes writing one key cannot corrupt the cache.
5. Integrity: the cache holds no secret and no corpus text, and a planted entry cannot make `verify` pass a corpus that should fail. The check chosen for each kind of result is stated here.
6. Standard library only, Python 3.11 or later, numpydoc docstrings, and the layer and effect rules of decision 0001, adjusted where needed and enforced by `tests/test_architecture.py`.
7. Tests: a hit gives identical output; a change of the clause set, the claim, the z3 setting, or the solver version misses; a corrupt entry is recomputed; `--no-cache` bypasses the cache; concurrent writers are safe; a planted wrong entry is caught. Every earlier test passes.
8. The time of `verify` is measured before and after (median of 3, cold, warm, and without the cache), with a profile. `verify governance` and a rehearsal print the same with a cold cache, a warm one, and none. The README states the cache.

## Record

- Design. The key (`checks/logic/solvecache.py`) is SHA-256 over a header line, the canonical JSON of `["govharness-solve", 1, version, backend]`, and then one line per clause, the canonical JSON of its name and its literals. Canonical JSON escapes every line feed, so the lines delimit the clauses and the key determines the ordered set. Nothing is sorted: the built-in solver's model and core depend on the order of the clauses (split order, core minimisation order), on the order of each clause's literals (split variable, variable numbering), and on repeated literals (`_Search` counts each occurrence), and z3 receives the clauses in that order. The claim enters the key as the clause of its negation, `NEG[<filled title>]`, with its literals. The backend is `satlib.backend_name(use_z3)`, `builtin-dpll` or `z3 <version>`, so `--no-z3`, the presence of z3, and its version are each part of the key. The version is a digest of the source of `satlib.py` and of `solvecache.py` (`workflows/solve_store.solver_version`). The encoding of the corpus as clauses (`proofs.py`, `facts.py`, `tiers.py`) needs no version, since its output, the clause set, is in the key. The Python version is not in the key either: the solver's result is a function of the clause list alone, built from lists and insertion-ordered dictionaries, with no iteration over sets or hashes.
- Planning keeps the checks on data. `proofs.py` now builds the base and each claim's negation once per run (`_negations_of`). With a cache, `_keys_of` digests the base once and extends a copy of that digest by each negation's one clause, and `planned_keys(ctx)` returns the 8 keys before the run. `workflows/verification.run_logic` loads those entries into `CheckContext.solve_cache` (a `SolveCache`: `known`, `fresh`, `hits`, `rejected`), runs the checks, and saves `fresh`. The checks never call the store. An injected store object would have let the checks perform file effects through a value, which the architecture test does not follow. Decision 0001 records the adjustment, and `tests/test_architecture.py` gains the effect `cache` for calls into `workflows/solve_store.py`, modeled on `config` for `ledger/gpg.py`.
- Entries hold `format`, `key`, `satisfiable`, `backend`, and the model as a string of `0` and `1` in the order of `ClauseSet.variables()`, or the core as positions in the clause set. They hold no corpus text: the core's names are rebuilt from the positions. Positions are needed because the corpus's base has clauses that share a name (`fact:PRIME.6 bars standing cover(PRIME.6#s1)` four times). `SolveResult` gains `positions`, which `solve_builtin` and `solve_z3` fill (z3's from its tracking names). An honest entry of this corpus is 154 to 1,456 bytes.
- Integrity check (`decode_entry`; `satlib.satisfies`, `satlib.confirms_core`). An entry of another key, format, or backend, or one that is malformed, is refused. Each kind of result then gets its own check:
  - Satisfiable result: the model must name exactly the set's variables, in order, and satisfy every clause. This is linear and needs no search. Its identity with the model a fresh solve finds is not checked, and no check, report, or output shows a model (`grep` finds no use of `.model` outside `satlib.py` and `solvecache.py`).
  - Unsatisfiable result: the positions must be distinct fact clauses, and the axioms with those facts must be unsatisfiable (one search). Since a superset of an unsatisfiable set is unsatisfiable, this confirms the verdict.
  - Unsatisfiable result of the built-in solver: the positions must also be increasing and exactly the core its deletion minimisation finds. The minimisation keeps a fact exactly when the facts kept before it and all facts after it, with the axioms, are satisfiable. A dropped fact needs no search, because those clauses include the core. A kept fact needs one search. So the check makes 1 + |core| searches instead of 1 + |facts|, and a reused core is byte for byte the fresh one.
  - Unsatisfiable result of z3: the core cannot be reproduced without z3, so it is checked for soundness only. A planted z3 core that refutes, but differs from z3's own, could change the listed core facts of a report, never a verdict. z3 is not installed here.

  A refused entry is recorded with its reason, recomputed, and overwritten with the fresh result. `verify` and `check` name it on the standard error and leave the standard output unchanged.
- Why a planted entry cannot pass a corpus that should fail. A check of the proofs fails only on a status: f.1 fails when the base is unsatisfiable, and each claim fails when its negation is satisfiable. A wrong "satisfiable" for an unsatisfiable set needs a model that satisfies every clause, which does not exist. A wrong "unsatisfiable" needs a set of facts that, with the axioms, the built-in DPLL refutes, and DPLL is complete. So no planted entry can change a status. For the built-in backend, the core check also fixes every core fact a report lists. What a writer of the cache directory can still do: delete entries or fill the disk (time and space only), and plant a different valid model (shown nowhere). Against the files themselves, entries are opened relative to their directory, which is opened with `O_NOFOLLOW`, and each entry is opened with `O_NOFOLLOW | O_NONBLOCK` and read only when it is a regular file of at most 4 MiB. A planted link, named pipe, directory, or oversized file is therefore skipped, never followed, blocked on, or written through. Because a link in place of the cache directory could aim writes into the corpus, a cache directory that resolves inside the corpus is refused with exit 2. I chose this check over trusting UNSAT entries because it costs little: with the exact check, the warm solves take 0.25 s, 225 searches against 3,122; checking soundness alone would save about 0.2 s more.
- Store (`workflows/solve_store.py`). An entry is `<dir>/<key[:2]>/<key>.json`. The directory is `--cache-dir DIR`, else `GOVHARNESS_CACHE_DIR`, else `govharness/solves` under an absolute `XDG_CACHE_HOME` (a relative one is ignored, as the XDG specification says) or `~/.cache`. `--no-cache` (on `verify` and `check`, exclusive with `--cache-dir`) or `GOVHARNESS_NO_CACHE` set to anything but empty or `0` turns the cache off, and the variable also reaches `rehearse` and amendment scripts, which take no option. A given `--cache-dir` wins over the variable. A write creates `.<key prefix>.<pid>.<count>.tmp` exclusively (`O_CREAT | O_EXCL | O_NOFOLLOW`, mode 0600) in the entry's directory (mode 0700), writes it, and renames it over the entry (`os.rename` with directory descriptors, atomic on POSIX). Two writers never share a temporary file, a reader sees the old entry or the new one whole, and the last rename wins between equal entries. There is no `fsync`: an entry lost or truncated in a crash is refused and recomputed. Where `os.open`, `os.rename`, and `os.unlink` take no directory descriptor, the cache is off (`supported`). Every failure to read or write is dropped, since the cache only saves time.

## Revision after review

This section supersedes the Record above where they differ: the z3 bullet of the integrity check, the test counts, and `SOURCES`.

- M1 (defect: `record_transaction` appended the ledger entry before `verify_corpus` refused a cache inside the corpus; `rehearse` likewise): fixed.
  - `record_transaction` calls `usable_store(root, True)` right after checking its scopes, before it rebuilds a manifest or appends, and passes that store to its verify.
  - `rehearse` calls it on the source before it snapshots or copies anything, and on the copy before the script runs.
  - Both document the `ValueError`.
  - `Location.test_amendment_refused_before_any_write` sets `GOVHARNESS_CACHE_DIR` inside a corpus copy. Both calls raise, every file digest of the copy (ledger and manifests included) is unchanged, and the rehearsal's work directory stays empty. With the earlier code the ledger gained a line, and this test fails.
- M2 (the z3 path cannot run here): of the two options, I chose to re-solve rather than reuse a z3 core. An unsatisfiable z3 result is no longer saved, and an unsatisfiable z3 entry found in the cache is refused ("a z3 core is not reused"). The reasons:
  - A z3 core cannot be confirmed to be the one a fresh z3 run lists, so reusing it could change the listed core facts.
  - z3 does not run the built-in solver's costly minimisation, so re-solving costs little.
  - This leaves one guarantee for every reused core: it is exactly the fresh one.

  A z3 model is still reused after the model check, since no output shows a model. `confirms_core` loses its `exact` parameter and is always exact. Without z3, `Z3Path` runs `solve_z3` against `StubZ3`, a stand-in that solves with the built-in solver:
  - `test_core_positions_are_parsed`: positions and names are read from the tracking names, an axiom tracker is dropped, z3's order is kept, and names holding `__` or shared by two clauses are handled.
  - `test_z3_model_is_reused_and_core_is_not`: a z3 model is saved and hit; a z3 core is not saved.
  - `test_z3_cores_are_not_reused`, replacing `test_any_core_that_refutes_passes_for_z3`: planted z3 cores are refused.

  A run with real z3 is still not done.
- T1 (no `..` or link path): `Location.test_cache_reaching_the_corpus_by_dots_or_link_is_refused` covers `<parent>/x/../<corpus>/c` and a link to the copy's `STND`, through `inside` and through `verify` (exit 2). With `resolve` removed from `inside`, both subtests fail; that mutant was run.
- L1: `SOURCES` now includes `core/hashing.py`, whose `canonical_json` builds every key (`Location.test_version_covers_the_canonical_json`).
- L2: `SolveStore.load` records in `skipped`, with a reason, each entry that is present but not read: a link, a linked shard directory, not a regular file, too large, or unopenable. `verify` and `check` print `solve cache: entry K skipped (reason); recomputed` on the standard error; an absent entry is not named. `test_unreadable_entries_are_skipped` asserts the five reasons. `test_corrupt_entry_is_named_and_rewritten` replaces an entry by a named pipe: the standard output is unchanged, the line is printed, and the entry is rewritten.
- L3, both parts adopted:
  - `verify_corpus` now defaults to `cache=False`, so a library caller writes no cache unless it asks (`test_library_default_writes_no_cache`). `verify`, `check`, `record_transaction`, and `rehearse` turn the cache on.
  - A relative `GOVHARNESS_CACHE_DIR` is refused with `ValueError`, or exit 2 from the commands, since it would name another directory from each working directory. A relative `--cache-dir` is made absolute when the command starts (`test_relative_paths`).
  - Hit counts and eviction are still not offered; see Open above.
- L4 (no `fsync`): left as is. A crash can leave an empty or partial entry, which is refused and recomputed (`test_corrupt_entries_are_recomputed`, `test_corrupt_entry_is_named_and_rewritten`), so durability would buy nothing but time per write.
- Also found while writing the M2 tests: `test_wrong_status_is_refused` used the first three facts of the two-core set as its satisfiable set, but `a`, `not a`, `b` is unsatisfiable. The planted cores it named were still refused, but for the wrong reason. The test now uses `a` and `b` alone, which are satisfiable.
