# Deep review of 2026-10-28: anthropic-docs

## Scope and method

I read Anthropic's public documentation on 2026-10-28 (Sources, 23 fetches): Agent Skills (overview, best practices, the engineering post, anthropics/skills), Claude Code skills, hooks, memory and rules, subagents, permissions, the extension overview, and the plugin pages (manifest, components, loading, install, marketplace reference, hosting, security), and anthropics/claude-plugins-official. I did not fetch anthropics/claude-code, or agentskills.io, which anthropics/skills names as the home of the specification and which is outside the listed sources. In the corpus I read CUSTODIAN.md, the reading copies of AGENT, STND.INSTR (identical to harness/rendered/agent-instructions.md), STND.PROJ, STND.DFLT, STND.CREW, STND.HARN, and STND.DOCS, the scope and agent passages of STND.WFLOW, and harness/README.md. I also ran `show` on PRIME.11, GOV.11, .13, .24, .36, .38, .39, .48 to .50, INTPR.5, REPRO.11, STND.CLASS.10, and LEX terms. Agnosticism holds: no provision names a vendor, and none blocks the packaging below.

## Plugin recommendations

**Layout.** Make `harness/` the plugin root and the repository root its marketplace. `harness/.claude-plugin/plugin.json`: `{"name": "governance", "description": "Read-only access to the governance corpus and its query harness", "author": {"name": "Brian J. McDermott"}, "keywords": ["governance"]}`. `name` is the only required field. Omit `version`: "Setting it keeps users on that version until you change it." Without it, a relative-path plugin takes "The commit SHA of the installed directory". `.claude-plugin/marketplace.json` at the root holds the required `name`, `owner` (`name` required), and `plugins`, with one entry: `{"name": "governance", "source": "./harness", "description": "..."}`. Move every reading copy inside `harness/` (AD8).

**References.** Skill bodies cite `${CLAUDE_PLUGIN_ROOT}/governance/...` and run `PYTHONPATH="${CLAUDE_PLUGIN_ROOT}" python3 -B -m govharness find "${CLAUDE_PLUGIN_ROOT}/governance" WORDS`. Reading the plain files is the fallback (GOV.38). The variables "aren't present in the environment of commands Claude runs through the Bash tool", so they go in the Markdown body. Nothing is written under the root, which "changes when the plugin updates".

**Skills** go in `skills/<name>/SKILL.md`. Keep `name` to 64 or fewer lowercase characters, and write `description` in the third person, in 1,024 or fewer characters, saying what the skill does and when to use it. Keep the body under 500 lines, with references one level deep. Bodies point to provisions, quote none (GOV.31, GOV.39), and direct nothing on their own (AD1).

1. `consulting-governance`: "Retrieves the provisions that govern an action or question from the governance corpus and reads each in full before relying on it. Use before a destructive action, a remote write, a network retrieval, a delegation, or a release, and when a reserved action, an authorization, a record, a referral, or the consequence class is in question." An optional `allowed-tools` covers `show`, `find`, and `context` only; confirm its match in a session.
2. `orienting-to-governance`: "Finds where the project keeps its governance records, the consequence class recorded, and the authorizations in force, from the project constitution or the default locations. Use before the first change to the work in a session, after compaction, and when the class or an authorization is in question." This serves AGENT.17. Where no class is recorded, the skill says so once and continues every line of work that does not need it (AGENT.15).
3. `classifying-work`, with `disable-model-invocation: true` and `argument-hint: [CSQ0-CSQ4]`: "Drafts the classification record, or its revision, for the human owner to adopt." It writes nothing (GOV.49).

**Commands:** none ("the older format"). **Agents:** at most one, `governance-reader`, with `tools: Read, Grep, Glob` and `skills: [consulting-governance]`. It returns identifiers and verbatim text.

**Hooks:** none. A project's own `AGENTS.md`, which Claude Code reads when no `CLAUDE.md` exists, carries a one-line pointer to the governance without code. If a hook is wanted anyway, ship it as a separate opt-in plugin with `"dependencies": ["governance"]` and one `SessionStart` hook, `"matcher": "startup|clear|compact"`, in exec form: `{"type": "command", "command": "cat", "args": ["${CLAUDE_PLUGIN_ROOT}/session-context.md"]}`. The file states facts in under 10,000 characters. At `SessionStart`, exit 2 only shows stderr to the user, so this hook is never able to block.

**Scopes.** Offer project scope (`.claude/settings.json`, committed) for an adopting project, local scope (`.claude/settings.local.json`) for a trial, and user scope for the custodian. A project pins a revision in its committed settings:

```json
{"extraKnownMarketplaces": {"governance-harness": {"source": {"source": "git", "url": "<repository URL>", "ref": "ledger-202"}}},
 "enabledPlugins": {"governance@governance-harness": true}}
```

The custodian tags each ratified ledger head. For an exact commit, use a `settings` source (`name`, `owner`, `plugins`) whose item has a `git-subdir` source with `url`, `path` `"harness"`, and `sha`, "a full 40-character lowercase commit SHA". A `directory` marketplace loads "in place" and pins nothing. Leave auto-update off (the default). The pin also gives REPRO.11 its "instruction revision".

**Raising the class.** The class lives in the project's records, not in the plugin. The human owner records a new class, which `/governance:classifying-work` drafts. The next session or compaction rereads it; nothing is reinstalled. Found the signer register before recording CSQ1 or CSQ0 (AD2).

**Keep out** `research/`, `review-records/`, `tools/`, `docs/`, `CUSTODIAN.md`, and `OPEN-ITEMS.md`. Also keep out:
- blocking hooks;
- permission rules and the `agent` setting, which replaces the main thread's prompt (a plugin's `settings.json` honors only `agent` and `subagentStatusLine`);
- MCP servers, `bin/`, monitors, and `userConfig`;
- a root `CLAUDE.md`, which "isn't loaded";
- the harness's write commands in any skill;
- names beginning `claude-`.

## Systemic observations

The corpus and Anthropic's practice agree on the substance. Instruction files are "context, not enforced configuration", and STND.DFLT.22 already forbids relying on a configuration that the agent is able to alter. Fetched content "might contain malicious instructions", which PRIME.11 and STND.CREW.23 already treat as data. Subagents start fresh and need a brief, as AGENT.11 has. Both prefer timeless text: "Avoid time-sensitive information." STND.DOCS keeps "instructions and briefs addressed to agents" out of work documentation, so AGENTS.md and SKILL.md files raise no conflict, and STND.WFLOW governs no agent.

The friction follows one pattern. The corpus assumes that standing instructions, owner records, and notes reach the agent through things the human owner writes by hand: ledger lines that name the owner, and a workspace at a fixed path. Agent environments deliver them through channels the environment keeps: instruction files, installed extensions, and memory stores. AD1, AD3, and AD4 each ask the corpus to recognize such a channel, and they keep the stronger trust tests (unalterable, signed) for CSQ1 and CSQ0. That gives the default CSQ3 or CSQ4 experience no human round trip beyond one statement of the class, and it keeps the assured-work machinery opt-in. Today that opt-in is also a trap (AD2): under the defaults, promotion works up to CSQ2.

Progressive disclosure in skills mirrors the harness's design: retrieval by identifier and by budget (STND.HARN.1 to STND.HARN.3) and full text before reliance (GOV.39). GOV.31 and the context budget both push the plugin toward pointers rather than summaries. A skill that paraphrased provisions would restate the corpus, go stale at the next amendment, and become a second source of instruction (AD1).
