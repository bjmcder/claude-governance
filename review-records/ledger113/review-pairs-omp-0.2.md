# STND.HARN.28 pair review: STND.OMP draft 0.2 (2026-10-24)

Scope: the 144 pairs of `pairs-OMP-0.2-delta.md` (numbered as in `pairs-OMP-0.2.md`), which come from the new provisions STND.OMP.12, 16, 22, 27, and 33; the new provision STND.OMP.24, which produced no listed pair; and the provisions of 0.1 whose text changed in 0.2 (STND.OMP.1, 7, 8, 10, 11, 15, 19, 21, 23, 26, 28, 31 in 0.2 numbering). Read against the rehearsed copy `/tmp/rehearsal-mh5rgys1/governance` and the reading copy `omp-0.2-draft.md`. The remaining pairs of the 477 of 0.2 are the pairs of 0.1 and keep the verdicts of `review-pairs-omp.md`, except where Section "Changed provisions" says otherwise.

## Method

- Followed `review-pairs-omp.md`: the same tests, the same table columns, the same grouping rule (pairs on unrelated subjects that share only a broad basis in one row with the pair numbers; every pair on the same subject with its own row). Conflict: can one provision be met only by failing the other, or do both answer one question differently as written. Unowned: do the two address one matter that no shared-matters table gives to an owner. The earlier precedent stands: a matter whose only profile provisions are in one profile, with an LVL2 standard on the other side, is not counted as unowned unless the standard adds a matter the profile does not hold. Every OMP provision is a default (SHOULD); a default that adds to a binding profile provision is not a conflict.
- Read STND.HARN.28 and GOV.31; the draft 0.2 reading copy in full and compared its 33 provisions with the files `STND/OMP/1.md` to `33.md` of the rehearsed copy (title, mode, instantiated provisions, body: no difference, checked by script); `dispositions-omp.md`; and the research notes `research/openmp-notes/r2`, `r3` and `r4` for the facts on which the new provisions rest.
- Read in full: STND.CONC.1-29 and its Notes; HW.2 (shared-matters table), HW.3-HW.20, HW.CPU.3, HW.GPU.1-4; STND.CODE.7-9; STND.CXX.20-23; STND.VVUQ.1, .2, .82; PRIME.4; SIMPL.4 and SIMPL.6; and the 67 distinct other provisions of the delta list: AGENT.12, AGENT.39, HDES.11, the HW provisions and NUMER.5, 11, 12, 17 read in full; the others (CPS, the other HDES, HDES.ASIC and HDES.FPGA provisions, HW.ASIC.4, HW.EMBED.3-4, HW.FPGA.4, HW.QPU.5-7, ML.4-5, the remaining NUMER provisions) read in their opening sentences, which state the subject.
- Shared-matters tables: HW.2 and HW.GPU.2 give the hardware contract of a path (HW.4-12, HW.GPU.3), the boundary contract between execution paths (HW.13, HW.14), agreement between alternative paths (HW.15-19), and budgets (HW.20, HW.21) to HW, and precision, approximation and tolerance basis to NUMER. No row concerns cancellation, signal handlers, atomics, device numbers, or test settings. STND.CONC and STND.OMP are LVL2 standards and have no table; their division is stated in the Purpose of each (STND.OMP adds to STND.CONC only what the directive model makes necessary).
- Completeness of the list: I did not rerun the harness command. I checked the list against the 0.1 list: the 336 pairs of `pairs-OMP.md`, with the provision numbers mapped by `dispositions-omp.md`, are all in the 477 pairs of 0.2 except three (0.1 pairs 29, 30 and 31, STND.OMP.19 of 0.1 with AGENT.39, HDES.11 and HW.11, which rested on the signal-handler sentence that is now STND.OMP.22 and whose basis DSGN.15 STND.OMP.21 no longer cites); 477 - 336 + 3 = 144 pairs are new, and they are the 144 of the delta file. The delta file is consistent with the front matter of the five provisions (OMP.12 and OMP.22 cite DSGN.15; OMP.16 DSGN.15 and VV.1; OMP.27 DSGN.5, DSGN.14, HW.13; OMP.33 VV.1; OMP.24 cites DSGN.1, DSGN.14 and HW.13, which no other listed provision shares, so it has no pair, as OMP.19, OMP.20 and OMP.21 have none).
- Each pair of the delta file is in exactly one row below (checked by script: 144 numbers, none missing, none repeated, 43 rows).

## Observations (not conflicts, not unowned)

1. Conflict, narrow: OMP.12 sentence 1 against OMP.22 (and against CXX.23 for a C++ handler). See "Within the standard".
2. OMP.16 sentence 1 and sentence 2: "each run of that code" against "tests run it with cancellation disabled" read as a contradiction unless the tests are excepted. Sentence 2 also does not say what the disabled run must show. PRIME.4 requires that it not continue silently, so it should show that the code finds the disabled state (a routine reports it) and halts or reports.
3. OMP.16 sentence 1 applies where code "answers a failure" by a cancel construct. CONC.10 (cancellation as the bound of a wait), CONC.12 (the parent cancels on early exit) and CONC.13 use cancellation for other reasons, and a cancel that is ignored is the same silent no-op. Suggest "where code relies on a cancel construct". The provision also does not ask that long-running tasks carry a cancellation point (CONC.13 sentence 3) or that a library state in its contract that the run must enable cancellation (it cannot enable it itself, CONC.17, OMP.19).
4. OMP.3 lists the control variables of the record and omits the cancellation setting (which OMP.16 now relies on) and the run-time schedule (OMP.33). HW.3 binds beyond the list. Suggest adding both, and the default device.
5. OMP.33 uses "schedule" for the assignment of iterations (and "binding" for placement), where CONC.26 uses it for interleavings with the number run stated. "Each run-time schedule ... that the runs of the work use" is vacuous for a loop with a fixed schedule clause, and a binding that the test machine lacks cannot be exercised; the provision says nothing of either. For a library, "the runs of the work" are the caller's, which the library's tests cannot know.
6. OMP.24 sentence 1 exempts "the default device", but the default device is itself set by the environment and can be a number that does not conform, with the silent behavior that the Notes describe. Sentence 2 does not ask for the check of the null return of an allocation (r3), which STND.CODE.7, PRIME.4 and HW.8 require anyway, and "exactly once" is not "after the last use" (CONC.5). Sentence 2 is partly a restatement of DSGN.14.
7. OMP.28 sentence 1 cites HW.4 but no longer states anything about the hardware contract. Either drop HW.4 from the front matter (the Notes cite it) or keep a clause. "In the same requires directive" cannot be literal, since each compilation unit has its own directive; "with the same requirements" is meant.
8. OMP.21 is silent on the cancel construct; OMP.16 now asks for it. Say in the provision or the Notes that a cancel construct, which sends control to the end of the canceled region, is an exit through the end.
9. OMP.7 sentence 3 forbids relying on a threadprivate value across any task scheduling point; the Notes qualify it to a point "at which another task is able to run on its thread". A barrier is a task scheduling point, and with no other task to run (a team of implicit tasks) the value persists. The provision should carry the qualification. Sentence 3 overlaps CONC.16 and adds the tied-task case; I treat it as the OpenMP form.
10. OMP.1: "no later revision of the specification marks as deprecated" does not say whether drafts of a revision count; the Notes mention the final public draft of 6.1.
11. OMP.12 sentence 1 names the atomic construct of OpenMP; an atomic of the base language on the same location is not that construct and the specification, as r2 reports it, does not say they interoperate. That is why the fix for the conflict above sends handler-shared locations to language atomics only.
12. Under mandatory offload a false if clause still runs the region on the host (Notes), and OMP.23 sentence 1 asks no report of it. HW.19, HW.9 and the host-path test of sentence 2 cover it; an adopter should know the report is not part of the first alternative.
13. OMP.26 sentence 3: the release of the last mapping copies back only for a mapping type with from or tofrom; the sentence reads as if any release did.
14. Gaps of 0.1 that remain by design: no route for the failure of a task or target region to reach its parent (CONC.1, CONC.2, HW.GPU.3 bind). HW.3, HW.CPU.4, HW.CPU.5, HW.GPU.4 are still in no row of a table; HW is the only profile addressing them, so they are not counted as unowned.
15. The 0.1 observation "OMP.19 silent on cancel" is closed by OMP.16 only in part (Observation 8); the observation on OMP.3 start-of-run values is answered by the Notes of 0.2, which cite HW.3 for a change during the run.

## Summary for the adopter

Conflicting pairs: none of the 144 listed pairs conflicts. One narrow conflict outside the list, between two provisions of this standard: STND.OMP.12 sentence 1 (an access able to run in parallel with an atomic construct on the same location SHOULD be an atomic construct) against STND.OMP.22 (a signal handler SHOULD NOT contain an OpenMP directive). A signal handler is a concurrent task and shares state with the code it interrupts (HW.11, STND.CXX.23 for C++); an atomic construct cannot be used in it, so the two answer differently how the handler accesses a location that threads access atomically. Suggested fix: except locations shared with a signal handler from OMP.12 sentence 1 and have them accessed by atomic operations of the base language only. The conflict of draft 0.1 (OMP.14 sentence 2 against STND.VVUQ.82) is closed by STND.OMP.15.

Matters left without an owning profile: none. The new provisions touch the boundary contract (HW.13, HW.14; owner HW), completion and faults (HW.GPU.3, HW.8; owner HW), and tolerance basis (NUMER); cancellation, signal handlers, atomics, and test schedules are shared only with STND.CONC, STND.CXX and STND.CODE, which are LVL2 standards that the Purpose of STND.OMP defers to, as in the review of 0.1.

Pairs covered: 144 of 144 listed pairs, each once, in 43 rows; the new provision STND.OMP.24, which has no listed pair, by hand; the twelve changed provisions of 0.1 and the three renamed ones by hand, with all of them keeping their 0.1 verdict (the HW.4 and HW.13 rows of OMP.28 with a changed reason).
