## Findings and observations

Ranked Defect (a broken rule or a factual error), Should-fix (a gap or ambiguity that makes a provision or a Note wrong or unusable in a case the standard covers), Optional (a preference or tidying). Items 16 to 21 are observations that need no change of the draft; they are for the reconciliation. None of the findings is a conflict between two provisions as written; item 4 and item 6 come nearest.

### Defect

1. **Obligations stated in the indicative in the Notes.** The brief (Documentation) allows Notes no obligations in the indicative. (a) The last paragraph of the Notes, outside any named paragraph: "Existing Fortran source enters the legacy list at the change that adopts this standard, and meets the provisions that the list names for it by modernizing changes." This states a duty; it repeats the "Legacy source" paragraph ("existing source enters it at the change that adopts this standard, and leaves it by modernizing changes"); and it contradicts STND.FTN.35, which admits a file to stay with "the reason that each stays", and the Term Legacy list. (b) "Under STND.VVUQ.82 and STND.VVUQ.83, a difference within the declared variation is no defect, and an agent does not change the work only to remove it" restates STND.VVUQ.83 as an indicative duty. (c) For STND.FTN.19, "a negative answer is a precondition violation, answered as STND.FTN.31 requires", states in the Notes a response that the body does not carry. Fix: delete the last paragraph (the Term and STND.FTN.35 hold the rule; if a transition rule is wanted, put it in the body of STND.FTN.35 as "Source of the work at the adoption of this standard SHOULD enter the legacy list at the change that adopts it"); write (b) as "STND.VVUQ.83 keeps an agent from changing the work only to remove such a difference"; for (c) either end the body of STND.FTN.19 with "and SHOULD respond to a negative answer as STND.FTN.31 requires (SIMPL.6, HW.5)", which asks nothing beyond PRIME.4, or delete the clause from the Notes.
2. **Factual error: the direction for the latest edition "concerns C++ alone".** The first paragraph of the Notes says that no provision prefers the newest revision, "as STND.CXX.2 does for C++ on a direction that concerns C++ alone". The Notes of STND.JL record a direction of the same kind for Julia ("use the latest version available", and the ruling of 2026-10-23 "Don't pin the version or tools; use the latest"), which STND.JL.1 follows, and STND.DEPS.3 asks the most recent stable revision of a dependency. I found no direction for Fortran in `HANDOFF.md` or in the Notes read; the choice not to prefer the newest revision is then the draft's own and may be sound (agnostic of revision, HANDOFF line 42), but the reason given is wrong. Fix: "as STND.CXX.2 and STND.JL.1 do on the custodian's directions for C++ and for Julia; the files record none for Fortran", and ask the custodian for the Fortran answer (item 18).

### Should-fix

3. **STND.FTN.9 states one half of the rule of argument association.** The body asks that the value or allocation status of an entity associated with a dummy be changed only through that dummy. The Fortran standard (clause 15.5.2.14, which the Notes cite) has a second restriction, from my knowledge and not quoted in the research note (unverified here): where the value is changed through the dummy, the entity is referenced only through that dummy during the invocation. A procedure that changes a module variable through a dummy and reads the same variable by use association meets STND.FTN.9 as written and breaks the rule; the processor may keep the stale value, which is the hazard the Notes describe. Fix: add "and where code changes it through that dummy argument, it SHOULD reference it only through that dummy argument", with the exceptions of POINTER and TARGET kept; check the clause before adopting.
4. **STND.FTN.34 (halts by ERROR STOP).** (a) It reads as asking that Fortran code halt on a failure, while STND.FTN.31 offers four responses and CPS.4 with PRIME.13 asks the designed safe state of hardware that the code commands; "SHOULD halt on a failure by an ERROR STOP statement" answers differently as written the question that STND.FTN.31 answers. Write "Where Fortran code halts on a failure, other than by the abort facility of MPI under STND.MPI.6, it SHOULD halt by an ERROR STOP statement whose stop code or message states the diagnosis". (b) ERROR STOP is a facility of the 2008 revision (the research note lists it under Fortran 2008), and the standard covers every revision; see item 5. (c) ERROR STOP ends every image of the Fortran program; each process of an MPI execution is a separate program, so by my reading (unverified) the language does not reach the other processes. MPI.6 (binding) asks that the other processes halt or be notified, and MPI.7 asks the contract to say whether the end of one process ends the others. The exception for the abort facility is right, but the Notes should say that ERROR STOP alone meets STND.MPI.6 only where the contract of MPI.7 says so. (d) Where a failure is detected in a pure procedure or a DO CONCURRENT construct, whether ERROR STOP is permitted depends on the revision (unverified); the response of STND.FTN.31 that returns the condition remains.
5. **Provisions presuppose a revision, while the standard covers "every revision of the Fortran standard, classic and modern".** Only STND.FTN.21 is conditioned ("Where the revision in force provides locality specifiers"). The others name facilities that older revisions lack, from my knowledge of the revisions and not from the draft's source except where stated: STND.FTN.5 and STND.FTN.6 (explicit interfaces, modules, IMPLICIT NONE: 1990), STND.FTN.7 (INTENT: 1990; on a pointer dummy later), STND.FTN.15 (SELECTED_REAL_KIND: 1990), STND.FTN.18 to STND.FTN.20 (the IEEE intrinsic modules: 2003), STND.FTN.29 (BIND and ISO_C_BINDING: 2003), STND.FTN.27 (NEWUNIT=: 2008), STND.FTN.34 (ERROR STOP: 2008, per the research note). A file whose revision in force is 1977 cannot meet them except by an extension, and the legacy list of STND.FTN.35 does not name STND.FTN.18 to STND.FTN.20, STND.FTN.29, or STND.FTN.34. Fix: one sentence in the Purpose or the Terms: "A provision that names a facility applies to a source file whose revision in force provides that facility", or add the condition to each provision as STND.FTN.21 has it; and say whether a file at an earlier revision is expected to raise it.
6. **STND.FTN.3 and STND.FTN.14 meet in the change that consolidates a common block.** STND.FTN.14 asks one source text for each common block, included by each scoping unit. Making that text moves or writes a COMMON statement, which is an obsolescent form; the Notes count a statement that a change alters as added, so STND.FTN.3 (SHOULD NOT add an obsolescent form) asks that the COMMON statement not be written. The two answer differently what the change to a legacy common block is to look like. Both are defaults, so this is not a conflict, but a project that follows one fails the other. Fix: in STND.FTN.3 let the statement that a change makes in order to meet STND.FTN.14 for a block that already exists be an exception ("Other than the fixed source form of a file that the legacy list holds and a COMMON statement that moves a declaration of an existing block under STND.FTN.14"), or say in the Notes of STND.FTN.14 that replacing the block by module variables (the first choice, row 4 of the table of STND.FTN.37) is the way out.
7. **Second sentence of STND.FTN.33 is narrower than the sentence the Notes call its model.** The Notes say it "is the Fortran form of the second sentence of STND.CXX.18". STND.CXX.18 names CPS.5, CPS.9 and STND.CODE.6 ("that STND.CODE.6, CPS.5, or CPS.9 requires"), and its first sentence also asks the checks of CPS.5 and CPS.9 to run in every build. STND.FTN.33 names STND.CODE.6 only. A Fortran file that holds the finite-value check of a command limit (CPS.5) is then not covered by the second sentence, though CPS.5 itself still binds. Fix, either way at no new cost (the Notes of STND.CXX argue the same floor): name CPS.5 and CPS.9 in the sentence and add them to the instantiation, or say in the Notes that the omission is deliberate because a check that CPS.5 or CPS.9 requires cannot be removed without failing them.
8. **"Untrusted data" is undefined in STND.FTN; STND.PY and STND.JL define it with a reach the custodian ruled on.** STND.PY and STND.JL have a Term Untrusted input: the arguments of each public function, unless the threat model of the project records otherwise; the Notes of both record the custodian's ruling of 2026-10-23 (PRIN.10) that this reach raises no floor. STND.CODE has no such Term, STND.CXX none, and the Notes of STND.FTN.33 say the reach "is that of STND.CODE.6, which this standard does not widen". For a Fortran program that means an index received as a dummy argument of a public module procedure is untrusted in Python and Julia and undecided in Fortran, while STND.FTN.33 binds at every class. The draft does not claim a ruling the custodian has not made. This is a decision for the custodian (the reach of the Term for Fortran and C++); the cost of adding a Term is wording. Until then, say in the Notes that the question is open, so that a reviewer does not read "does not widen" as a ruling.
9. **Scope of STND.FTN.18 and STND.FTN.40 on a library, a thread, an image, and a device.** STND.FTN.18 asks "each program" to set the halting modes "at its start". (a) A Fortran library called from C, C++, Python, or Julia has no program start; if it sets the modes at entry it changes the state of its caller, which HW.CPU.3 (binding, third sentence) asks restored before control returns to code the contract does not cover, and which CONC.17 asks a library to leave unchanged; the Notes say the halting state per thread is unverified. (b) HW.CPU.3 asks the control state confirmed in each thread or pool that performs the operations; a mode set in the main program at start need not be in force in a thread started later (unverified for Fortran processors), and STND.OMP.30 sends the code to rely on an environment only where it is set. (c) A DO CONCURRENT construct or target region that runs on an accelerator is not under the host mode (STND.OFFLD.14), and a "run that halts at the first of them and reports its location" (STND.FTN.40) is not available there. Fix: say "each main program" in STND.FTN.18 and put in the Notes the library case (set and restore under HW.CPU.3, or leave unset) and the thread and device cases (confirm in the scope that computes, as STND.OMP.30 and STND.OFFLD.14 say); confine STND.FTN.40 to the host or cite STND.OFFLD.14.
10. **STND.FTN.33 (binding) and an assumed-size dummy.** The first sentence asks a test "against the bounds of the array or the length of the string". An assumed-size dummy has no extent in its last dimension (the Notes on STND.FTN.8 say so), and STND.FTN.8 admits the form at an interface that a library fixes. For a subscript of such a dummy that comes from untrusted data, the binding provision cannot be met against bounds that the callee does not have unless the extent arrives by another argument or by a convention. Fix: add to the Notes of STND.FTN.33 that the bound is the extent the caller passes, and that where the interface fixed by a library passes none, the work wraps the call in a procedure that takes the extent; or "the bounds of the array or the extent that the caller states".

### Optional

11. **STND.FTN.12 and default initialization.** "Each local variable ... that its declaration or a DATA statement initializes" can be read to include a local of a derived type with default initialization of a component, which does not imply SAVE (to my knowledge, unverified) and is initialized at each entry; SAVE added on that reading would change behavior. Say "by an initialization in its declaration, or by a DATA statement, other than default initialization of a component".
12. **Conditions on the means.** STND.FTN.38 first sentence asks the static checks to include reports of an interface without explicit interface, a disagreement across source files, and an implicitly typed name; the first sentence of STND.FTN.39 asks run-time checks of each subscript, substring, and association status; only the second sentence of STND.FTN.39 says "where a processor of the work provides". DSGN.3 asks mechanical checking "wherever the means allows". The Notes say that a check the Fortran standard does not require may be absent from a processor. Add the same condition to the two first sentences. In STND.FTN.39 second sentence, "a value that shows in results" should be one fixed value on every run (CODE.9).
13. **Terms.** (a) Processor is the compiler with its run-time library. In the corpus "processor" otherwise means hardware (HW.CPU "general-purpose processor", CONC.18 "processor affinity"), and in the Fortran standard it includes the computing system, which the Notes admit. A reader of STND.FTN.2 ("the target instruction set" of "its processor") meets both. Use "compiler" with its library, as STND.CXX does, or "Fortran processor". (b) Legacy list: "each source file of Fortran that does not meet this standard" is wider than STND.FTN.35, which lists the forms the check of STND.FTN.1 reports and nine provisions; write "that does not meet a provision that STND.FTN.35 lists".
14. **Wording of the Notes.** (a) "STND.MPI.16 keeps a buffer allocated only where code sees it" is inexact: MPI.16 asks the buffer to stay allocated and unwritten until completion, which a temporary copy released at the return of the call does not do. (b) The threadprivate common block "named as a block (STND.FTN.22)": the body of STND.FTN.22 covers clauses other than shared, not the threadprivate directive. (c) The Notes narrate the drafter's reading ("the note did not read", "the note found no statement", "by a search of the text that it calls inference"); the sources and the marks `unverified` are enough, and the first needs no account of what was read. (d) "The custodian's order of standards also lists a standard for builds, which is able to take STND.FTN.4 once it is adopted" looks ahead; a Note that says STND.FTN.4 stays until another standard holds it would do.
15. **Table of STND.FTN.37.** Two rows would help: a loop moved to threads or images changes the floating-point control state under which its operations run (HW.CPU.3, item 9), and a change of an option that sets the default kind (STND.FTN.2) changes the kind of every entity declared without one, so every result. The second is the case of row 1 reached by a different route. Also say, in the Notes of STND.FTN.35, that a file in the legacy list for STND.FTN.15 or STND.FTN.16 still needs the options of STND.FTN.2 for NUMER.5 to be true.

### Observations

16. **The return of a condition against HW.8.** STND.FTN.31, like STND.CXX.16, STND.PY.22, and STND.JL.15, adds the return of the condition to the responses that PRIME.4 and HW.8 list. For exhaustion of a capacity of the hardware (a failed ALLOCATE) and for an error in the completion status of offloaded work (HW.GPU.3), the response falls to the caller, and the path as a whole still halts, degrades visibly, or enters the safe state before a result is reported. The three languages have the same wording; FTN adds "in a status argument". I did not read the earlier reviews of those standards. Stated so that the reconciliation sees the four wordings side by side.
17. **HW.3 is in no row of HW.2, HW.CPU.4, HW.CPU.5, and HW.GPU.4 in none of theirs** (as in the reviews of STND.OMP and STND.OFFLD). STND.FTN.1, STND.FTN.2, STND.FTN.15, and STND.FTN.23 add items to the record that HW.3 asks (the revision, the options, the kinds, the Fortran binding of MPI). HW is the only profile that addresses the matter and STND.FTN adds items, so I did not count it as unowned.
18. **Differences between the language standards for the reconciliation.** (a) Revision in force: CXX newest edition with a binding rule for agents (CXX.3), Julia the latest stable minor, Python the oldest declared release with checks at the oldest and the newest, Fortran neither; and whether the revision of a language is a "dependency" under DEPS.3 and DEPS.4 is stated nowhere (CXX.2 adds the edition to the review of DEPS.4 by its own text). (b) Binding rules for agents about the language: PY.4 (annotations) and CXX.3 (edition); none in JL and none in FTN; STND.FTN.5 and STND.FTN.7 are defaults. (c) A run of the tests in the production configuration: JL.34 asks it; CXX.27 asks the library checks kept in production builds; STND.FTN.39 asks only the checked build. (d) The wording of the list of responses (item 16) and the riders on visible degradation (PY.22, JL.15). (e) The Term Untrusted input (item 8). (f) The second sentence of FTN.33 against CXX.18 (item 7). (g) FTN.35 follows PY.6; CXX and JL have no list of exempted code.
19. **Matters that other language standards answer and STND.FTN does not.** Each is a default or a Note in the other languages and none is a conflict. (a) A comparison within a tolerance written "by an expression" (PY.20, JL.21): the Notes say Fortran has no intrinsic comparison, but the provisions of the other two cover the expression, which Fortran code writes. (b) Random numbers (PY.15 to PY.18, JL.22 to JL.25, CONC.23): the intrinsic generator of Fortran has a state that the standard leaves to the processor, and a stream per image or per thread is the case of CONC.23; no provision. (c) Directives and attributes that assert a condition (CXX.24, JL.18, PY.31): vector and independence directives and CONTIGUOUS. (d) Suppressed reports of a listed condition (PY.30): a program that turns halting off and never reads the flags continues silently past an invalid operation; PRIME.4 binds, no Fortran provision says so. (e) Ownership of memory that crosses to C (CXX.20): C_F_POINTER on memory that C allocates, or `free` on memory that Fortran allocated; STND.FTN.10 covers only the temporary copy. (f) Input and output beyond unit numbers and record order: processor-dependent record markers of unformatted sequential files, the digits that a formatted write of a real keeps (a list-directed write of a double may lose digits that the result needs, NUMER.5), and list-directed input; STND.MPI.22 covers files of MPI only. (g) A command started without waiting (CONC.1, hand row). These are from my knowledge of the language, not from the research note; unverified.
20. **Legacy list and incorporated external code.** The Notes send external Fortran code to STND.DEPS.11, which keeps it apart, and STND.FTN.35 lets a change that incorporates external code add entries. External code kept apart still fails the check of STND.FTN.1 unless it is in the list, so each such file needs an entry with the reason that it stays (origin). That is workable; the Notes could say that the entry cites the record of DEPS.11.
21. **Label and onsets.** The reading copy says revision 1.0, adopted in ledger entry 118; this is the draft 0.1 and the rehearsed ledger holds placeholder rationales (the same note as in the reviews of STND.OMP and STND.OFFLD). The mnemonic FTN is at edit distance 3 or more from every mnemonic of STND (nearest: CONC, CXX, DFLT, HARN, JL, MPI). The "Class onset" paragraph agrees with STND.CLASS.10: the DSGN.4 parts at CSQ2 (STND.FTN.8, the first sentence of STND.FTN.14, STND.FTN.26, the second sentence of STND.FTN.29), the DSGN.15 parts at CSQ3 on the stated reasoning, and STND.FTN.17 at CSQ3. Two small points: the paragraph lists the second sentence of STND.FTN.35 among the "mechanical checks under DSGN.3", but that sentence forbids adding entries (as STND.PY.6 does) and checks nothing; and STND.FTN.1 is listed whole although its first sentence asks a statement, not a check. Both are at CSQ3 either way.
