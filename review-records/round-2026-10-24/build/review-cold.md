The imported terms exist where the Terms section says: Repository configuration and Execution setting in STND.CODE; Fetched component, Integrity digest, Dependency record in STND.DEPS; Accelerator, Hardware model, Runtime library in HW; Device code in STND.OFFLD; Workflow and Result in the Lexicon (LEX/workflow.md, result.md).

## Defects
1. **STND.BUILD.3 refers to variation that nothing can declare.** It allows "the variation that the build record declares", but the build record's "Declared variation" row covers only outputs that "differ between clean builds". A difference between an incremental or parallel build and a clean one, for example from a tool that embeds a run identifier (the Notes' own example), has no place to be declared. The Notes say such variation "is not a defect"; the provision does not carry that. Fix: "within the variation that REPRO.3 asks to be declared (REPRO.3)", and widen the record row to "Each output that differs between builds from the same declared inputs, whatever the kind of build, with its source". STND.BUILD.19 sentence 2 then needs "clean builds" only for the comparison it names.

## Should-fix
1. **STND.BUILD.12 sentence 2 does not rest on INTPR.10, so its CSQ2 onset is unsupported.** The sentence asks the build description to report a warning without failing; it asks no documentation of a limit of validity, which is the CLASS.10 row. The Notes say INTPR.10 "has documented and reported", which the provision does not ask. Fix: either (a) cite SIMPL.6 and place the sentence at CSQ3 with the rest, or (b) add what INTPR.10 needs: "and the release notes SHOULD state the toolchains on which the checks ran". Choose (a) unless the custodian wants the stated-toolchain duty. The sentence is also not operable as written: a build description cannot know that "the checks of the release did not run" on this toolchain. Fix: "A build from a release archive SHOULD NOT fail on a warning under a toolchain other than those on which the checks of the release ran". Drop "by default" (double hedge with SHOULD).
2. **Onset paragraph misses three CLASS.10 rows.** (a) STND.BUILD.21 (build scripts "reviewed as code of the work") is REPRO.10, versioning and review of each workflow, CSQ2, and the draft's own Terms make a build a workflow. (b) STND.BUILD.24 sentence 2 (rebuild what a result still relies on) and STND.BUILD.23/1 rest on QA.14, a mechanism that tracks dependencies between results, CSQ2; at minimum say why BUILD.24 does not. (c) STND.BUILD.10 sentence 1 states a contract for hardware (DSGN.5, CSQ2) if read as the build's contract with the accelerator. Fix: place BUILD.21 at CSQ2 on REPRO.10 (add it to Instantiates), and either place BUILD.24.2 at CSQ2 on QA.14 or add one clause saying it rests on no row because QA.13 propagates only after the fault is found. State the BUILD.10 decision either way. The listing of `.3, .5, .19, .20` as "comparisons of outputs with outputs, not an oracle" is sound; QA.9 (CSQ1 regeneration by another actor) is not what they ask, and the paragraph could say so in one clause.
3. **Overlap with STND.WFLOW is unmanaged.** The WFLOW draft (Purpose, second paragraph, and its Notes) says "A build system that runs the steps of a workflow is a workflow engine under this standard; the building of software belongs to the planned standard for builds". BUILD Terms in turn say a build is a workflow. Both are then true of a build, and these pairs overlap: BUILD.1 and WFLOW.1 (declared inputs; WFLOW.1 also names the environment); BUILD.23 and WFLOW.6 (reuse key over the content of inputs, code, parameters, environment); BUILD.3 and WFLOW.2 (variation under reuse); BUILD.25 and WFLOW.37 (provenance of step outputs); BUILD.14 and WFLOW.40 (clocks; different matter, no overlap, but cite); BUILD.7 and WFLOW.36 (state kept between runs, caches). BUILD.23 is the closest: it adds the identity of each tool and the environment variables read, which WFLOW.6 already lists as "the identity of its computational environment". Fix: add to the Purpose one sentence: "A build is a workflow, so STND.WFLOW applies to it; this standard adds what building makes necessary and cites that standard for the declaration of steps, the staleness rule, and provenance." In the Notes, give BUILD.23 as "the build form of STND.WFLOW.6" and reduce it to what is new (tools by revision, variables read). The WFLOW author should change "belongs to the planned standard for builds" to a citation of STND.BUILD; the lead should coalesce the two.
4. **STND.BUILD.12 sentence 1 restates STND.CXX.25 sentence 2** (warning on own source fails the change at a recorded set) in general terms, and the Notes list CXX.25 only as a language form. Likewise BUILD.11 sentence 1 restates CXX.4 sentence 3 and BUILD.13 overlaps CXX.26 (see overlaps). Not a defect (CXX predates; the Notes say the language standard holds the form), but the Notes should say which side cites which, and the lead should plan a CXX amendment that cites BUILD in place of repeating.
5. **STND.BUILD.13 "from which the work reports results" collides with STND.CXX.26.** CXX.26 runs the tests, whose verdicts are results, in a checking build. A reader may conclude that a test verdict cannot come from a checking build. Fix: "from which the work reports a measured, computed, or delivered result, a verdict of a test excepted", or define Reporting build in Terms (STND.CXX.27 already uses "reporting builds" undefined in the same sense).
6. **Notes narrate drafting and research (STND.DOCS).** "The custodian's directions of 2026-10-24 ask for…", "Most sources of the note were read as extracts that a retrieval tool wrote; the manuals of one Make implementation… were not read" describe the process, not the standard. The statement that unverified facts stay out of provisions is the only part that belongs, and it holds (see below). Fix: delete both sentences; keep one line: "Facts that the research note marks unverified do not appear in a provision."
7. **Fortran, Rust, and C fit mostly; two wordings do not.** (a) STND.BUILD.2 says "files that its source names". A Fortran `use` or a Rust `mod` or crate names a module or crate, not a file, and a Fortran compiler writes a module file that later units read. Fix: "files and units that its source names". Add module files to the Notes as a generated file read as an input (BUILD.4 applies). (b) The Compilation unit term is "source that one run reads … with the files it includes"; for Rust it is a crate, for Fortran a file with its modules. Add "as that compiler or translator defines it" is already there, so this holds; but BUILD.9 sentence 2 ("a tool that a later build step runs") should say "or that the compiler loads", which covers procedural macros and plug-ins compiled for the build host. (c) Build scripts of a language package manager that run code at build time (hand-written) are not "generated" and so escape BUILD.21; the Notes should say that BUILD.21 covers only generated scripts and a hand-written script falls under REPRO.10 and QA.7.
8. **Coverage gaps against b1.** b1 practice 21 asks that a mismatch between build targets and the installed device be found "at build or start"; BUILD.10 and .25 cover the build only. Add to the Notes that STND.OFFLD holds the start-time check, or cite it. b1 section 7 (hermetic isolation beyond network) has no provision; the Notes should say it is left out as not timeless across tools, if that is the decision. b1 practice 12 (the project states what the environment holds) is only in the Notes; REPRO.2 holds it, so cite it there.

## Optional
- BUILD.25's table has eleven rows at CSQ3. Allow the Declared variation, Kind of build, and Device code rows to read "where there is one" so a small project writes a short record.
- Term "Toolchain" differs from STND.CXX's "Toolchain matrix" (a set of compilers and library implementations for a unit). Add one sentence to Terms noting that a toolchain matrix lists toolchains.
- The Checking build term is partly circular with BUILD.13 sentence 1 (the build is defined by checks that reporting builds do not carry). Acceptable; the provision's content is the separate tree and name.
- Mnemonic questions are for the drafter's report, not checked here.

## Defaults and the floor
- No provision raises the floor. The two floor claims in Notes (DEPS.6 and PRIME.7) are right: STND.BUILD.7 adds only the timing of a fetch and a stop on a missing input.
- **STND.BUILD.20 under GUARD.17: keep it a default.** STND.THRT.2's row covers "fetched components that the work depends on". A release archive of the work's own is not a component that the work depends on, so no row of the threat model reaches it, and a binding provision would raise the floor (GOV.11) on a threat the model does not list. STND.DEPS.6 binds because the row exists. Option for the custodian, separate from this draft: add a protected row for the work's own releases to the threat model (STND.THRT.2), after which BUILD.20 sentence 2 could bind through GUARD.17. Recommend the draft state this in one Notes sentence, without asking for a ruling.
- The Notes' "Normative and informative" text and tighten-only: no provision loosens CODE, CXX, DEPS, or REPRO. BUILD.12 sentence 2 relaxes only a release build by third parties and conflicts with no sentence of CXX.25 once Should-fix 1 is applied.
