## Answer in brief

1. Every procedure that the work calls has an explicit interface at the call, from a module or an interface block. Without one the processor cannot compare the actual and dummy arguments, and a mismatch of type, kind, rank, or count is a program error that the standard does not require anything to diagnose (S1 15.4.2.2, 4.2; S6 for the measured frequency).
2. Every program unit declares every name. Implicit typing is switched off with `IMPLICIT NONE` (and its external form, which also requires every external procedure to be declared), so that a misspelled name is a compile-time error and not a new variable (S1 8.7, C.1).
3. No code relies on a variable that has no defined value. Locals, function results, `INTENT(OUT)` dummies, allocated allocatables, and `DO CONCURRENT` locals have an undefined value until assigned, and the standard asks no processor to detect the use (S1 4.2, 11.1.7.5).
4. Locals that carry an initializer are known to be static: explicit initialization implies `SAVE`, so such a variable keeps its value between calls, is shared by every thread and image-local call, and makes the procedure non-reentrant in effect. Code writes `SAVE` or uses assignment at entry, as the intent requires (S1 8.5.16, 8.6.7; S3 on "data initialized" locals).
5. Aliasing obeys the argument-association rule: while an entity is associated with a dummy argument, it is changed only through that dummy unless the dummy is a pointer or a target of the stated kinds, and two dummies that overlap are not both defined in the overlap. Code that violates this gives the processor leave to assume no overlap and the result is undefined in effect (S1 15.5.2.14 and its Note 2).
6. Array arguments that the code passes to explicit-shape or assumed-size dummies are shown to be contiguous or are given to assumed-shape dummies. Sequence association lets the shape differ, but only the element count must fit; a copy-in/copy-out is then allowed, and it breaks any code that relies on the callee seeing the caller's storage (S1 15.5.2.12, Notes 5 and 6 of 15.5.2.5).
7. Floating-point kinds are named with kind parameters chosen by `SELECTED_REAL_KIND` or the named kinds of the intrinsic modules, and every literal carries its kind. A real literal with no kind suffix is of default kind, whatever the variable it initializes, so `0.1` stored to a double precision variable has the default-kind rounding error (S1 7.4.3.3 and the paragraph on the literal, 16.10.2).
8. The kind of the result of an operation on two kinds with the same precision or range is processor dependent, so a result that depends on it is avoided by converting one operand explicitly (S1 10.1.9.3 and the processor-dependent list in Annex A).
9. Integer arithmetic that can leave the range of its kind is checked in the program, before the operation. The standard defines the integer model only over its range and prescribes no wrap, trap, or flag for an out-of-range result, so the result is whatever the processor does [inference; a statement of behavior in the text was not found].
10. Floating-point exceptions are observed, not assumed away. A program that must detect invalid, overflow, or divide-by-zero results reads the exception flags with the `IEEE_EXCEPTIONS` module or turns on halting, and states which; the initial halting mode is processor dependent, and halting "is not precise and may occur any time after the exception has occurred" (S1 17.6).
11. A test for NaN or an infinity, and the comparisons that must not signal, use the IEEE inquiry and comparison functions and not equality on an assumption. The relations `<`, `<=`, `>`, `>=` signal on a NaN, while `==` and `/=` are quiet (S1 C.1, 17.11).
12. Every `DO CONCURRENT` iteration is independent as the standard defines: no value defined in one iteration is referenced or defined in another, locality is stated for every variable (`DEFAULT(NONE)` makes that checkable), and the loop does not depend on the order of iteration, of output records, or of a reduction (S1 11.1.7.5, Annex A).
13. Code that relies on a particular order of floating-point combination in a `DO CONCURRENT` reduction, a coarray collective, an intrinsic reduction, or an OpenMP reduction fixes that order itself (S1 11.1.7.5; S3; STND.CONC.22).
14. Module variables and `SAVE`d locals are treated as shared state in every threaded or image-parallel context. In OpenMP they are shared unless named in a `threadprivate` directive, and a common block is made threadprivate as a whole or by member (S3 data-sharing rules for called routines).
15. A buffer that a nonblocking MPI call uses is declared `ASYNCHRONOUS` where it is accessed between the initiating call and the wait, and the program uses the MPI binding that the compiler and library support for that purpose. Where the library reports that it does not protect such buffers, the program passes contiguous whole arrays and calls the synchronization routine of the binding (S1 C.13 on asynchronous communication; S4 20.1.7, 20.1.8, 20.1.17).
16. Subarrays with strides are not given to a nonblocking, one-sided, or split-collective MPI call unless the library reports that it supports them; behavior is otherwise undefined (S4 20.1.12).
17. A C interface is declared once, with `BIND(C)` and the kinds of `ISO_C_BINDING`, and lengths and strides cross it in the types of the C side. `LOGICAL` is not interoperable with C `bool` by value of its representation, and the MPI chapter records the compiler-dependent representation of `.TRUE.` (S1 18; S4 20.1.5).
18. Input and output units are named constants or variables obtained at run time (`NEWUNIT=`, or the units of `ISO_FORTRAN_ENV`), never the literal numbers 5 and 6 and never a number chosen by hand. Records written by different `DO CONCURRENT` iterations, and by different images, are not ordered by the language (S1 12.5, 16.10.2, Annex A).
19. Legacy code is modernized by steps that each keep the results within a tolerance stated beforehand, verified by a regression run before and after each step; the steps that change a result by design (kind changes, summation order, removing an implicit `SAVE`) are separate steps, recorded as such.
20. The obsolescent and deleted forms in use are listed once for the work, with the reason each stays. A processor must be able to report the obsolescent forms and the deleted ones, so the list can come from the processor's own report (S1 4.2, B.1 to B.3).
21. A claim that code conforms to a revision names the revision and states what checked it. A conforming program may still behave differently on different processors, because the standard says that conformance "does not ensure that a program will execute consistently on all or any" processors (S1 4.2 para 5).

## 1. The revisions and what changed

Fortran was first standardized in 1966, and the standard "has since been revised six times (1978, 1991, 1997, 2004, 2010, 2018)"; the revision of 2023 is the seventh (S2 section 1). The first five alternated between minor (1978, 1997, 2010) and major (1991, 2004) revisions, and 2018 and 2023 were planned as minor, to let implementations keep up (S2). The informal names that S1 Table 4.3 gives are FORTRAN 66, FORTRAN 77, Fortran 90, 95, 2003, 2008, 2018, and 2023.

| Revision | Deletions and obsolescence (S1 Annex B, C) | Main additions |
|---|---|---|
| Fortran 77 | The base of most classic code: fixed form, implicit typing, `COMMON`, `EQUIVALENCE`, `ASSIGN`, assigned and computed `GO TO`, arithmetic `IF`, real `DO` variables, `PAUSE`, `H` edit descriptor (S1 B.1) | Block `IF`, `CHARACTER`, `SAVE` |
| Fortran 90 | Deleted at 90 or 95 from the 77 base: real and double precision `DO` variables, branching into an `END IF` from outside, `PAUSE`, `ASSIGN` and assigned `GO TO` and assigned formats, the `H` edit descriptor, vertical format control (S1 B.1) | Free form, modules, explicit interfaces, `INTENT`, `KIND`, derived types, allocatable arrays and pointers, array syntax, `SELECT CASE`, `CYCLE` and `EXIT`; 12 obsolescent forms named at this revision |
| Fortran 95 | | `FORALL`, `PURE`, `ELEMENTAL`, default initialization |
| Fortran 2003 | | Interoperability with C, `ASYNCHRONOUS`, `IEEE` modules, type extension, polymorphism, parameterized derived types, `ALLOCATE` of deferred length, `NEWUNIT` |
| Fortran 2008 | The arithmetic `IF` and the nonblock `DO` construct were deleted at the revision after this one (S1 B.2) | Coarrays, submodules, `DO CONCURRENT`, `CONTIGUOUS`, `BLOCK`, `ERROR STOP` |
| Fortran 2018 | Arithmetic `IF` and nonblock `DO` deleted; `COMMON`, `EQUIVALENCE`, block data, labeled `DO`, specific intrinsic names, and `FORALL` made obsolescent (S1 B.2, B.3, C.1) | Teams, events, atomics, collectives, failed images, assumed-rank and assumed-type, the C-descriptor interface, `IMPORT` forms, locality specifiers for `DO CONCURRENT`, a `GENERIC` statement |
| Fortran 2023 | None added to the lists (S2 section 10) | Conditional expressions, `typeof` and `classof`, enumeration types, `RANK` clause, integer arrays as subscripts, `REDUCE` locality for `DO CONCURRENT`, C-to-Fortran string procedures, longer lines, `NOTIFY` on coarray put, more `IEEE` functions (S1 C.1; S2) |

The assignment of features to the revisions of 77 to 2008 in the table is from S1 Annex B and the compatibility subclauses where a clause states it, and otherwise from my knowledge of the language [unverified against the earlier standards]; the rows for 2018 and 2023 come from S1 and S2. S1 4.4.1 states the policy: the revision "protects the users' investment in existing software by including all but six of the language elements of Fortran 90 that are not processor dependent", and a feature is made obsolescent first and deleted in a later revision. Six deleted features of Fortran 90 are those in S1 B.1, and two of Fortran 2008 in B.2.

Compatibility is stated per revision. A conforming program of an earlier revision that avoids the deleted features remains conforming (S1 4.3.3 to 4.3.8). The exceptions that matter for modernizing without changing results:

- A FORTRAN 77 program that initialized a named variable in a `DATA` statement without `SAVE` had a processor-dependent `SAVE` attribute; now the variable is saved (S1 4.3.8).
- A FORTRAN 77 processor could supply more precision from a default real constant that initialized a double precision object in `DATA`; the later standards forbid that (S1 4.3.8). Code that relied on the extra digits changes its value.
- Each revision defines more intrinsic procedures than the one before; an old external procedure whose name equals a new intrinsic is the intrinsic unless it has the `EXTERNAL` attribute (S1 4.3.2).
- A processor may supply a positive and negative real zero, and the sign of a result then differs for `SIGN`, formatted output, `ATAN2`, `LOG`, and `SQRT` of complex values from the early revisions (S1 4.3.6, 4.3.8).
- Fortran 90 left `MOD(x, 0)` processor dependent; the later standards prohibit a zero second argument (S1 4.3.7).
- The first column of formatted output no longer carries a processor-dependent meaning (vertical format control, S1 B.1, 4.3.6).

## 5. Interplay with MPI

The MPI standard states that "MPI-3.0 (and later) compliant Fortran bindings are not only a property of the MPI library itself, but rather a property of an MPI library together with the Fortran compiler suite" (S4 20.1.7). The facts that bear on a Fortran standard:

| Hazard | Source fact | Failure | Practice as an outcome | Sources | Holds across versions and implementations, or specific |
|---|---|---|---|---|---|
| Nonblocking buffers and the compiler | Local variables are assumed not to change across a call that does not receive them; a register may hold the value of `buf` across `MPI_WAIT`, and the compiler may "schedule the load of buf earlier than typed in the source" (S4 20.1.17.1) | The buffer holds stale or overwritten data when sent or read | The buffer has `ASYNCHRONOUS` where the code touches it between the start and the completion, within a `BLOCK` or a routine of limited scope as the standard's example does (S1 C.13); or the code calls the register-synchronization routine with the buffer after the wait | S1, S4 | The language rule is general; whether the library and compiler honor it is reported by `MPI_ASYNC_PROTECTS_NONBLOCKING` |

| Binding choice | `mpi_f08` is the only method that the Fortran standard fully supports; `mpi` and `mpif.h` are older; `mpif.h` is deprecated in MPI 4.1; `LOGICAL` arguments are not interoperable with C (S4 20.1.5, 20.1.10) | Code written to `mpif.h` has implicit interfaces and no argument checking | The program uses the module that gives explicit interfaces; the one it uses is in the run record (STND.MPI.2) | S4 | The set of modules is part of the MPI standard; which exists on a system is specific |

## 7. Modernizing legacy code without changing results

Steps that change no result by the semantics: converting source form (checked by identical output), adding `IMPLICIT NONE` and declaring each name (an undeclared name that was a misspelling shows as an error and is a defect found), replacing `COMMON` by a module with the same declarations in the same order and `SAVE` (a common block's storage association is the only reason to keep a layout), replacing a computed `GO TO` by `SELECT CASE`, replacing a labeled `DO` by `END DO`, replacing specific intrinsic names by generic names (the result kind then follows the argument kind), and moving external procedures into a module so the interface becomes explicit (this exposes mismatches and so may change a result that was wrong).

Steps that can change a result, to be recorded as separate steps: giving a literal a kind suffix; changing a default real to a named kind; turning an explicit-shape dummy into assumed-shape (the contiguity of the argument and the copy behavior change); removing an implicit `SAVE`; replacing `EQUIVALENCE` with `TRANSFER`; replacing a loop with `DO CONCURRENT` or an array statement (the order of floating-point operations may change); replacing a loop sum by `SUM` (the order of combination is the processor's choice, which the intrinsic reduction text states [not quoted]); and switching a deleted feature's extension to a standard form.

The practice that the studies support is a regression comparison before and after each step with the tolerance stated by the work (STND.VVUQ.1 and .5), since one study of climate-model code finds that "old Fortran features are still being used" in those models and proposes syntactic metrics to estimate the number of changes a program needs (S7, extract only).

## 8. Studies of defects in scientific Fortran codes

- Hatton's "T experiments" (S6, extract only): static deep-flow analysis of several million lines of C and FORTRAN 77 scientific code found statically detectable inconsistencies independent of application area, with interface inconsistencies about once in 7 interfaces in Fortran and once in 37 in C. A second experiment found agreement between independent implementations of the same algorithms degenerating from six significant figures to one. The 1993 study he cites reports a statically detectable fault every 80 lines of C and every 130 of Fortran, and the extract notes that the static study does not measure the effect on users. I could not read the paper itself; the figures come from a search summary, are marked [unverified], and are of FORTRAN 77 code of the 1990s, so they show the kinds of defect that explicit interfaces now prevent and are no measure of present code.
- Pipitone and Easterbrook (S5, full text): defect reports and fixes of three climate models, mostly Fortran, gave median defect densities mostly below those of an open-source comparison project under three ways of assigning defects to versions. Their text lists the limits: only suitably important defects are fixed and recorded, a fix has to be matched to a defect, and a low density can come with low quality in what is not counted. It reports no Fortran-specific taxonomy.
- The ICON case study and the interviews with its developers (found by search, not read; [unverified]) propose a "resolution-dependent" category of long-lived bug that shows when a model moves to a finer grid, and report that scientific testing is not standardized.
- I found no peer-reviewed study that classifies Fortran defects by language feature. The evidence that the hazards of sections 2 to 6 occur in practice is therefore the standard's own wording of what it leaves undefined, the static study S6, and one anecdotal forum thread (S8) in which results differed between build modes and uninitialized values were the suspected cause. Mariner-type stories of a lost character in a `DO` statement are folklore that I did not check and do not cite.

## 9. Compiler checks stated as outcomes

A conforming processor must be able to report: the use of an obsolescent form, the use of a form not permitted by the numbered syntax rules and constraints, including the deleted features, a kind not supported, characters or source form not permitted, inconsistent use of names, and a nonstandard intrinsic procedure or module (S1 4.2 para 2). The constraints of the standard that are numbered (such as C1140 to C1146 for `DO CONCURRENT`) are therefore checkable at compile time, and the rules that the standard states without a constraint are not: argument overlap, use of an undefined value, an out-of-range subscript, a shape mismatch under sequence association, an out-of-range integer, and the ordering of unsynchronized access. The outcomes a project can ask of its checks, then, are:

1. The build reports, and fails on, a use of a deleted form; the obsolescent forms that remain are listed.
2. The build reports a call without an explicit interface and a mismatch of the actual and dummy arguments in type, kind, rank, and count, across files.
3. A test run exists in which each array access is checked against its bounds, and each pointer and allocatable use is checked against its status.
4. A test run exists in which each use of an undefined local value is reported, or in which locals are given a recognizable value (a NaN for reals) so that a use shows in the result.
5. A test run exists in which an invalid operation, overflow, and divide by zero stop the program at the first occurrence, with the line.
6. A test run exists in which overlap of actual arguments, and unsynchronized access by threads or images, is reported.
7. A run records that a copy of an argument was made, where the processor can say so, for the dummies that are `ASYNCHRONOUS`, `VOLATILE`, or contiguous.

None of these outcomes names a tool; each is decided by a test run and its record (STND.CODE.4, STND.CXX.26 as the model). A check that the standard does not require can be absent from a processor, so the project's record says which of the seven it has.

## Timeless versus moving

Timeless (the model of the language, unchanged since Fortran 90 or earlier): explicit interfaces; the argument-association rules; sequence association; implicit `SAVE`; the absence of any requirement to diagnose an undefined value, an out-of-bounds subscript, or an alias; the processor-dependent kind of mixed-kind results; the default kind of an unsuffixed real literal; the statement that conformance does not ensure identical execution on all processors.

Stable but not old: `DO CONCURRENT` constraints and its locality (2008, 2018); the `IEEE` modules (2003, extended 2018 and 2023); `BIND(C)` interoperability and the descriptor interface (2003, 2018); coarrays (2008) and teams (2018).

Moving: the contents of the obsolescent and deleted lists (they grow with each revision, although 2023 added nothing); the support that processors give to the newer facilities; the `mpi_f08` and `mpif.h` status in MPI; the OpenMP rules for Fortran (assumed-size, allocatable privatization, the deprecation of `omp_lib.h` in r1); new features of the 2023 revision (conditional expressions, enumeration types, `typeof`).

A timeless standard should therefore name the outcomes (explicit interface, declared names, defined values, independent iterations, a stated floating-point regime) and leave the lists of deleted and obsolescent forms to the revision of the standard that the repository configuration names.
