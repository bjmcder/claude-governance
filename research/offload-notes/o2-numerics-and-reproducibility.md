# O2: Numerics and reproducibility of results computed on accelerators

## Method caveat

Every fetch returned a model-written extract of the page, not verbatim text, and every web search returned a model-written summary of result snippets. All findings below are therefore paraphrase, and numbers (ULP bounds, defaults) are as the extract reported them. No PDF was read directly. Where an extract contradicted itself or the page was truncated, the item is marked [unverified]. Frameworks and libraries (CUDA, cuBLAS, cuDNN, PyTorch, ROCm, CUB) appear only as evidence of hazards that a vendor-neutral standard should address. Primary documents for the OCP low-precision formats, the OpenCL numerical tables, the Vulkan float-control enumerations, and the HIP math documentation could not be read. The earlier notes r3 and r4 already cover OpenMP reduction order, `reproducible`, and the host-reference test pattern, so those points are cited, not repeated.

## Answer in brief

The custodian's direction is applied throughout: strict determinism is a choice where feasible; variation inside an agreed tolerance is no defect; a true race is a defect.

1. **State the numerical acceptance criterion before the first run.** Each offloaded computation declares one of: bitwise identical to a named reference, bitwise identical run to run on a named configuration, or equal within a stated tolerance. Strictness follows the consequence class. Vendor documents already distinguish levels (not guaranteed, run to run, across GPUs) and say the strongest is slowest and not always available [S13, S12, S2].
2. **Record the arithmetic contract of the device build.** Fused multiply-add contraction, fast-math or approximate-math options, subnormal handling, and division and square-root precision are written down per build, because the defaults differ from the host and between toolchains [S1, S3, S8, S9].
3. **Compare with a host reference using tolerances, never bit equality, unless item 1 demands it.** A difference from the host does not by itself show the device is wrong. Either side may be the less accurate one [S1, S3].
4. **Derive tolerances from error analysis and the documented accuracy of the functions used, then check them by test.** Device math functions are specified as bounded error in ULP, not correct rounding, and the bounds differ between host and device libraries and between precise and fast variants [S3, S1].
5. **Reduced precision is never silent.** Any use of tensor or matrix units, lower-precision internal formats, reduced-precision accumulation, or emulated arithmetic is an explicit, recorded choice, and the effective precision of each matrix product is stated [S2, S5, S7].
6. **Accumulate in a wider format than the storage format, and state the accumulator.** Half-precision and brain-float data need a wider accumulator, scaling, and range checks for overflow and underflow [S22, S6, S2].
7. **Treat reduction order as part of the design.** Any parallel sum, atomic accumulation, or split-K style partition whose order depends on launch shape, device, scheduling, or library heuristics gives results that vary, and the variation is declared or removed [S1, S2, S14, S28].
8. **Where reproducibility is required, use an order-independent or fixed-order method.** Options are fixed-tree reductions, reproducible summation (pre-rounding or binned), long fixed-point accumulators, and integer accumulation. Each has a stated cost [S18, S19, S13].
9. **Floating-point atomics that accumulate are a declared source of nondeterminism.** They are not a race, because each update is atomic, but their order is unspecified. A standard forbids them only where bitwise reproducibility is required, and requires a stated tolerance elsewhere [S2, S28, S12].
10. **Know the library's determinism switches, their defaults, and their cost.** Libraries may be nondeterministic by default. The deterministic switch can slow the code, disable fast algorithms, or raise an error for operations that have no deterministic form. The switch used is recorded with the result [S4, S2, S10, S11].
11. **Algorithm selection is an input.** Autotuning, heuristics, and benchmark-mode selection can choose different algorithms between runs, devices, and versions. Where results must repeat, selection is fixed or recorded [S2, S4, S11].
12. **Reproducibility claims name their scope.** A bitwise claim states what is held fixed: device architecture, device count, library and driver versions, launch configuration, tuning, and parallel layout. Vendors give no guarantee across architectures or, in general, versions [S12, S2, S13, S11].
13. **Random numbers are keyed to the computation, not to the thread schedule.** Counter-based generators keyed by logical index, seed, and step make streams independent of launch shape and device count [S17, S4].
14. **Test the edges of the number format.** Tests include values near overflow, subnormal values, NaN and infinity, signed zero, and cancellation, run under the production arithmetic options, because flush-to-zero and fast-math change exactly these cases [S3, S1, S6].
15. **Index and size arithmetic is checked for width.** Offset products formed in 32 bits overflow on large arrays. Widen before the first multiply or prove the bound, and test with sizes above 2^31 elements [S27].
16. **Cross-device variation is expected and tested.** Results are checked on each device class in use and again after any change of compiler, library, or driver, because results move with them [S12, S16, S15].
17. **Numerical contracts are written down as testable statements.** A kernel states its precision, ordering, tolerance, and reference oracle, so a disagreement between devices can be judged against an artifact [S23].
18. **Report variance, not a single run.** Training and iterative codes run repeated identical runs to measure implementation-level variance before claiming an improvement [S15, S14].

## Timeless versus moving

Stable (true since the first GPU computing guides and independent of vendor):

- Floating-point addition is not associative, so any change of partitioning changes bits. NVIDIA's 2011 guide, oneMKL, and 2024 studies all say this [S1, S20, S14].
- Fused multiply-add changes results relative to a separate multiply and add and is permitted by IEEE 754 operations; a difference from the host is expected [S1].
- Correct rounding is guaranteed for basic operations in IEEE mode, but not for transcendental functions, whose accuracy is bounded in ULP and differs by library [S3, S1].
- Atomic accumulation of floating-point values has unspecified order [S28, S19].
- Order-independent, fixed-point, and compensated methods exist and cost time [S18, S19, S21].
- Counter-based random generators decouple values from the schedule (2011) [S17].
- Bitwise guarantees are always scoped to a version and a hardware class [S12, S2, S13].

Moving:

- Low-precision formats: TF32, bfloat16, FP8 variants, and block-scaled MX formats are new within about a decade, with vendor-specific special-value rules still settling [S24, S5].
- Library defaults: the default of PyTorch's matmul TF32 flag changed in release 1.12 [S5, S7]; emulated FP32 and FP64 modes in cuBLAS are new [S2].
- Determinism infrastructure: determinism levels as execution requirements (CCCL) and error-on-nondeterminism switches are recent; documentation gaps were found as late as 2024 [S13, S4, S14].
- Algorithm selection and autotuning are increasingly default [S2, S11].
- Specification languages for kernel contracts are a 2026 proposal, not practice [S23].

The standard should therefore state outcomes (declare, record, bound, test) and avoid naming any format, flag, or library.
