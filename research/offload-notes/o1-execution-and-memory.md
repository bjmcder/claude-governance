# O1: Execution model and memory model of accelerator offload

## Answer in brief

1. Treat every launch, copy, and library call that "returns" as possibly incomplete. A result, a buffer, or a status is used only after a completion point (a wait, an event, a queue drain, or a defined dependency). This holds in CUDA, HIP, OpenCL, SYCL, and OpenMP. [S1, S4, S6, S10]
2. Check for errors at every completion point, not only at the call that was suspected. Errors from device execution are reported by a later call, so each completion point has an error check, and a debug mode that serializes work (blocking launches) is available to attribute an error to its cause. [S1, S2, S3, S7]
3. Define what happens after an unrecoverable device error. Some errors (device-side assertion, illegal address, launch timeout, device loss) leave the context or device unusable, and later calls may return the same or a different error. The program must stop, restart the device or process, or fail the job, and must not continue with results from the failed context. [S3, S7, S18, S19 (secondary), S22]
4. Know the ordering rules of the queue. Work in one in-order queue is ordered; work across queues is not unless an event or dependency says so; some default or legacy queues synchronize implicitly with others, and the setting can differ per compilation unit. Code states which it relies on. [S1, S5, S10, S14]
5. Host memory used by an asynchronous copy is valid and unmodified until the copy completes, and is allocated in the kind the copy path needs (page-locked or otherwise). A copy from pageable memory can silently become synchronous or be staged, so overlap is verified, not assumed. [S1, S4, S6]
6. Every launch configuration is validated against the device's limits and the problem size: group size, grid size, resources per thread, shared memory, and stack. A launch whose grid does not divide the problem size has a guard in the kernel. Index arithmetic uses types wide enough for the largest problem. [S13, S14, S16]
7. A barrier is reached by all threads of its group or by none. Control flow that reaches a barrier is checked for divergence, and "early return" from a kernel before a barrier is treated as a defect. [S9, S10, S12, S13]
8. No code assumes lockstep execution of the threads in a group, a particular subgroup or warp size, or the convergence of divergent threads. Group-level operations name the participating threads explicitly and are written for a size obtained at run time. [S9, S10, S11, S23, S24]
9. No kernel assumes that all work-groups or blocks run concurrently, or that one makes progress while another waits. Inter-group synchronization uses a mechanism the model guarantees (a kernel boundary, or a launch mode that guarantees co-residency and fails if it cannot) and never a hand-written spin barrier on a fair-scheduling assumption. [S8, S9, S15, S16]
10. Every synchronizing access (atomic, fence, barrier) states the scope of the threads it must order: thread, group, device, system. A scope that does not include the communicating thread is a data race even when the operation is atomic. [S6, S9, S11, S17]
11. Memory ordering on the device is not assumed to be sequentially consistent or coherent. Published hardware tests found stale reads, coherence violations, and failed locks in code that followed vendor tutorials. Device code uses the model's synchronization operations, is tested on each target, and is checked with a litmus test or a checker when it uses fences directly. [S15, S17]
12. Unified or managed memory is a convenience, not a coherence guarantee. Code states whether it needs concurrent host and device access, oversubscription, or atomics across host and device, tests for each capability at run time, and times the data movement. Access outside the supported model can fault or give a wrong result depending on hardware, driver, and operating system. [S7, S11]
13. Memory and handle lifetimes follow the queue, not the host scope. A buffer is not freed, reused, or destroyed while queued work uses it. Resources that block on destruction, or silently complete work, are documented. [S1, S9, S10]
14. Device memory exhaustion, stack and heap limits, and fragmentation are tested, and allocation failure is a handled outcome on host and device (null result or error code). [S12, S14]
15. Multiple devices, multiple host threads, and multiple libraries sharing a device each have an owner for ordering and for error state. Peer access and cross-device atomics are queried, not assumed. [S1, S7, S11]
16. Verification uses a host reference, runs with synchronization-stressing settings (serialized launches, small and odd sizes, different group sizes), and uses race, barrier, and memory checkers. A bug study found that conventional test cases catch most GPU bugs except synchronization bugs. [S15, S16, S17]

## Timeless versus moving

Stable for a decade or more:

- Asynchrony is the norm, completion points are explicit, and errors can surface at a later call. The same facts appear in CUDA, HIP, OpenCL, and SYCL (S1, S2, S4, S9). OpenCL 1.x and SYCL 2020 use the vocabulary of events and in-order or out-of-order queues; the CUDA stream model is older still.
- A barrier must be reached by all threads of a group. This is in OpenCL, SYCL, and CUDA (S9, S12, S16).
- No model promises that separate work-groups run concurrently. SYCL says weak parallel progress at best (S9); CUDA gives "parallel" progress, and concurrent progress only in cooperative grids (S8); the 2016 paper's deadlock hazard remains (S15), and the 2021 paper says Vulkan and Metal say little (S16).
- Wavefront and warp size vary by vendor (S24, S9).
- Atomics and fences are scoped, and a scope smaller than the communication range is a race (S6, S12).
- Launch configuration has limits, and exceeding them produces errors (S12, S13).
- Pinned or page-locked memory is needed for real copy overlap (S1, S6).

Still changing:

- Thread scheduling. Independent thread scheduling arrived with Volta (CUDA 9, 2017) and made years of warp-synchronous code unsafe (S10, S11). The compatibility mode (`-arch=compute_60 -code=sm_70`) is a transition aid, not a promise.
- Unified memory. The same API now covers legacy fault-less, page-fault-based, pageable, and hardware-coherent systems, with different rules for concurrent access, oversubscription, and atomics (S7). Expect the capability list to keep changing.
- Scopes and memory models. CUDA's scoped memory model is a recent formalization (S6); the 2015 study showed the earlier documentation was wrong in places (S17).
- Cooperative and cluster-level launch. Cooperative grids and thread-block clusters introduce groups with progress guarantees that other groups lack (S8). This is where progress models will move.
- Progress models. The 2021 work shows that the intuitive occupancy-bound model does not hold on some GPUs (S16).
- Error handling. HIP's `hipGetLastError` changed in ROCm 7.0 so that it no longer returns non-error statuses (S2). Details of what is sticky differ by driver and are not stable.
- API conventions: the legacy and per-thread default streams, deprecated callbacks (`cudaAddCallback` is "slated for deprecation," S1).

Consequence for a standard: say what must be shown (completion point, error check, scope, tested size) and not name an API.
